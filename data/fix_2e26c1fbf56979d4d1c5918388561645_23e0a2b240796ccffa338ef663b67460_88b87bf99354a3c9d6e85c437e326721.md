1. 一条 Agent 工作链里都有什么**

完整的 Agent 工作链，主角并不只有 Agent。

输入得先进系统，任务得有人触发；某些情况下，还得先判定任务属于哪一类，再分派给对应的 Agent。

干活时它会调用工具，收工后把成果写进文档、表格或业务系统，其中关键的部分再送到人手里复核。

建议从以下七处逐一排查：

[PRE2]

**4.1 人的位置**

授权、核实事实、扛业务责任，这些都由人来做。

例如：

- 核对纪要准不准；
- 拍板哪些行动算真正生效；
- 确认责任人与交付期限；
- 审核钱款、对客户的许诺、公开发布以及敏感信息。

**4.2 Agent**

Agent 承担的是一段相对完整的工作：读懂上下文、做出判断，最后交出可被检验的成果。

三个问题可以帮忙界定：

1. 这算不算一段完整的工作？
1. 过程中需不需要结合上下文来判断？
1. 完成后有没有独立的成果可供核查？

4.3 工具、Skill、MCP 或 API**

这类能力用来帮 Agent 落成一个具体动作。

例如：

- 把音视频下载下来；
- 转换文件格式；
- 做语音识别；
- 读取或新建飞书文档；
- 查询表格或外部数据；
- 发出消息。

工具由 Agent 来调用，但工具自身未必是 Agent。

**4.4 固定流程**

当规则足够清晰，只剩下触发、转发、按点执行或改字段这些动作时，交给机器人、脚本或工作流即可。

例如：

- 收到固定格式的消息就转发出去；
- 每天到点自动开工；
- 把结果写进指定字段；
- 按规则推送提醒。

**4.5 业务系统或内容来源**

这一类环节，负责把内容生产出来、存下来或者托住。

例如：

- 飞书会议；
- 飞书妙记；
- 飞书文档；
- 文件夹；
- 邮箱；
- 多维表格；
- CRM；
- 项目管理系统。

架构师要做的，并不是把每个步骤都改造成 Agent，而是想清楚每一步交给谁最合适。

5. 判断这些环节之间是什么关系**

[PRE3]

**5.1 各干各的活**

两个 Agent 面对的是不同类别的任务，各交各的成果，彼此之间无需连线。

[PRE4]

**5.2 共用同一批工具、资料或系统**

两个 Agent 也许读同一份知识库、待在同一个飞书空间，或调用同一套工具，但它们之间并不互传结果。

资源共享，并不等于上下游关系。

**5.3 一棒接一棒**

如果上游 Agent 的产出经常被下游 Agent 当作原料，且先后次序稳定，那就适合把交接建起来。

1. 这样的交接发生得频繁吗？
1. 上游那边有没有清晰的交付物？
1. 下游这边知不知道该怎么验收？
1. 连起来之后，能否少掉复制、等待和反复说明？
1. 一旦出岔子，能不能判断该退回哪一端？
1. 哪一步需要人来把关，是否心中有数？
1. 两个 Agent 是否都能独立运行？

**6.1 这一轮决定连接**

若存在合适的关系，就挑一段 Agent 之间的前后衔接。

写清六件事：

- 上游是谁；
- 下游是谁；
- 上游交出来的是什么；

**6.2 这一轮先不连**

碰到下面这些情形，可以判为“暂不连接”：

- 交接本身很少出现；
- 输入与结果都还没定型；
- 权限与责任尚未讲清；
- 后续工作交给人做更合适；
- 两个环节只是共享资料，并非一前一后；
- 连起来之后的维护开销，比省下的时间还大。

写清四件事：

- 已经找到的上游与下游；
- 暂不连接的理由；
- 接下来打算继续观察或补齐什么；
- 哪些条件具备后可以重新评估。

判定“暂不连接”，同样是一种有效的架构结论。
