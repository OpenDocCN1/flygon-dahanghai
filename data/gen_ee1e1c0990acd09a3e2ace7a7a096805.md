# 从零做 Chrome PDF 插件：我的试错与避坑记录

作者：颜过｜2021-08-11

PS：这篇内容此前仅在小范围内部圈子流传，最近一次是在帅张张哥群里做的分享。熟悉我的财友大多先想到“跨境电商”这个标签，但今天先放下跨境，聊聊出海小工具从 0 到 1 的试错。程序员朋友往往把注意力放在技术精进上，这次我主要讲技术之外的经验；有不足的地方，后续迭代再补充分享。

一、先定主战场

选方向时，我主要看两个维度：开发难度和开发耗时。按这个维度大致排序：电脑PC端 ≥ 手机端Apps > Web端SaaS或网站 > 插件（电商类Apps，比如Shopify Apps、Chrome插件、WordPress+WooCommerce等周边插件<即wp+woo>）。

凭借过去的跨境电商经验，电商类小工具本来更顺手，也就是Shopify Apps或wp+woo。但前者上架难度明显更高；后者生态相对成熟、需求也多，很多Shopify Apps的需求可以直接搬到wp+woo上做。可时间不等人，再加上我希望快速拿到反馈，遵循“从0到0.5”的原则，最后把赛道锁定在Chrome插件。它基本只需要JavaScript+css等前端知识，再加一些服务器知识（真做起来盲区不少），就能做出一个产品。小产品通常只解决一个小需求，审核也快——大约12小时就能审核上线，之前查资料还说会更快。

二、细分市场与需求怎么选

挑细分市场或需求，有点像跨境选品。新人常觉得这是玄学，但真动手做出第1个小产品后，感觉会慢慢长出来；如果整天只想不做，大概率就没有然后了。

这次选小工具，我也绕了些固有思维的弯路。最早摆在面前的是两条大路：电商类小工具，或wp+woo小工具。可它们等于没选，因为没法立刻开干；再加上开发人员怎么选，又耗掉不少时间（后面再讲）。最后，一位在美国做物流的朋友提出一个PDF相关的小需求，付费环节也由此跑通（半买半送，后面相关的PDF需求PDFXYZ——暂时隐去插件名，等公开后再说，因为上架已有一段时间——会免费送她一整套小插件使用）。她付了两笔49.99美金。钱不算多，但正向反馈最重要。

最终锁定PDFXYZ这个细分需求，还有几个原因，值得细品，尤其对想进入新市场的人：找个细分点，快速试、小成本跑通全流程，先完成再完美。另外deadline也很关键——对小众产品或市场尤其重要，开发进度一拖，各种成本就会上来。

此外，这个PDF需求在GitHub上能找到相关实现源码（虽然用的是其它语言，但在Chrome插件里可以复用），等于借前人的轮子，加快进度。

PDF的各类需求在海外市场很大，直接Google一下，竟有250多亿条搜索结果。软件有边际效应，开发出来后的维护成本很低。做这个需求，也是为了先试水Chrome插件市场，并积累PDF需求的第一批种子用户。周边可拓展的需求太多了，每个子功能都能做成一个小工具，逐渐形成小工具矩阵（是不是有点跨境多账号的味道）。

三、想和做之间的各种坑

3.1 招人坑

这里浪费了很多时间。一是具体需求还没太确定就去招人，而且是在国外平台，比如fiverr、upwork等freelancer平台。

有些事只有真正做过，才知道坑有多深。就像Chrome插件PDFXYZ，看着简单，里面却有几个难点，需要有一定经验、能主动解决问题的程序员才搞得定。

找老外做开发，你得把实现细节1、2、3、4、5……拆得足够细。否则加上时差，再碰上对技术框架不熟（我的编程语言和算法套路基本都还给大学老师了），来回沟通更是难上加难。

如果要找老外开发，一定先把需求列细，直接让他实现code；不然开发时间和进度会拖死你。最重要的是，多找几个人对比，多磨合几轮，才能找到合适的。

最后我找了两个朋友（朋友L一直帮我处理程序上的事，有全栈能力，但需要时间来实现；朋友Y是另一个朋友介绍的大公司前端大牛）做两个版本，需求相同。为什么这样做？因为我不只做这一个插件或小工具，后面还会有N多个（如果你有程序员朋友想变现，也可以推荐给我）。前面多次提到，开发时间对小工具来说是个大坑，拖得越久，成本只增不减。这也是相互磨合的过程；开发这活还是技术优势主导，差一点，就真的需要时间打磨，别无他法。

3.2 业务流程坑

做小众市场，先行原则是：找别人已经赚到钱的需求，再往深挖（最直接的是看差评，看能不能解决这些问题），这样离变现不会太远。

有句话叫，想学会游泳，至少得先下水；否则动作再漂亮也没用。先行原则前面提过：PDF这个大工具周边其实有很多需求，用户基数也足够大，先积累种子用户，能收到第一块钱的用户更好；再去拓展其它需求，赚钱是迟早的事。先下水，就直接先模仿，把核心需求实现，尤其把支付环节实现（Chrome插件以前有Google Pay支付，现在没有官方支付支持了，但能接第三方；支付坑下面展开讲）。

说回PDFXYZ这个小工具的核心需求。朋友L用中间服务器来实现，PDF文件基本能无损呈现（也就是文件清晰度，因为PDF文档要么是文字，要么是图片，还有其它格式合成的），能满足客户真实需求，但这里有服务器上传下载的问题，还有文件大小的门槛——文件大，下载时间就长。文件一大，插件体验就极差，会卡在那里半天动不了，所以只能限制大小，设为10M。

朋友Y直接用js api实现，但文件下载下来会模糊（客户的核心需求实现还差一些）；同样有文件上传下载问题，不过文件大小限制更大一些，为30M。

3.3 支付坑（大坑）

国外工具、需求或产品，除了广告变现（Google Adsense），常见变现方式还有：捐赠（PayPal）；通过分享产品等知识，用affiliate模式（分销赚佣金）来实现；最直接的方式当然就是直接收费。

Chrome插件大多数情况下只能选捐赠或直接收费。结果现在PayPal账号不支持国内账号的捐赠。

直接收费方面，因为Google Pay官方支付停止，但接受第三方支付。你可能第一反应是PayPal，但不好意思，虚拟产品PayPal不支持（大型软件应该会有收款白名单）。其他选择还有stripe等，但现在申请门槛非常高，申请下来也有被封号的风险。

现在收款先试的是Sendowl（可以再转PayPal；目前测试结果，几十美金通过Sendowl付款链接，PayPal是直接到账的）。这个工具是壹树老板（插件大佬，👸号：树下随想）推荐的，尤其在支付环节帮了大忙。壹树老板也趟过无数坑（如果你想问，请付费，真的绝对超值）。

因为Sendowl是Web端网页支付，插件端要有支付回传（webhooks），确认用户已经支付成功。熊（全栈大牛，大学同学，之前的👸号介绍过）和壹树老板的综合建议是：

不做登录，就可以生成一个本地唯一标识Key；用户付款后，生成标识Key，保存到数据里（或者用户本地电脑缓存）；另外最好手动或自动再给支付邮箱发一封邮件，把Key发给用户。如果用户卸载了，可以用这个Key来识别。

另外插件内不支持回传确认，如下图，就会卡死在那里，因为没有回传确认是否支付成功。朋友Y是直接单独新开浏览器标签页，让付款用户通过Sendowl网页链接付款。

3.4 图标图像坑

这个坑，估计大多数独立开发者只有真有一款小工具跑出来后才会意识到；但往往这个时候，如果造成侵权，你的款都可能被扣光。

前文提到是PDF需求，图标方面，朋友Y直接用了Adobe PDF的图标。虽然辨识度极高，但这个潜在小隐患可能让你全盘皆输。

也许你没碰到过，所以看到这个坑会觉得有夸大嫌疑。真没有。想起N年前，第一次做私模，做硅胶材质的汉堡制作工具，因为一家加拿大公司把这个细分类的常用词都注册成商标了，导致当时在亚马逊仓库的货、在途的、工厂生产的，都得换包装（还是彩盒），产品上的LOGO和产品词得去掉。这样一处理，小几十万没有了……

3.6 推广坑

简单优化后的数据，表现最好的区域为新加坡，0.5—0.7美金一个安装；精细化优化，成本至少可以降一半以上。30%的卸载（数据量基数不大），另外同类产品功能差不多的情况下是免费的，PDFXYZ这个小工具性能也要再优化。安装率45%，即差不多2个人看，有1个安装；说明需求还是有的，流量也算精准。
