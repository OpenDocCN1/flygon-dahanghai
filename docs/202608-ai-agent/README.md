### 01. 本期航海介绍

**1. 这个项目是什么**

很多人已经会用 AI 写文案、整理会议纪要、制作表格、撰写周报、优化客服回复话术，但大多数使用还停留在“问一句，答一句”。你想让它帮你做事，还是要自己复制资料、描述背景、提醒格式、检查结果，下一次又从头来一遍。

Agent 要解决的是更进一步的问题：把一段重复、规则明确的工作流程，交给 AI 自动执行。

比如，每周都要整理行业信息、写周报、生成会议纪要、回复客户问题、更新数据表、产出内容初稿，这些工作本身不一定难，但很消耗时间。如果能把岗位、流程、判断标准和工具连接好，Agent 就可以像一个“AI 员工”一样，按你设定的规则接收任务、调用工具、输出结果，并留下可检查的运行记录。

本期航海要带你跑通的，就是用Codex + Hermes +飞书 CLI这一套技术栈，搭出自己的第一个 Agent，将一项你每周重复做 3 次以上的工作，交给它去实现自动化。

你可以从一个简单但真实的场景开始，回忆一下你工作中高频出现的某项重复工作，比如自动整理飞书文档、读取评论生成回复、生成内容草稿、整理客户信息、汇总项目进度、做数据记录和复盘等等。

**将这个工作内容，做成一个最小可运行版本的** Agent ，让它替你自动完成这件事。

先做出一个能干活的 Agent 员工，逐步增加它的功能和稳定性，再理解多 Agent 团队和企业 AI 服务的可能性。

**3. 航海期间需要交付什么**

21 天内，你需要完成**必修关卡 1-6**的所有作业，并最终完成一个**可运行、可展示的 Agent**。

它可以是资料整理 Agent、会议纪要 Agent、周报 Agent、客服回复 Agent、选题整理 Agent、内容初稿 Agent、数据更新 Agent，也可以是你自己业务里的某个小岗位。

你最终需要至少提交 3 样东西作为佐证：

| 你交什么 | 证明什么 | 是什么 |
| --- | --- | --- |
| Agent 网址链接 | 它能被公开看见 | 一个别人点开就能访问的展示网页链接 |
| 1 次成功运行截图 | 它最近真的自动干过活 | 输入前 → 运行中 → 输出后的证据 |
| 使用说明书 | 别人知道它省了什么人工、怎么用 | AI 生成的一份说明文档 |

**需要注意：这里的 Agent 网址链接**，指的是展示页，不是真正的在线调用页面。

也就是说，别人可以访问、了解你的 Agent，但不能直接在网页里与你的 Agent 对话或调用它完成任务。

为什么本期采用展示页，而不是直接部署上线？

因为真正让别人在线使用你的 Agent，通常还需要完成部署，并承担一定的运行成本，例如服务器、模型调用（Token）等费用。当其他人使用你的 Agent 时，也会持续消耗这些资源。

对于大多数同学来说，现阶段更重要的是先完成一个能稳定工作的 Agent，而不是一开始就投入部署和运维。

如果你的能力和需求都已经具备，当然可以进一步完成部署上线。部署成功后，别人就可以真正在线体验和使用你的 Agent，而不仅仅是查看展示页。

不过，这部分属于**跑通 Agent 基础闭环后**，可以自行探索的高阶玩法，不在本期航海的学习范围内。

每一关的作业都会帮助你逐步完成最终成果，因此所有必修关卡的作业都很重要，需要完成。

5. 为什么选 Codex + Hermes + 飞书 CLI？

**可**能你已经在用 Codex ，觉得它已经可以直接完成很多事情，为什么还要接入 Hermes 和飞书 CLI？

这是因为，**让 AI 完成一次任务**，和**拥有一个长期工作的 Agent**，其实是两件不同的事情。

如果只是偶尔处理一次工作，直接打开 Codex 对话，让 AI 帮你完成就够了。

但如果希望这项工作能够反复使用、长期维护、持续优化、定期自动触发，甚至让团队成员也能直接使用，就需要把它沉淀成一个业务场景内真正的 Agent。

而这三个工具，分别承担了不同的角色：

Codex 负责降低开发门槛，Hermes Agent 承接 Agent 能力能24小时运行，飞书 CLI 连接真实协作场景。

对普通人来说，这是一条相对清晰的从 0 到 1 路线。

| 工具 | 在本船里负责什么 | 为什么选它 |
| --- | --- | --- |
| Codex | 会动手干活的人：搭项目、写脚本、跑命令、调用工具、检查结果 | 你把目标和约束说清楚，它能把工作流变成可执行动作，让 Agent 不只停留在聊天框里 |
| Hermes | 让这个人长期值班的调度台：承载任务入口、运行节奏、状态记忆和持续调度 | Codex 擅长当下动手，Hermes 让这套工作可以被持续调用、长期运行，不用每次从零解释 |
| 飞书 CLI | 连接飞书的工具箱：读写文档、表格、消息、日历等真实工作数据 | 很多工作数据都在飞书里；接上这套工具箱，Codex 才能真的进入你的工作流 |

三个工具组合在一起，就形成了一个最小闭环：

• **Codex**：是会动手的人，负责开发和调试 Agent；

• **Hermes**：是让这个人长期值班的调度台，负责承载和运行 Agent；

• **飞书 CLI**：是连接飞书的工具箱，负责让 Agent 真正进入你的工作场景。

**接**下来的【开工前准备】，我们会带你把这三个工具安装好，并完成基础配置，为后续正式搭建 Agent 做准备。

### 03. 本关小结

最小 Agent = 先让 AI 真正替你完成一次可见任务。

本关借助【音视频转录Agent】 Demo，先跑通一次从输入到处理再到输出的完整链路。

只要 Agent 能接收任务、调用工具、生成文件，并且你能用截图证明结果存在，第一个最小 Agent 就已经成立。

**核心四个动作：**

1.  **准备一个明确输入**：先选公开可访问、长度适中的音视频材料，让 Agent 有东西可处理。

1.  **搭好可对话入口**：用 Codex 创建 Hermes Agent 和飞书 Bot，完成私聊或群聊接通测试。

1.  **发布一个具体任务**：把下载、转录、保存文件这些动作说清楚，让 Agent 按步骤执行。

1.  **检查可见输出和边界**：确认转录结果文件存在，再让 Agent 说清楚自己能做什么、不能做什么。

跑通这一关后，你已经有了第一份真实体感：Agent 不是一个抽象概念，而是一条可以被验证的工作链路。

**如果你觉得这个 Demo 还有很多不足，甚至离****真正能替你**工作还有点距离，这都是正常的。因为这一关的目标不是做出一个完美的 Agent，而是先建立体感：理解一个 Agent 是如何工作的，以及一条完整的工作链路是如何跑通的。

### 01. 本关重点

关卡 1 你已经通过 Codex + Hermes +飞书，跑通了一个最小 Agent Demo：把音视频链接交给它，它能下载、转录，并生成了一份【转录结果】。

你可能会有一个疑问：

**既然 Codex 一句话就能完成这些事情，为什么还要接入 He**rmes 和飞书，再搭一个 Agent？

这是很多人第一次接触 Agent 时都会有的疑问。

因为**完成一次任务**和**拥有一个长期工作的 AI 员工**，其实是两件不同的事情。

如果只是偶尔处理一次音视频，直接打开 Codex 对话，让 AI 帮你完成就够了。

但如果这项工作每天都会发生、需要反复执行，甚至希望别人也能使用、长期维护和持续优化，那么就需要把它沉淀成一个真正的 Agent。

它有自己的岗位、固定的工作流程、稳定的调用入口，也可以不断积累规则和经验。以后无论是你自己，还是团队成员，都可以直接把任务交给它，而不用每次重新解释一遍。

**所**以，本期航海真正想教你的，不是”怎么让 AI 完成一次任务”，而是”怎么培养一个可以长期工作的 AI 员工”。

你也会发现，这个 AI 员工就像刚入职的实习生一样，非常很粗糙：在【音视频转录】这件事上，它能帮你完成基础动作，但转录文字可能不够准确，内容只是原始文字、没有重点整理，文件也还只是保存在本地，不方便线上修改、多人同步和长期沉淀。

这很正常。

实习生想把一项工作做好，需要有人带：告诉它负责哪类工作、接收什么输入、按什么步骤处理、交付什么结果，以及什么情况必须停下来找人确认。

Agent 作为 AI 员工也是一样，需要清晰的岗位定义、稳定的工作流程、明确的交付标准和必要的人工兜底，才能从“能跑一次 Demo”逐步变成“能承担一项具体工作”。

给你一些常见的工作线索作为参考，有哪些戳中你的痛点：

**职场人常见的重复工作**：

• 整理资料：把一堆文档/表格/聊天记录整理成结构化内容

• 会议纪要：每次开完会花半小时写纪要

• 表格报表：从多个来源复制粘贴数据到一张表

• 客服回复：很多客户问题都是重复的，不需要每次都从零思考

• 销售话术：根据不同客户生成个性化方案

**业务者常见的重复工作**：

• 内容生产：选题→写稿→排版→配图→发布

• 素材采集：每天刷小红书/公众号/即刻找选题灵感

• 客户跟进：新线索来了要回复、老客户要跟进

• 数据整理：从多个平台拉数据做分析

**判断标准**：你至少列出了 3 个重复工作，可以仔细想想这周你做的最烦、最机械、最想交给别人做的三件事是什么。

**1.2 用五个维度筛选**

把 1.1 中列出的工作逐个代入下面 5 个问题。每回答一次“是”，得 1 分：

1.  **是不是会反复出现？**每周都会遇到，或者每个项目、每次活动中都会重复出现，需要持续投入时间。

1.  **输入是不是相对稳定、容易识别？**每次收到的材料类型比较固定，比如聊天记录、文档、网页、表格，不会每次都完全不同。

1.  处理步骤和判断规则是不是比较明确？大部分情况下都有相对固定的操作顺序和判断标准，不需要每次临时决定怎么做。

1.  **输出结果是不是清晰、可验收？**做没做完、结果对不对，可以通过文档、表格、消息、链接等直接检查。

1.  出现问题时，是不是可以人工兜底？Agent 完成后，你可以在发送、发布或交付前检查一遍，即使出错也不会立刻造成严重损失。

**得分 ≥ 4 分：****很适合优先尝试 A****gent 化。得分** 2–3 分：可以尝试，但可能需要先简化流程、补充规则或增加人工检查。得分 ≤ 1 分：暂时不适合优先 Agent 化，可以先放进“不做清单”。

**1.3 一句话岗位定义**

用这个公式：

Plain Text

```
我希望我的的 Agent 员工 = 当收到 [输入] 时，自动 [做什么]，并把结果 [输出到哪里]
```

举几个真实例子：

• "当收到一个选题和参考素材时，Agent 自动提炼素材、生成大纲和初稿，并把结果创建成飞书文档。"

• "每周五下午，Agent 自动拉取我飞书多维表格里的本周工作记录，生成周报草稿，发到我的飞书消息。"

• "当客户发来询价消息时，Agent 自动检索知识库，生成报价方案草稿，写入飞书多维表格的待审核列。"

**判断标准**：这句话里包含了输入、动作、输出三个要素。如果缺了哪一个，补上再往下走。

### 04. 本关小结

**Agent 岗位卡 = 把一个“能跑的 Demo”**，变成一个“说得清职责的 AI 员工”。

关卡 1 你已经看到 Agent 可以完成一次可见任务；

这一关完成，是把这份体感收拢到自己的真实工作里：先找出重复工作，再判断哪一项适合交给 Agent，最后把它写成一张清楚的岗位卡。

第一个正式 Agent 更适合从一个小岗位开始：任务反复出现、输入来源明确、处理步骤能说清、输出结果能验收，做错了也可以人工兜底。

**核心四个动作：**

1.  **列出重复工作**：先用 AI 对话帮你把每日、每周、被动触发的重复任务整理成候选清单。

1.  **用五个维度筛选**：让 AI 做初筛，但由你最终确认频率、输入、规则、验收方式和风险边界。

1.  **写一句话岗位定义**：用“当收到什么输入时，自动做什么，并输出到哪里”把岗位说清楚。

1.  **生成 Agent 岗位卡**：补齐输入、处理动作、输出、成功标准、人工兜底和本期不做清单。

3. 翻译成 Agent 工作流

到这一步，你已经把自己的工作流程和判断标准梳理清楚了。

接下来，我们要把这些经验进一步翻译成Agent 能真正理解和执行的工作流。

这里会使用一种常见的规范写法（RFC 2119），目的是让 Agent 清楚区分：

• MUST：**哪些事情必须做**；

• SHOULD：**哪些情况建议做**；

• MAY：**哪些属于可选操作**；

• MUST NOT：**哪些绝对不能做**。

不用担心这些英文术语， AI 会帮你按照这种规范整理。

依旧是同一个👇 复制这段 prompt 发给 AI：

Markdown

```
你现在是一名 AI Agent 架构师。

将上面的【工作的流程】和【判断标准】汇总

请不要简单润色，而是把它抽象成一个真正适合 AI Agent 执行的工作流。

要求：

第一步，理解人工真正完成的目标，而不是照抄步骤。

第二步，删掉所有属于人的操作，例如：
- 打开网页
- 点击按钮
- 复制粘贴
- 登录网站
- 上传文件
- 下载文件
- 手动整理

改成 AI 真正应该执行的能力。

第三步，把流程改写成下面结构：

## Agent 工作流：xxx

### 触发条件

什么时候开始执行。

### 步骤

每一步描述 AI 的行为。

遵循 RFC2119 规范：

- MUST：必须执行，没有例外。
- SHOULD：通常应该执行，特殊情况可以调整。
- MAY：可选执行，根据情况决定是否进行。
- MUST NOT：禁止执行，任何情况下都不能做。

每一步尽量写成：

动作
判断
异常处理

不要写人成本。

### 成功标准

什么叫真正完成。

要求尽量可验证。

### 失败处理

所有可能失败情况。

每一种失败都给处理方案。

### 人工兜底

哪些情况必须暂停交给人确认。

不要写实现代码。

不要考虑具体平台。

重点描述 Agent 应该如何思考和执行。
```

```

### 触发条件
用户发送一个播客/视频/音频链接，或上传一个本地音频文件。

### 步骤
1. MUST 确认收到链接或文件。如果格式不明确，MUST 反问&quot;请发送播客/视频链接，或告诉我本地文件路径&quot;。
2. MUST 判断来源类型：小宇宙、B站、YouTube、飞书妙记、本地文件、其他。
3. SHOULD 优先查找是否有现成字幕/逐字稿（如 YouTube 字幕、飞书妙记转录）。有字幕则直接使用，跳过 ASR。
4. 没有现成字幕时，MUST 使用 yt-dlp 下载音频（或直接读取本地文件）。
5. MUST 检查音频格式和时长。超过 2 小时的音频 SHOULD 分段处理。
6. MUST 使用 faster-whisper 或 mlx-whisper 进行语音识别转录。
7. MUST 清洗转录稿：去时间戳、去说话人标签、去口水话和重复句、修正常见 ASR 错词（尤其人名、公司名、术语）。
8. MUST 按话题分段，加简短标题。标题 MUST 来自真实内容，MAY NOT 使用&quot;其他有效观点&quot;&quot;补充说明&quot;等模糊标题。
9. SHOULD 对重要判断、金句、关键数据适度加粗。
10. MUST 把整理稿写入飞书文档，标题为&quot;[来源平台]-[原标题]-整理稿-YYYY-MM-DD&quot;。
11. MUST 验证飞书文档目录结构和权限，确认用户能打开。
12. MUST 把飞书文档链接交付给用户。

### 成功标准
- 无时间戳、无说话人标签
- 无&quot;其他有效观点&quot;等垃圾桶标题
- 不是摘要式要点，是分享式提纯稿
- 保留了关键案例、数字、判断链和重要原话
- 主要 ASR 错词已修正
- 飞书文档目录正常、用户有访问权限

### 失败处理
- 链接无法下载 → 报告原因（平台限制/需要登录/地区不可用），建议用户换链接或提供本地文件
- 音频超长（&gt;2小时） → 自动分段处理，每段独立转录后合并
- ASR 转录质量极差（大量乱码） → 标注&quot;转录质量异常，建议人工校对&quot;，仍交付初稿
- 飞书权限授予失败 → 交付文档链接，附注&quot;文档已创建但协作者权限未完成，请手动添加&quot;

### 人工兜底
- 涉及非公开音视频（付费课程、私密会议）时，MUST 停下来问用户确认授权
- ASR 无法确认的专有名词标注[待确认]，由用户最终校对
- 整理稿交付前，用户可选择先看大纲再决定是否继续
```

**6.不同 Agent 类型的重点差异

不同类型的 Agent，关注的重点会有所不同。

可以对照你的 Agent 属于哪一类，重点补充对应的信息。

**6.1 文档型 Agent**

（内容创作、会议纪要、报告生成等）重点关注：

• 输入材料的读取顺序和优先级；

• 输出格式、风格、长度等规范；

• 内容质量检查标准（如事实核查、格式检查、是否遗漏关键信息）；

• 引用来源、敏感内容等处理规则。

**6.2 表格型 Agent**

（数据整理、报表汇总、信息统计等）重点关注：

• 字段之间的映射关系；

• 数据更新规则（新增、覆盖还是合并）；

• 缺失值、重复值、异常值如何处理；

• 哪些情况需要报警或人工确认。

**6.3 消息型 Agent**

（客服回复、通知推送、私聊助手等）重点关注：

• 什么事件触发执行；

• 回复边界（哪些能答、哪些不能答）；

• 不同场景的回复策略；

• 哪些情况必须暂停并转人工处理。

**6.4 流程自动化 Agent**

（审批、文件流转、多工具协同等）重点关注：

• 每一步调用哪个工具；

• 工具失败后的重试策略；

• 上下游数据如何传递；

• 哪些步骤必须等待结果，哪些可以并行执行；

• 中断后如何恢复执行。

每个 Agent 都有自己的特点，可能兼具多个类型的部分特点。没有一套规则适用于所有场景。

根据你的实际业务不断完善这份工作流，比一开始追求面面俱到更重要。

### 03. 本关小结

**Agent 工作流 = 把岗位卡里的职责，翻译成 A**gent 看得懂、能执行、可检查的步骤。

关卡 2 你已经定好了第一个正式 Agent 的岗位，知道它要服务谁、接收什么输入、交付什么结果。

这一关完成的是从“岗位”到“流程”的拆解：先还原你人工做这件事的真实步骤，再把每一步里的隐含判断、异常情况和人工兜底点写出来，最后整理成 Agent 可以照着执行的工作流。

Agent 最怕的不是任务复杂，而是流程模糊。人可以凭经验跳步、补漏、临场判断，但 Agent 需要你把这些经验显性化：什么情况必须做、什么情况应该做、什么情况可以不做，以及什么时候必须停下来问人。

**核心四个动作：**

1.  **还原人工流程**：先让 AI 生成一版人工原流程，再由你删掉不真实的、改掉不准确的、补上遗漏步骤。

1.  **挖出关键判断点**：把“我一看就知道”的经验说清楚，写成判断条件和判断依据。

1.  **翻译成 Agent 工作流**：用 MUST / SHOULD / MAY 把动作、判断、异常处理和人工兜底写成规则。

1.  **画成流程图**：把核心步骤和至少 2 个判断节点画出来，让人能复核，后面也能写进 Profile。

完成这一关后，Agent 就不只是知道“自己负责什么”，也知道“这件事应该怎么一步步做”。

3. 不同类型的 Agent 的重点差异

前面的步骤是通用的，但不同类型的 Agent，真正需要写清楚的规则并不完全一样。

你不需要把下面所有内容都写进 Profile，只需要找到和自己 Agent 最接近的类型，重点检查对应内容有没有写清楚。

**3.1 内容生产类 Agent**

例如：文章写作、短视频脚本、选题策划、社交媒体文案等。

Profile 中要重点写清楚：

• **写给谁看：**目标读者是谁，他们关心什么，能看懂什么。

• **写成什么样：**文章结构、字数范围、语气、格式和常用表达。

• **不能怎么写：**不允许出现哪些词、哪些语气和哪些表达方式。

• **信息从哪里来：**可以使用哪些资料，不能编造哪些内容。

• **如何自检：**是否跑题、是否重复、是否有空话、是否符合要求。

• **什么时候询问用户：**主题不清楚、资料不足或写作要求冲突时，不能直接猜。

这类 Agent 最容易出现的问题是：看起来写完了，但内容不符合你的风格，或者为了写得完整而编造信息。

3.2 音视频转录与资料整理类 Agent

例如：音视频转录、会议纪要、课程笔记、采访整理等。

Profile 中要重点写清楚：

• **支持什么输入：**音频、视频、网页链接、飞书妙记还是本地文件。

• **如何处理原内容：**是否去掉时间戳、口水话、重复内容和无意义语气词。

• **可以改到什么程度：**只整理表达，还是可以重新概括和总结。

• **哪些内容必须保留：**关键原话、数据、案例、结论、任务和负责人。

• **听不清怎么办：**无法确认的内容如何标记，不能自行编造。

• **如何交付：**输出到聊天窗口、飞书文档，还是指定文件夹。

• **如何自检：**是否漏掉重点、是否改变原意、文档结构是否正常、用户是否有权限。

这类 Agent 最重要的是：整理可以更清楚，但不能把原意改掉。

**3.3 办公整理类 Agent**

例如：周报整理、日报汇总、资料归档、报表更新、信息收集等。

Profile 中要重点写清楚：

• **需要哪些字段：**每条信息必须包含什么，哪些字段可以为空。

• **字段如何对应：**输入中的内容要分别填到哪里。

• **格式是什么：**日期、金额、姓名、链接等采用什么统一格式。

• **如何排序和分类：**按时间、部门、项目、优先级还是其他规则整理。

• **重复内容怎么办：**删除、合并还是保留最新版本。

• **信息缺失怎么办：**留空、标记待补充，还是向用户询问。

• **异常内容怎么办：**格式错误、数据冲突或无法识别时如何处理。

• **如何自检：**是否漏项、填错位置、重复录入或修改了原数据。

这类 Agent 最重要的是：内容可以简单，但字段不能放错，数据不能随便改。

3.4 客服与销售类 Agent

例如：售前咨询、客户跟进、社群答疑、销售回复等。

Profile 中要重点写清楚：

• **可以回答什么：**能处理哪些常见问题。

• **不能回答什么：**哪些问题超出权限，不能自行承诺。

• **使用什么语气：**正式、亲切、简洁，还是更有销售感。

• **如何判断用户需求：**用户处于咨询、犹豫、投诉还是准备购买阶段。

• **哪些话不能说：**不能虚假承诺、夸大效果或泄露隐私。

• **什么时候推荐产品：**满足什么条件后才能推荐，不能一上来就推销。

• **什么时候转人工：**投诉、退款、价格特批、合同、隐私或复杂问题必须转人工。

• **如何记录：**需要保存哪些客户信息和沟通结果。

• **如何自检：**是否答非所问、承诺过头、语气不合适或遗漏用户问题。

这类 Agent 最重要的是：先划清回复边界，再考虑如何把话说得更好。

3.5 数据分析与判断类 Agent

例如：用户分析、内容评分、商品筛选、风险审核、线索判断等。

Profile 中要重点写清楚：

• **根据什么判断：**使用哪些数据、条件和判断标准。

• **标准的优先级：**多个条件冲突时，先看哪一条。

• **结果如何分类：**通过、不通过、待确认，还是按照等级评分。

• **评分如何计算：**每项多少分，什么结果对应什么结论。

• **证据如何展示：**结论需要引用哪些原始信息。

• **信息不足怎么办：**不能直接下结论，要标记缺少什么。

• **模糊情况怎么办：**哪些情况必须交给人工判断。

• **如何自检：**判断依据是否充分，结论和证据是否对应。

这类 Agent 最重要的是：不能只给结果，还要说明为什么这样判断。

3.6 流程自动化类 Agent

例如：收集信息后自动整理、生成文件、发送消息、更新表格等。

Profile 中要重点写清楚：

• **什么时候开始执行：**用户发送指令、收到文件，还是定时启动。

• **执行顺序是什么：**每一步先做什么、后做什么。

• **需要调用哪些工具：**每个工具分别负责什么。

• **上一步失败怎么办：**重试、跳过、停止，还是请求人工处理。

• **哪些步骤不能重复：**避免重复发消息、重复建文档或重复写入数据。

• **数据如何传递：**上一步的什么结果，要交给下一步使用。

• **什么情况算完成：**文件创建成功、表格写入成功，还是消息发送成功。

• **如何留下记录：**是否需要记录执行时间、结果和失败原因。

• **什么时候请求人工：**登录失败、权限不足、数据异常或涉及重要操作时及时暂停。

这类 Agent 最重要的是：不仅要写正常流程，还要写清楚失败以后怎么办。

3.7 文件与知识库问答类 Agent

例如：公司知识库助手、课程答疑助手、制度查询助手等。

Profile 中要重点写清楚：

• **可以查哪些资料：**明确知识来源和文件范围。

• **资料冲突怎么办：**优先使用哪个版本，是否查看更新时间。

• **找不到答案怎么办：**直接说没有找到，不能凭经验补全。

• **如何引用来源：**回答时是否需要附上文件名、章节或链接。

• **可以回答到什么程度：**只复述资料，还是可以进一步整理和解释。

• **哪些内容不能回答：**超出资料范围、涉及隐私或权限不足的内容。

• **如何自检：**回答是否真的能在资料中找到依据，是否引用了错误版本。

这类 Agent 最重要的是：只根据已有资料回答，不知道就明确说不知道。

但是一个 Agent 也可能同时属于几种类型的综合体。

例如：

• 会议纪要 Agent，既属于音视频转录类，也属于办公整理类；

• 销售复盘 Agent，既属于资料整理类，也属于数据分析类；

• 自动生成周报并发送到飞书的 Agent，既属于办公整理类，也属于流程自动化类

你可以先找到最接近的一个或两个类型，再检查自己的 Profile 有没有缺少对应规则。

不用现在把所有细节都补完。先把最容易影响结果的内容写清楚：

• 输入是什么；

• 要怎么处理；

• 什么结果算合格；

• 哪些事情不能做；

• 出现问题时怎么办。

这些内容明确后，就可以先让 Agent 跑第一轮真实任务，再根据实际结果继续补充。

### 01. 闭环测试与进阶优化

上一关，你的 Agent 已经完成了基础配置，也已经成功执行过至少一次任务。

接下来，我们来验证它**能不能稳定完成真实工作**。

用更多真实样例 → 跑完整流程 → 保存证据 → 人工验收 → 修正问题 → 进行复测

**1. 准备 3 个测试样例**

先准备 3 个你真实工作中会遇到的输入，尽量不要为了测试临时编一个样例。

测试样例越接近真实工作，越能暴露 Agent 的问题。

| 样例 | 应该是什么 | 作用 |
| --- | --- | --- |
| 样例 1 | 一个最典型、最常见的输入 | 测 Agent 能不能正常完成主流程 |
| 样例 2 | 一个稍微复杂或边缘的输入 | 测 Agent 的兜底和异常处理 |
| 样例 3 | 一个你最关心的真实场景 | 测 Agent 对你的实际工作有没有用 |

准备样例时，建议同时想清楚 3 件事（可以记下来）：

以音视频转录 Agent（小D）为例：

• 样例 1：一期 10 分钟的公开播客（小宇宙链接），测正常主流程

• 样例 2：一个 10-20 分钟的哔哩哔哩公开视频（B 站链接），测视频链接的识别和下载

• 样例 3：一个 2 小时的视频（YouTube 链接），测长视音频分段处理和转录稳定性

如果你的 Agent 不是音视频转录类，也可以按这个逻辑准备。

比如日报 Agent 可以准备：

• 样例 1：一份正常日报素材；

• 样例 2：一份信息不完整的日报素材；

• 样例 3：一份你真实要提交给团队的日报素材。

客服回复 Agent 可以准备：

• 样例 1：一个常见客户问题；

• 样例 2：一个情绪强烈或信息不完整的问题；

• 样例 3：一个你最担心回复出错的真实问题。

**2. 跑一次完整流程并保存证据**

每个测试样例都要跑完整流程，不要只看配置截图。

你要证明的不是“我配置过 Agent”，而是“Agent 真的完成了一次工作”。

按这个顺序跑，每步保存证据：

这一关的作业需要你提交至少一次成功运行的截图：

| 级别 | 包含什么 |
| --- | --- |
| ✅标准 | 至少：输入样例 + 运行过程截图 + 飞书输出结果 更好：有人工验收反馈 + 让它修改的人工复盘 |
| ❌不合格 | 只有配置截图、只有脚本截图，看不出&quot;Agent 真的干活了&quot; |

如果你不确定证据是否够，可以把截图发给 Codex，问：

Markdown

```
我会给你提供几张截图，请帮我检查这次 Agent 测试证据是否完整，

我的截图应该至少包含：
1. 输入样例；
2. 运行过程截图；
3. 输出结果链接或截图；

请你帮我判断：
- 这次测试是否能证明 Agent 真的完成了任务；
- 证据链里缺了哪一步；
- 还需要补什么。
```

**3.**人工验收**

Agent 有输出，不代表输出可用。

验收时可以至少参考这 4 个方面：

**其实最简单的验收标准只有一个：**看完这份结果后，你会不会满意？它有没有真正帮你解决问题？你敢不敢把这项工作放心交给这个 Agent？

如果答案是否定的，也没关系。把你不满意的地方写下来，比如哪里做错了、哪里漏了、哪里不符合预期，这些就是下一轮优化 Agent 最重要的方向。

以【音视频转录 Agent】 为例，可以这样去检查验收：

如果你自己还拿不准这份结果做得怎么样，还有一个简单的方法。

新开一个 AI 对话，把 Agent 的输出结果（复制粘贴或截图都可以）发给 AI，再让它站在专业从业者的角度帮你验收。

⬇️可以直接发送下面这段提示词 （记得替换【】的内容）：

Plain Text

```
你是一名资深的【Agent 所负责工作】从业者。
请不要评价 Agent 本身，而是站在真实使用者的角度，帮我验收下面这份工作成果。

请重点检查：
1. 是否完成了目标；
2. 哪些地方做得好；
3. 哪些地方存在问题或风险；
4. 如果这是你团队同事交付给你的，你会不会直接采用？为什么？
5. 给出具体的修改建议，而不是泛泛评价。

【粘贴图片或者文字】
```

**4.问题整理与 Profile 迭代

**4.1 问题整理**

跑完 3 个样例后，不要急着继续加新功能，先把测试过程中发现的问题整理出来。

**不需要一开始就**整理得很正式， 你可以直接用自然语言按1、2、3……列出你的问题，例如：

1.第一个样例遗漏了部分内容；

2.第二个样例格式不符合要求；

3.第三个样例专有名词识别错误；

4.飞书文档标题不统一。

整理完这些问题后，把这些内容统一发到 Codex 对话框中，让它帮你归类并整理成一份问题清单。

你也可以直接在飞书里的 Agent 对话框中完成这一步，但 Codex 更适合处理较长内容，生成的问题表格通常也会更清晰，方便后续逐项优化。

👇 可以直接发送下面这段提示词，（记得替换【】的内容）：

Plain Text

```
下面是我测试 Agent 时记录的问题。

【粘贴你的问题】

请帮我整理成一张表格，并按照&quot;问题现象、可能原因、优化建议、优先级（高/中/低）&quot;进行归类。

如果发现多个问题本质相同，请帮我合并；如果有些问题应该先解决，也请说明原因。
```

整理完成后，你会得到一份清晰的优化清单，例如：

**4.2 Profile 优化**

接下来就可以开始和 Agent 一起优化，你只需要把发现的问题，用自然语言告诉 Agent，让它判断问题可能出在哪里，并把需要修改的内容整理成清晰、可执行的规则。

你的任务是检查这些规则是否符合真实工作要求，确认后再让 Agent 更新 Profile。

为了方便验证，建议每次先解决一个最重要的问题。

大致流程如下：

1.  把问题现象和你的预期告诉 AI；

1.  让 AI 找到 Profile 中需要补充或修改的位置；

1.  让 AI 将你的要求改写成可执行的规则；

1.  你检查并确认修改内容；

1.  让 AI 更新 Profile；

1.  使用同一个样例重新测试，确认问题是否解决。

你可以直接这样告诉 Agent ：

Plain Text

```
刚才测试时发现了一个问题：

【描述出现了什么问题】

我希望正确结果是：

【描述你期待的结果】

请你：
1. 判断这个问题可能是 Profile 中哪条规则不清楚或缺失；
2. 将我的要求整理成明确、可执行的规则；
3. 告诉我准备修改或补充到 Profile 的哪个位置；
4. 先把修改内容发给我确认，不要直接更新；
5. 我确认后，再帮我更新 Profile。
```

还是拿我们的默认案例举例，你发现【音视频转录助手】小D 经常把“生财有术”识别成“升财有数”，只需要告诉 Agent ：

Plain Text

```
刚才测试时，“生财有术”被识别成了“升财有数”。

正确结果应该是“生财有术”。

请判断 Profile 中需要补充什么规则，把它整理成可执行的写法，并先发给我确认。
```

Agent 会将它整理为：

Plain Text

```
MUST 在清洗阶段检查并修正常见的 ASR 错词。

已知高频错误包括：
- “升财有数”必须修正为“生财有术”；
- “一仁”必须修正为“亦仁”；
- “飞输”必须修正为“飞书”。

无法确认的专有名词 MUST 标记为“[待确认]”，MUST NOT 自行猜测。
```

又或者，你发现 Agent 每次输出的格式都不一样，也可以直接告诉 AI：

“我希望以后固定按照下面的结构输出，不要每次都变。”

AI 可能会帮你整理成这样的规则：

Plain Text

```
MUST 按以下固定结构输出：
1. 转录稿链接
2. 内容摘要
3. 关键结论
4. 行动项
5. 待确认问题

MUST NOT 自行新增、删除或修改一级标题。
```

你不需要自己编写这些规则，只需要确认 AI 整理出来的规则是否符合你的真实需求。

确认无误后，再让 AI 更新到 Profile，并使用同一个样例重新测试。

再次提示：不要一次修改很多规则。

每次只解决一个最重要的问题，用同一个样例验证确实修好了，再继续优化下一个。这样更容易判断是哪条规则真正起了作用，也能避免多处修改互相影响。

5. 进阶优化：让 Agent 更稳定地进入真实工作流

完成前面的测试和简单优化后，你的 Agent 已经"能用了"。

但"能用"和"好用"之间还有距离。

一个真正能进入日常工作流的 Agent，不只是跑通一两次任务，还要做到：

• 结果越来越稳定；

• 出错时能被发现；

• 重要动作不会误执行；

• 能在固定时间或固定条件下自动运行；

• 后续出问题时，能继续迭代和回滚。

所以，你还可以从下面两个方向继续优化。

5.1. 让 Agent 的结果越来越正确

Agent 最开始跑出来的结果很难尽善尽美，甚至可能达不到你心目中的最佳标准。

核心做法是**迭代 Profile**——每次发现输出有问题，就和 Agent 进行沟通，迭代 Profile 的规则。

你可以按照这五点来做 ：

1.  **记录每次"输出不对"的具体表现**

比如：漏掉了关键案例、标题太模糊、格式没有按要求来、输出顺序不稳定。

1.  找到 Profile 里对应的那条规则

看看这个问题是因为规则没写、写得太模糊，还是写了但 Agent 没有稳定遵守。

1.  **把规则改得更具体、可验证**

比如"标题要具体" → "标题 MUST 包含真实内容中的关键词，MUST NOT 使用'其他有效观点'这类模糊标题"）

1.  **用同一个输入再跑一次**

看这个问题是否修好了

1.  **每次只改一个问题**

不要一次改太多规则。确认一个问题修好后，再处理下一个。

以【音视频转录 Agent 】为例：

如果你发现转录稿经常把“生财有术”识别成“升财有数”，就可以在 Profile 的质量标准里加一条：

MUST 在清洗阶段修正常见 ASR 错词。已知高频错误包括：生财有术（而不是“升财有数”）、亦仁（不是“一仁”）。

如果你发现它经常漏掉会议里的行动项，可以加一条：

MUST 单独提取会议中出现的行动项，并标明负责人、事项、截止时间。如果原文没有明确负责人或截止时间，必须标注“未明确”。

如果你发现它输出格式经常变，可以加一条：

MUST 按固定结构输出：一、会议摘要；二、关键结论；三、行动项；四、待确认问题。不得自行新增或删除一级标题。

Profile 不是一次写完的，而是在真实使用中慢慢养出来的。

每一次错误，都是一次让 Agent 变得更可靠的机会。

5.2 让 Agent 长期可靠地工作

完成基础配置后，你的 Agent 已经可以通过手动发送命令或消息来执行任务。

这一步说明：Agent 已经能安装你的指示，替代你的一部分工作了。

但如果你希望它真的进入日常工作流，只能手动命令它还不够。你还需要根据自己的业务场景，进一步配置它什么时候启动、从哪里取资料、把结果发到哪里、遇到问题怎么处理、哪些动作必须先问人。

这些配置不一定每个 Agent 都要做，但它们会决定你的 Agent 是一个“临时帮手”，还是一个能长期稳定工作的“数字员工”。

你可以从下面几个方向检查是否需要进阶配置：

**你不需要一次配完所有进阶能力**

如果你一上来就想给你的 Agent 配上所有能力：自动触发、自动读取、自动判断、自动发布、自动复盘，全都要。

这样反而容易出问题。

更稳的做法是：先让 Agent 跑通一条最小工作流，再根据真实使用中的卡点，一项一项补配置。

你可以考虑按这个顺序来：

1.  **先稳定输入**明确 Agent 每次从哪里拿资料。比如飞书文档、多维表格、固定文件夹，还是你手动发给它。

1.  **再稳定输出**明确结果写到哪里。比如飞书群、飞书文档、多维表格，还是本地文件。

1.  **再加人工确认**如果 Agent 会对外发送、修改数据、触达客户，建议先加一道“确认后再执行”。

1.  **再加异常提醒和运行日志**

保证它出错时你能知道，后续也能查到问题发生在哪一步。

1.  **最后考虑自动触发**

等手动运行稳定后，再配置定时任务或事件触发，让 Agent 自动进入工作流。

怎么判断自己现在要不要做进阶配置？

你可以用下面几个问题判断：

• 这个任务是不是会重复发生？

• 输入资料是不是来自固定位置？

• 输出结果是不是需要沉淀到固定位置？

• 这个任务失败时，我需不需要第一时间知道？

• Agent 有没有可能误发、误删、误改？

• 后续我是否需要查看它以前做过什么？

• 这个流程以后是否可能交给别人一起用？

如果你有 2 个以上回答“是”，就可以考虑补一项进阶配置。

如果你只是刚刚跑通第一个 Agent，可以先不急。先手动运行 2-3 次，在实际体验中发现需求。

比如：

• 总是忘记运行，就先加定时触发；

• 每次复制资料很麻烦，就先固定输入来源；

• 结果散落在对话里不好找，就先固定输出位置；

• 担心它误发给客户，就先加人工确认；

• 经常不知道哪里失败，就先加运行日志和异常提醒。

先让 Agent 稳定帮你完成一件事，再慢慢把它养成一个更可靠的数字员工。

这样一来，这个 Agent 就不只是“会写日报”，而是进入了一个可追踪、可检查、可长期运行的工作流。

Markdown

```
请帮我给当前这个 【你的Agent名字】 增加一个定时运行配置。

我的目标是：让这个 Agent 在固定时间自动执行一次任务，而不是每次都由我手动触发。

请你先检查当前 Agent 的配置，包括：
1. Agent 名称和 Profile 是否存在；
2. 当前任务的启动方式；
3. 是否已经接入飞书；
4. 是否有固定输入来源；
5. 是否有固定输出位置。

然后请你一步一步带我完成定时配置。

如果当前条件不足，请先告诉我缺什么，并给出最小补齐方案。
如果需要我提供信息，请一次只问我 1-3 个问题。
如果需要飞书授权、Hermes 配置或本地命令执行，请直接告诉我下一步要做什么。

我希望最终实现：
- 每天上午 9:00 自动运行一次；
- 运行后把结果发送到指定飞书群；
- 如果运行失败，要在 Codex 对话里说明失败原因；
- 如果能配置运行日志，请帮我记录每次运行时间、执行结果和输出链接。

注意：
不要直接覆盖我现有的 Agent 配置。
在修改前，请先说明你准备改哪些文件或配置项。
修改完成后，请帮我做一次手动测试，确认 Agent 仍然可以正常运行。
```

Codex 通常会先检查当前 Agent 的状态，然后问你几个问题。

你可能会看到类似问题：

• 这个 Agent 现在叫什么名字？

• 你希望每天几点运行？

• 结果要发到哪个飞书群？

• 输入资料来自哪里？

• 失败后要通知谁？

### 04. 本关小结

**跑闭环 = 用真实样例证明 Agent 不是只能演示**一次，而是能被验收、能被修正、能被交付。

前面五关，你已经完成了从 Demo 体感到正式 Agent 的搭建：定岗位、拆流程、写 Profile、接工具、接飞书。到了关卡 6，重点不再是继续增加功能，而是用真实输入反复跑一遍，把它从“我自己觉得能用”推进到“别人也能看懂、能验收、能复用”。

核心四个动作：

1.  **准备测试样例：**至少准备 3 个真实或接近真实的输入，覆盖常规场景、边缘场景和你最关心的业务场景。

1.  **保留运行证据：**记录输入、执行过程、输出结果和人工验收结论，让别人能看出 Agent 最近真的干过活。

1.  **校对并优化一轮：**把测试中发现的问题按影响排序，回到 Profile、工具链或流程规则里逐个修正，并用同一个样例复测。

1.  **整理交付材料：**准备公开链接、成功运行截图、使用说明书和测试记录，让这个 Agent 从“能跑”变成“能交”。

到这里，你已经完成了必修篇的全部内容，拥有了至少一个能够独立完成任务、跑闭环的 Agent。它有岗位、有流程、有大脑、有工具，也有可验证的交付材料。。

接下来的选修关卡，会在这个基础上继续往前走：不再只看一个 Agent 自己怎么工作，而是把它放回真实业务中，看看它的输入从哪里来、结果要交给谁，以及是否值得和其他人、工具或 Agent 连接起来。

选修篇的内容会比前面更开放、更难一些。

**选修篇更像是一份进阶指南。**不需要一次全部完成，先完成与你当前 Agent 最相关的内容，等未来需求发生变化，再回来继续探索也完全没有问题。

**1.Agent 提炼出 Skill 的教程

一个 Agent 往往会完成很多工作，但并不是每一步都需要写成 Agent。

有些能力本身就足够独立、足够通用，更适合提炼成一个可以反复调用的 Skill。

你也可以从这些方向里考虑：

**例如，在【音视频转录助手 Agent】里，就可以抽**出一个独立的【转录稿清洗 Skill】。

这个Agent 的完整工作流大概是这样的：

Plain Text

```
接收音视频链接；
下载音视频；
提取音频；
调用转录工具生成文字稿；
清洗转录稿里的错词、口癖和断句；
整理摘要、行动项和待确认问题；
写入飞书文档；
把结果链接发到飞书群。
```

这个 Agent 本身很完整，能帮你做事，但它不一定方便直接分享给别人。

因为它可能依赖你的：飞书空间、本地工具、账号权限、文件路径、业务资料、固定输出位置······

别人拿到整个 Agent，不一定能直接跑起来。

但里面有一个能力很适合抽出来：

清洗转录稿，并按照固定结构整理成摘要、行动项和待确认问题。

这个能力不依赖你的账号，也不依赖你的飞书空间。只要别人有一段转录稿，就可以使用。

所以，它就适合沉淀成 Skill。

你可以按 3 步来从 Agent 中抽出 Skill ：

1.  **回看你的 Agent 工作流**找出里面重复出现、最有价值、别人也可能需要的一小段能力。

1.  **把它从完整流程里拆出来**不要上传整个 Agent。只保留一个清晰的小能力：输入是什么、处理什么、输出什么。

1.  **写成别人能复用的 Skill**说明它适合谁、解决什么问题、怎么使用、使用前后有什么效果。

当然，接下来不需要你自己硬想“我的 Agent 里哪个节点适合抽成 Skill”。

更简单的方式是：把你的 Agent 工作流交给 AI，让它帮你拆节点、判断价值、筛选出最适合上传 Skill Hub 的一个能力。

1.1 从完整 Agent 里找到可复用节点

⬇️把下面这段 Prompt 复制给 Codex：

Markdown

```
我刚刚完成了一个 Agent，请你帮我从这个 Agent 工作流里，找出可以沉淀成 Skill 的能力。

请你按下面步骤分析：

1. 先把我的 Agent 工作流拆成多个节点。
   每个节点请说明：
   - 这个节点在做什么；
   - 输入是什么；
   - 输出是什么；
   - 是否依赖我的本地文件、账号权限、飞书空间、私有数据或特定工具。

2. 判断每个节点是否适合抽成 Skill。
   请按下面标准判断：
   - 是否足够通用，别人也可能需要；
   - 是否可以脱离我的完整 Agent 单独使用；
   - 是否有清晰的输入和输出；
   - 是否不强依赖我的私人数据和本地环境；
   - 是否能解决一个具体问题。

3. 给每个候选节点打分，满分 5 分。
   评分维度包括：
   - 通用性；
   - 复用价值；
   - 使用门槛；
   - 展示价值；
   - 是否适合上传 Skill Hub。

4. 最后请推荐最适合抽成 Skill 的 1-3 个节点，并说明推荐理由。

注意：
不要推荐需要我提供账号、密钥、私人资料、本地路径才能运行的能力。
优先推荐别人复制后就能理解、能使用、能改造成自己场景的能力。
```

选中一个节点，我们进行下一步。


# 选修篇：从单个 Agent，到协作团队与商业化服务

## 关卡 7：找到上下游，判断是否值得连接

### 00. 本关任务卡

🎯任务目标：从关卡 6 已经验收的 Agent 出发，找到它的上游和下游，判断各环节由谁完成，并决定当前是否有一段关系值得先连接。

🗒️任务描述

• 写清当前 Agent 接收什么、完成什么、交付什么。

• 向前找到输入从哪里产生、怎样进入当前 Agent。

• 向后找到谁会继续使用结果，还要完成什么。

• 分清各环节由人、Agent、工具、固定流程还是业务系统完成。

• 判断这些环节属于各自工作、共用资源、前后交接，还是先判断再分流。

• 有合适关系时，只选择一段进入关卡 8；暂时没有时，写清“本轮暂不连接”的理由。

💡新**手提醒**

从本关开始进入选修篇，是进阶学习的内容，不再设置必须提交的作业。你只需要对照关卡的任务目标和任务描述，跟着步骤完成练习即可。

这一关考察的不是你能连接多少个 Agent，而是能不能作出合适的判断。

自己的业务暂时没有稳定的交接关系，可以如实填写“本轮暂不连接”。不要为了过关，临时虚构一个新的 Agent 或交接关系。你仍然可以使用默认案例继续完成关卡 8。

![](img/9da1650ba3cec625186a5e1d93960497.png)

### 01. 本关重点

前六关，你完成的是一个 Agent 的独立工作闭环。

它已经知道：

• 自己负责什么；

• 收到什么输入；

• 按什么流程工作；

• 可以调用哪些工具；

• 要交付什么结果；

• 遇到什么情况需要停下来问人。

但在日常工作中，一个 Agent 通常只负责其中一段的工作内容。

它的输入从哪里来？完成后，结果交给谁？前后还有哪些人、Agent、工具和业务系统？

关卡 7 要做的，就是把这个 Agent 放回完整工作中，找到它的上游和下游。

可以先用下面这条线帮助理解：

Plain Text

```
输入从哪里产生
→ 通过什么方式进入
→ Agent 完成处理
→ 结果保存在哪里
→ 谁继续使用
→ 哪一步需要人确认
```

这里有两个常用词：

• **上游**：为当前 Agent 提供输入的工作环节；

• **下游**：继续使用当前 Agent 结果的工作环节。

先把工作链看清楚，再决定要不要连接。

![](img/ab1fe44b90a87adab6ec6708f5793d59.png)

### 02. 实操步骤

**1.先看完成结果**

下面以小 D 为例，看看关卡 7 完成后大致会得到什么。

1.  看清一条 Agent 工作链由什么组成

一条完整的 Agent 工作链，不只有 Agent。

输入要先进入系统，任务要被触发；有时还要先判断任务类型，再交给合适的 Agent。

Agent 工作时会调用工具，完成后把结果保存到文档、表格或业务系统，关键结果再交给人检查和确认。

可以从下面七个位置检查：

![](img/1b417240e297d5c16863dcf3b97ec63c.png)

**4.1 人**

人负责授权、确认事实和承担业务责任。

例如：

• 确认纪要是否准确；

• 决定哪些行动正式成立；

• 确认负责人和截止时间；

• 审核金额、客户承诺、正式发布和敏感信息。

**4.2 Agent**

Agent 负责一段相对完整的工作。它需要看懂上下文、作出判断，并交出可以检查的结果。

可以用三个问题帮助判断：

1.  这是不是一段完整工作？

1.  过程中是否需要结合上下文判断？

1.  完成后是否有单独的结果可以检查？

4.3 工具、Skill、MCP 或 API

这些能力帮助 Agent 完成一个明确动作。

例如：

• 下载音视频；

• 转换文件格式；

• 语音识别；

• 读取或创建飞书文档；

• 查询表格或外部数据；

• 发送消息。

工具会被 Agent 调用，但工具本身不一定是 Agent。

**4.4 固定流程**

规则已经说得很清楚，只需要触发、转发、定时执行或更新字段时，可以使用机器人、脚本或工作流。

例如：

• 收到指定格式消息后转发；

• 每天固定时间开始处理；

• 把结果写入固定字段；

• 按规则发送提醒。

**4.5 业务系统或内容来源**

这类环节负责产生、保存或承载内容。

例如：

• 飞书会议；

• 飞书妙记；

• 飞书文档；

• 文件夹；

• 邮箱；

• 多维表格；

• CRM；

• 项目管理系统。

Agent 架构师要做的，不是把每一步都变成 Agent，而是判断每一步最适合由谁完成。

**5.1 各自处理不同工作**

Plain Text


**5.2 共用工具、资料或系统**

两个 Agent 可能使用同一份知识库、同一个飞书空间或同一套工具，但彼此不传递结果。

共用资源，不等于上下游。

**5.3 前后交接**

前一个 Agent 的结果，经常成为后一个 Agent 的输入，而且顺序稳定，就适合建立交接。

Plain Text

```

→ 智能纪要 Agent
```

选择时检查：

1.  这段交接是否经常发生？

1.  前一个 Agent 是否有清楚的交付结果？

1.  后一个 Agent 是否知道怎样检查？

1.  连接后能否减少复制、等待和重复说明？

1.  出现问题时，能否判断退回哪一边？

1.  是否知道哪一步需要人确认？

1.  两个 Agent 是否都可以分别运行？

**5.4 先判断，再分流**

同一个入口收到不同类型的任务时，可以先判断任务类型，再交给合适的 Agent。

Plain Text

```

→ 判断任务类型
├─ 类型 A → Agent A
└─ 类型 B → Agent B
```

## 关卡 8：连接两个 Agent，在飞书群跑通一次可追溯的自动接力

### 00. 本关任务卡

**🎯任务目标**

让两个 Agent 对应的飞书机器人在同一个群里完成一次真实的自动接力，并留下交付、接收、处理和检查记录。出现问题时，你能找到卡住的环节，知道应该退回、暂停还是交给人处理。

**🗒️任务描述**

• 使用关卡 7 选中的一段固定接力；暂时没有合适关系时，跟做“音视频转录 Agent → 智能纪要 Agent”。

• 为前后两个 Agent 分别准备一个飞书应用机器人和一个 Hermes Profile，并把两个机器人加入同一个测试群。

• 先分别测试两个机器人，再由你手动@下游机器人，确认材料、权限和处理规则都没有问题。

• 人工接力通过后，再配置上游机器人发送完整交付，并真正@下游机器人接手。

• 下游 Agent 先检查收到的材料，检查通过后再继续处理；检查不通过时，写清原因并退回。

• 每一步都保留任务编号、消息、结果链接、待确认事项和当前状态。

• 第一次自动接力结束后，用 Codex 检查权限、交付格式、触发结果和异常处理方式。

![](img/46e07fa9fb748c837acc5e0f5958c3d4.png)

**💡新手提醒**

第一次运行不要直接追求“全自动”。先确认下面几件事：

• 两个机器人单独工作都没有问题；

• 上游交付的结果，下游真的能打开；

• 人工转交时，下游能正确接手；

• 自动转交使用的是真正的飞书@，不是消息里的普通文字；

• 自动触发失败时，流程会停止，不会反复重试。

### 01. 本关重点

关卡 7 已经帮你判断：

哪两个 Agent 之间存在稳定的前后关系？哪一段最值得先连接？

关卡 8 要做的是：

让这两个 Agent 在飞书群里先完成人工接力测试，再跑通一次自动接力，并留下可以回看的处理过程。

你可以把这条接力理解成两道连续工序：

Plain Text

```
人先启动上游 Agent
→ 上游 Agent 完成工作并交付结果
→ 上游机器人真正 @下游机器人
→ 下游 Agent 检查并接手
→ 完成下一段工作
→ 输出最终结果
```

每个环节都要留下三样东西：

1.  **收到什么**

1.  **做了什么**

1.  **交付什么**

最终结果出现问题时，沿着记录往前查看：

Plain Text

```
最终结果
→ 下游 Agent 使用了什么材料
→ 下游接收时是否发现问题
→ 上游 Agent 当时交付了什么
→ 原始材料是否完整
```

这样就能判断问题出在原始材料、上游整理、交接过程、下游处理，还是需要人决定的业务事项。

1.为什么使用同一个飞书群

同一个飞书群可以同时承担三个作用：

• **工作现场**：两个 Agent 在同一处接收任务、交付结果；

• **接力入口**：上一位完成后，通过@通知下一位接手；

• **过程记录**：每一步的消息、链接、检查结论都能回看。

![](img/f401d9a4715f5216f793db1acbffe9e3.png)

默认案例的目标路径如下：

Plain Text

```
会议材料进入飞书群
→ 人工 @音视频转录 Agent
→ 音视频转录 Agent 完成转录和整理并发布飞书文档
→ 音视频转录 Agent 发送完整交付消息
→ 音视频转录 Agent 真正 @智能纪要助手
→ 智能纪要 Agent 检查材料
→ 检查通过后生成纪要
→ 普通结果归档
→ 需要承担业务责任时 @确认人
```

2.一次完整接力包含哪些动作

一次完整接力至少包含：

1.  两个机器人分别通过人工@测试；

1.  上游 Agent 接收真实材料并完成处理；

1.  人工把上游结果转交给下游，确认材料和权限可用；

1.  上游 Agent 发出完整交付消息，并真正@下游机器人；

1.  下游 Agent 先做接收检查；

1.  检查通过后完成下游处理；

1.  留下最终结果和检查结论；

1.  根据实际情况完成、退回、暂停或交给人。

1.  Codex 在这一关负责什么

Codex 主要用于搭建和调试：

• 帮你创建或调整两个飞书机器人和 Hermes Profile；

• 检查两个 Agent 的职责是否清楚；

• 检查机器人接收其他机器人消息所需的权限和配置；

• 帮你整理交付消息的固定格式；

• 帮你生成真正的飞书@，而不是普通文字；

• 帮你检查第一次运行留下的证据；

• 帮你判断问题发生在哪个环节；

• 缺少信息时是否标为待确认；

• 是否增加了材料中没有的事实；

• 是否保留了需要人决定的事项。

检查完成后，在接力记录中写明：

Plain Text

```
结果检查：通过 / 退回下游 / 等待人工处理
```

1.  出现问题时，退回对应环节

最终结果出现问题时，先查清问题在哪里，再决定退回谁。

**5.1 原始材料有问题**

例如：

• 材料缺失；

• 来源不清楚；

• 没有获得访问权限；

• 材料版本无法确认。

处理方式：

Plain Text

```
暂停
→ 找材料提供人补充
→ 补充完成后重新启动上游 Agent
```

**5.2 上游交付有问题**

例如：

• 结果无法打开；

• 关键内容缺失；

• 待确认内容没有标记；

• 整理稿出现明显事实错误。

处理方式：

Plain Text

```
退回上游 Agent
→ 写清缺少什么或哪里有误
→ 上游修改并重新交付
```

下游 Agent 不要悄悄修改上游事实。这样会让问题来源变得难以查找。

**5.3 接力过程有问题**

例如：

• @没有真正触发下游 Agent；

• 同一个任务被重复触发；

• 下游 Agent 收到了错误版本；

• 群消息和结果链接权限异常；

• 飞书接力记录无法更新。

处理方式：

Plain Text

```
暂停当前任务
→ 保留已经完成的结果
→ 记录问题发生的位置
→ 交给维护人或回到 Codex 排查
```

**5.4 下游处理有问题**

例如：

• 漏掉必要内容；

• 把一般讨论写成明确结论；

• 增加了材料中没有的事实；

• 应当待确认的内容被直接确定；

• 使用了错误的上游材料。

处理方式：

Plain Text

```
退回下游 Agent
→ 写清需要修改的内容
→ 使用原交付材料重新处理
```

**5.5 需要承担业务责任**

例如：

• 把候选行动确定为正式任务；

• 确认负责人和截止时间；

• 金额或报价正式生效；

• 对客户作出承诺；

• 正式对外发布；

• 授予敏感权限；

• 事实存在争议或证据不足。

处理方式：

Plain Text

```
暂停自动接力
→ @业务确认人
→ 记录确认人和确认结果
→ 再决定是否进入下一步
```

**5.6 连续失败时停止**

同一个环节连续失败时，不要让两个 Agent 反复互相点名。

停止继续触发，保留已经完成的材料，并记录：

• 失败发生在哪一步；

• 已经尝试了几次；

• 当前需要谁处理；

• 恢复后从哪一步继续。

1.  写出下一次准备怎样运行

完成第一次自动接力后，先根据真实结果写出下一次准备怎样运行。一次成功只能证明这条路径跑得通，还不能证明它已经稳定。

6.1 默认案例的下一次运行路径

```
→ 人工 @音视频转录 Agent

```

6.2 什么时候可以作为日常方式

第一次自动接力通过后，继续完成几次稳定性测试。满足下面条件，再把它作为日常方式：

• 上游 Agent 连续几次都能输出相同结构的交付消息；

• 下游 Agent 能稳定读取上游结果；

• 下游 Agent 能明确回复接收通过或退回；

• 没有出现重复点名和循环触发；

• 权限和结果链接保持稳定；

• 异常情况能够暂停并通知人。

没有完成稳定性测试前，在接力记录中写“自动接力首次验证通过”，不要写“已经稳定运行”。

• 上游机器人真正@下游机器人后没有触发；

• 同一任务被重复触发；

• 交付格式变化，导致下游无法读取；

• 无法判断问题发生在哪个环节；

• 需要修改 Hermes Profile；

• 需要增加新的检查规则；

• 接力环节增加，准备使用脚本或工作流工具管理。

**6.4 人什么时候介入**

下面这些情况需要人确认：

• 规则无法判断；

• 事实存在争议；

• 需要确定正式任务、负责人或截止时间；

• 涉及金额、报价或客户承诺；

• 准备正式发布；

• 涉及敏感数据或权限；

• 同一步连续失败；

• Agent 的处理结果可能带来实际业务责任。

## 关卡 9：Agent 企业服务变现（选修）

### 00. 本关任务卡

**🎯任务目标：**把你已经跑通的 Agent，包装成一份边界清楚、能够试点的企业 AI 服务方案。

**🗒️任务描述：**

• 从你已经跑通的 Agent 出发，选择一个明确的企业AI智能体业务场景。

• 不从工具功能讲起，而是先写清客户实际痛点、核心需求。

• 把 AI智能体项目的落地交付方案、客户流量来源、风险规避措施全部摸清楚。

你做出的这 1 页企业AI智能体服务落地方案，要尝试回答如下问题：

• 目前接触的客户，有哪些实际痛点？

先卖一个可验收的小试点，不要一上来承诺全公司智能化。

请先把这句话刻在脑子里：

**企业真正愿意付钱购买的，从来不是一个名字叫“AI Agent”的技术产**品，而是一个过去做不快、做不好、成本很高或者根本跑不通的业务问题，被重新跑通了。

### 01. 客户痛点与变现路径

先知道怎么变现，你才能够知道该往哪个方向努力。

1.  AI 智能体企业咨询

痛点场景：老板想要利用AI智能体做事情，但不知从何入手

这里主要有两种具体交付方式：

第一种：线上咨询

重点在于聆听老板诉求，并给出针对性的解决方案，最好是说老板关心的几个核心点，比如：

💡第一，当前的业务经过盘点之后，是否有必要利用AI智能体改善？

第二，如果要做AI智能体，直接使用成熟工具（用哪个），还是自己开发？

第三，同行是怎么做的？花了多少成本？用的什么方式？最终效果如何？

第二种：线下咨询

重点和线上咨询差不多，但线下的好处是信息密度更大，对接资源可以更多，要想通过介绍完核心点之后让老板认可你，并之后有可能采购你们公司的AI智能体服务，需要准备如下内容：

💡第一，客户所在行业经过AI智能体赋能前后的显著对比，是效率提升了，还是成本降低了，还是赚钱更多了，还是资源拓展了？

第二，客户既然约了线下，大概也了解了市场上的通用工具，那么要准备几个标准化工具实操，比如workbuddy、codex、企业垂直赛道智能体，不要一个，是因为要给老板提供选择，但切记不要多，否则和没有提供一样。

第三，同行的案例，包括投入成本、建设周期、最终成效。以及你们公司成套的解决方案，包括要给客户如何落地。

注意以上所有内容要放到PPT里面，最次也要有文档，如果是有实操的内容，最好有工具简单演示或者视频，

咱们的目标是：让客户知道咱们专业，同时要留下钩子，比如：

💡【老板，您看了这么多内容，我觉得可以做一次全公司的企业培训，毕竟将来需要高管和底下的员工知道AI智能体，并熟练运用，才好推进】，瞄准的是老板不干活，是底下的人干活这一需求，先推AI企业培训服务。

【老板，无论是采购成熟工具，还是咱们自己开发，都得提前测算成本，预计最终效果，我觉得可以进行一次深度的售前交流，或者轻咨询，详细把所有内容说一遍，好方便帮您确定用什么方案】，瞄准的是老板既想要知道怎么做，但是又不想花太多钱的需求，可以同时推AI企业咨询服务和轻量化产品。

【老板，您的XX同行目前已经布局AI智能体了，他们分别在XX场景下有了成效，我建议咱们公司也尽快先找1-2个场景测试一下，评估下是否值得投入资源继续放大】，瞄准的是老板确实想做，又怕钱打水漂，可以先合作1-2个场景，目的是推一个小合同，然后再接大单。

1.  AI 智能体企业培训

痛点场景：员工不知道如何配置+应用AI智能体，实操有卡点

这里主要有三种具体交付变现方式：

💡

1、讲标准课：也就是重点在于给企业输入，适合于还没怎么接触过AI智能体的小白企业，早期AI探索的企业，刚想要转型部分工作用AI智能体替代的企业

2、讲标准课+部分定制：也就是既要扫盲，也要结合企业自身的产品和服务进行培训。重点在于后者，因为员工只关心和自己的工作有什么关系

3、基本都是定制：也就是必须结合企业的实际业务流程进行培训，老板已经有一定认知，不需要入门培训，而是需要如何培训完之后能立刻见到效果，比如效率提升（同时能做更多的项目，能引流更多的客户），项目收入提高（直接体现在员工业绩上）。

那么对于想要做这块服务的人，有两方面的要求：

💡首先得有课程打磨能力。并且经过多次AI智能体线上或者线下的企业培训，随时可以讲标准课。

其次要懂真实业务需求。企业的产品和业务必须熟悉，特别是某个垂直领域，比如电商、教培、工业自动化等，这样之后可以构建壁垒，做的是“AI智能体垂直领域”培训或者产品定制开发。

1.  AI 智能体联合研发 / 项目外包

痛点场景：老板已经有了想法，也明确了建设方案，但是缺少牵头的人

这里确实也要分几种情况，都有可能成单：

💡第一种，客户方案明确，但是预算不够，因此只能做部分场景，要想做的多一点，可能会和其他公司联合研发，产出的成果双方都能用。

第二种，客户方案明确，预算也够，但是自己的人忙不过来，因此可以直接把项目外包，但不是纯外包做，而是带着公司的骨干一起，项目做完了，骨干也培养出来了，之后才有更多AI智能体的事情可以做。

第三种，客户方案明确，但是需求较散，得通过多种方式满足，比如插件和skill得自己重新开发，工具可能使用成熟大平台的，场景和数据得对接现有系统。因此要通过综合性的落地方案才能搞定。

### 02. 场景实操与需求拆解

梳理B端企业的需求，也可以借助AI智能体，再不济用AI大模型也行

1.  场景1：针对老板想要利用AI智能体做事情，但不知从何入手这一痛点

将下面的【企业AI智能体业务诊断顾问】提示词给到 AI ，去和 AI 对话。

**你将得到一份企业 AI 智能体建设**方案，包括优先场景、实施路径和试点建议。

Plain Text

```
你是一名具有企业管理咨询、业务流程梳理、AI智能体规划和数字化转型经验的高级顾问。现在需要帮助一家企业判断应该从哪些业务场景开始建设AI智能体。

请不要直接推荐工具，也不要一开始就设计复杂系统。请先通过提问方式完成需求诊断，每次只提出3—5个最关键的问题，并根据我的回答继续追问，直到能够形成初步方案。

你需要重点了解以下内容：

1、企业所在行业、主营产品、客户类型和团队规模；
2、老板最希望改善的经营目标，是降本、增效、增收、获客、提升服务还是降低风险；
3、当前最耗时间、最依赖人工、最容易出错的业务流程；
4、每项工作的发生频率、参与人数、单次耗时和当前成本；
5、输入资料来自哪里，包括文档、表格、聊天记录、CRM、ERP或其他系统；
6、数据是否完整、是否涉及客户隐私、商业秘密或敏感信息；
7、出错会造成什么损失，是否可以设置人工审核；
8、企业目前使用了哪些AI工具、软件系统和自动化工具；
9、客户希望在多长时间内看到效果，大概可接受的预算范围；
10、谁负责推动项目，哪些部门需要参与。

完成诊断后，请输出：

1、企业当前AI应用成熟度判断；
2、最值得优先验证的5个AI智能体场景；
3、每个场景的业务痛点、输入、处理流程、输出和人工审核节点；
4、按照价值、难度、数据基础和风险进行评分；
5、推荐的第一期试点场景；
6、适合采用成熟工具、低代码平台还是定制开发；
7、预计实施周期、人员投入和预算区间；
8、试点验收指标；
9、客户需要提前准备的资料；
10、本期不建议开展的高风险场景。

要求方案务实、具体，避免“提升效率、赋能业务”等空泛表述。每个建议都要说明为什么值得做、怎样落地、怎样验证。
```

这里要重点提醒💡：提示词只是帮助我们快速建立框架，不能代替真实的客户访谈。

客户在第一次沟通时，说出的内容通常不是完整需求。

例如，客户说：“我们想做一个商机分析系统，自动分析微信聊天里的客户需求。”这句话不能直接作为开发需求。还要继续拆解：

💡

1、客户是谁？是否有统一客户档案？

2、聊天记录通过什么方式取得？是否获得授权？

3、企业销售什么产品？产品资料是否完整？

4、哪些表达算高意向信号？

5、销售下一步应该采取什么动作？

6、售前和售后分别有哪些SOP？

7、AI只是提供建议，还是允许自动发送消息？

8、哪些动作必须经过销售确认？

拆解之后，第一版项目可能变成：

💡

1、每天读取合规取得的客户聊天记录，结合CRM客户档案、产品知识库和销售SOP，输出高意向客户清单、判断依据、客户需求摘要和建议跟进动作，由销售人员确认后再联系客户。

2、到这一步，输入、知识库、智能体动作、输出结果和人工节点才基本清楚，才能估算周期、成本和验收方式。

3、需要特别注意，如果客户要求绕过平台规则、控制未经授权的个人账号、批量自动发送营销信息或者处理未经授权的数据，应该明确拒绝，或者调整为符合平台和法律要求的方案。

能实现，不等于适合交付。

1.  场景2：针对员工不知道如何配置+应用AI智能体，实操有卡点的这一痛点

将下面的【企业AI智能体培训需求设计师】提示词给到 AI ，去和 AI 对话。

Plain Text

```
你是一名企业AI智能体培训顾问，需要为一家企业设计一套能够真正落地的培训方案。
请先向我了解以下信息：
1、参训人员所在部门、岗位、人数和AI基础；
2、企业的主营业务、产品和主要客户；
3、员工每天或每周最常做的重复工作；
4、当前最耗时间、最容易出错和最依赖熟练员工的任务；
5、企业现有的文档、表格、SOP、知识库和业务系统；
6、培训后老板希望看到什么具体结果；
7、哪些资料可以用于现场演示，哪些资料属于敏感信息；
8、培训时间、培训形式和是否安排课后陪跑。

根据我的回答，设计一套企业AI智能体实战培训方案，输出：
1、培训对象分层；
2、培训目标；
3、课程模块和时间安排；
4、3—5个企业真实业务案例；
5、每个案例的输入资料、操作步骤、提示词、输出结果和人工核验方式；
6、课前需要客户准备的资料；
7、培训现场需要使用的工具；
8、培训后交付的提示词库、操作手册、案例库和岗位场景地图；
9、培训效果评估方式；
10、适合进一步开发成智能体的业务场景。

要求培训内容至少有50%与企业真实工作相关，不要只介绍工具功能。案例必须能够由员工在培训后重复使用。
```

以本章节共创老师**@飞掌柜**公司为例：客户痛点是销售每天拜访客户后，需要整理客户需求、竞争情况、预算、决策人和下一步计划，但很多销售记录不完整，管理人员也无法快速掌握项目进展。

培训时不要只演示“帮我整理一份会议纪要”，而应该设计完整流程。

💡第一步，让员工输入客户基本信息、拜访录音转写内容和本次拜访目标。

第二步，让AI提取客户当前问题、采购意向、预算线索、决策链、竞争对手和风险。

第三步，让AI按照企业CRM字段生成标准记录。

第四步，让AI根据销售SOP生成下一步行动建议。

第五步，由销售人工确认事实是否准确，再录入公司CRM系统。

这个案例的价值不是“纪要写得更漂亮”，而是帮助企业形成统一的客户信息记录标准，提高销售管理质量。

培训完成后，可以进一步升级为系统项目：自动读取合规取得的会议记录，生成结构化客户信息，并推送给销售确认。

1.  场景3：针对老板已经有了想法，也明确了建设方案，但是缺少牵头的人这一痛点

将下面的【企业AI智能体项目交付规划师】提示词给到 AI ，去和 AI 对话。

Plain Text

```
你是一名企业AI智能体项目总监，需要帮助客户把已经明确的建设想法转化为可以实施、报价、排期和验收的项目方案。

请先检查客户提供的方案是否完整，并重点追问：
1、项目要解决的具体业务问题；
2、项目涉及的部门、岗位和用户数量；
3、当前业务流程和目标流程；
4、每个环节的输入、处理、输出和责任人；
5、需要接入的知识库、文档、数据库和业务系统；
6、是否需要插件、Skill、API、自动化流程或专属应用；
7、数据权限、数据安全、部署方式和审计要求；
8、哪些结果允许自动执行，哪些必须人工审批；
9、客户能够投入的业务人员、技术人员和项目负责人；
10、预算、周期、验收标准和后续维护要求。

完成分析后，请输出：
1、项目目标和范围；
2、现状流程与目标流程；
3、智能体总体架构；
4、Agent、知识库、自动化、人工审核和系统接口的分工；
5、项目工作分解结构；
6、双方人员和职责；
7、项目里程碑；
8、数据和知识库建设方案；
9、测试与验收指标；
10、风险清单和应对措施；
11、本期交付范围和明确不交付范围；
12、需求变更机制；
13、预算测算逻辑；
14、上线后的培训、运营和维护方案。

要求方案能够直接用于项目立项、合同附件和项目启动会，所有任务要有责任人、输入、输出和完成标准。
```

建议启动前，和项目组同时梳理清楚四张表，当然，如果能和客户确认好，那更佳！

💡

1、业务场景表。

记录场景名称、使用部门、当前问题、发生频率、当前耗时、输入资料、输出结果、风险等级和预期价值。

2、系统接口表。

记录系统名称、数据内容、接口方式、负责人、权限要求、测试环境和预计开放时间。

3、知识库资料表。

记录资料名称、来源部门、格式、数量、更新时间、保密级别、责任人和是否可以用于模型。

4、项目责任表。

明确客户项目负责人、业务负责人、技术负责人、数据负责人、验收负责人，以及服务商对应人员。

没有这四张表，项目很容易在中途因为资料不到位、接口没有开放、需求反复变化而延期。

### 03. 设计交付与知识库构建

不同规模的企业，交付方式有差异，这边给通用和定向两类方案。

1.  通用版交付方案

多数企业AI智能体项目，都可以尝试使用“Agent+知识库+自动化+人工节点”的框架。

注意：是尝试，不合适就不要用！

💡

1、Agent负责接收任务、理解意图、调用工具和生成结果。

2、知识库负责提供客户、产品、制度、流程和历史案例等企业上下文。

3、自动化负责定时触发、消息通知、任务流转和结果归档。

4、人工节点负责审核高风险内容、处理异常和完成最终决策。

不要把人工节点理解为系统不够智能。对于企业项目，合理的人机协同往往比追求完全自动化更加安全、稳定和容易验收。知识库建设前，可以先盘三类资料：

💡

1、CRM和客户档案。

它回答的是：谁在买？客户有什么特征？过去沟通过什么？目前处于什么阶段？

2、SKU和产品资料。

它回答的是：企业卖什么？产品规格、价格、适用范围和限制是什么？

3、SOP和流程标准。

它回答的是：员工应该按照什么步骤工作？什么结果才算合格？什么情况需要升级处理？

如果这三类资料都不完整，不能假装“接上大模型就能解决”。应该先做最小可用知识库。

所谓最小可用知识库，不是把企业所有文件一次性导入，而是围绕第一个试点场景，只整理真正需要的资料，也就是业务人员、销售人员等不用的千万别放，浪费时间、浪费人力！

例如，做客服问答智能体，第一期可以只整理产品说明、常见问题、售后政策、退款规则和升级人工的条件。其他的之后陆续补充。

1.  针对大型企业的AI智能体交付方案

大型企业通常具有组织复杂、系统较多、数据敏感、权限严格和决策链较长的特点。简单点说，就是国企央企流程太长，公司容易卡在流程上，无论是交付还是最后的收尾款。

第一阶段：应该开展企业级诊断

不仅访谈老板，还要访谈业务部门、信息科技部门、数据部门、安全合规部门和一线使用人员。

先访谈老板，领导发话了，底下的人才配合。

第二阶段：建立场景库和优先级

大型企业可能一次提出几十个场景，需要按照业务价值、实施难度、数据基础、风险和可复制性评分。

按照频次划分，先把用的最多的挑出来。

第三阶段：建设统一基础能力

包括统一模型接入、统一知识库、统一权限认证、统一日志审计、统一智能体编排和统一运营看板。

这个最好用成熟产品，因为容易重复造轮子

第四阶段：开展单部门试点

即使企业预算充足，也不建议第一期全公司上线。可以选择一个部门、一个场景和一组真实用户连续使用。

小闭环跑起来，先让领导看到成效，才有二期项目。

第五阶段：进行安全和稳定性测试

需要测试正常输入、缺失输入、异常输入、越权访问、敏感信息、网络中断、接口失败、模型不可用和并发压力。

主要是让客户方人员觉得好用，客户说好才是真的好。

第六阶段：找典型场景逐步推广

试点稳定后，将标准化能力复制到其他部门，同时保留不同业务条线的个性化配置。

一个场景建好了，才容易复制，老板也比较喜欢复制，不用动太多脑筋。

B端大型企业的AI智能体项目主要交付物包括总体规划、业务场景地图、技术架构、数据架构、知识库标准、安全方案、试点系统、测试报告、培训材料、运营制度和推广计划等。

1.  针对中型企业的AI智能体交付方案

中型企业通常有一定业务基础和数字化系统，但预算、技术团队和管理能力有限。不适合一开始建设过于复杂的平台，更适合采用成熟平台加场景定制。说直白点，有钱，但不多。

第一步：选择一个与收入或者核心交付相关的场景。

例如，销售商机分析、客户方案生成、客服知识问答、项目资料整理或者内容生产。销售！销售！销售！先拿下这个场景再说其他！

第二步：整理最小知识库。

只整理与试点场景直接相关的客户资料、产品资料和SOP。

第三步：使用成熟平台搭建智能体和工作流。

尽量减少底层重复开发，把预算放在业务规则、知识库质量、系统接口和员工使用体验上。很多企业不会用国外的知识库的，直接上乐享等国内知识库。

第四步：安排两到四周试点。

让真实员工连续使用，记录成功任务、失败任务、人工接管和改进建议。用客户的数据跑任务，逐步迭代！

第五步：验收后决定是否扩展。

扩展方向可能是增加用户、增加场景、对接更多系统，或者将临时工具升级为正式系统。二期项目需要引导，老板也需要成绩证明自己！

中型企业的AI智能体项目交付重点是快、稳、可见，不要追求落地方案太多复杂。

1.  针对小型企业的AI智能体交付方案

小型企业更关注价格、速度和立即见效。说直白点，没钱！能省则省！但是还想做！收入主要在后期！

1、最开始可以从咨询、培训、Skill、小工具或自动化流程切入。例如：自动整理每日销售记录；根据客户资料生成跟进建议；根据产品资料生成短视频文案；自动汇总客服问题；根据会议记录生成任务清单。

2、尽量使用客户已有工具和成熟平台，不要让客户一开始承担过高的服务器、开发和维护成本。小型企业项目应尽量做到1到2个月内看到结果。

3、交付物可以包括一个可用工具、一套提示词、一份知识库、一套操作手册和一次员工培训。小型企业的关键是控制范围。客户很容易在看到效果之后，不断提出新的想法。因此合同中必须明确第一期只解决什么问题。

### 04. 流量来源和订单报价

流量必须重视，都知道AI智能体有用+要建，但是谁能卖出去更重要。

1.  公域流量

公众号软文，朋友圈投流，抖音快手视频号（短视频平台）为主。

比“我会做AI智能体”更有效的，是发布一个具体业务问题如何被改善。例如：

💡

1、“我们如何把销售拜访纪要从40分钟缩短到10分钟。”

2、“如何从两千条客户聊天记录里筛选出高意向线索。”

3、“如何让客服智能体只回答有依据的企业知识。”

4、“为什么企业AI项目不能一上来追求全自动。”

5、“一个十万元以内的中小企业AI项目应该怎么设计。”

内容要包含客户原来怎么做、遇到什么问题、使用了什么资料、AI负责什么、人工负责什么、最终有什么变化。

尽量展示真实流程和边界，而不是只展示漂亮界面。也要突出AI智能体垂直化的解决方案和产品优势

1.  私域流量

转介绍，线下沙龙，行业论坛，B端大客户销售渠道为主。

搞流量的时候，和客户主要问三个问题：

💡

1、你们现在最花时间的重复工作是什么？最怕哪个环节出错？哪个环节不怕，比较标准化一点？

2、这件事现在几个人做，每次花多久？成本大概多少？

3、如果先改善一部分，什么结果你们觉得最值得付费？预计想省下多少钱？

第一次合作可以从诊断、小培训、小工具或者短周期试点开始。小订单的价值不仅是订单金额，更重要的是让你进入现场，看到老板没有说清楚的真实问题。

很多大项目并不是第一次沟通就签下来的，而是先做咨询，再做培训，再做小场景，最后进入更大的智能体建设和陪跑项目。

1.  订单报价

不同AI智能体服务的报价，在各家公司相对报价差异很大。

以OPC一人公司和20人以内小团队为例子，可以参考如下报价：

1、AI智能体企业咨询：2000-3000/半天，水平更高的咨询师报价再提高点。

2、AI智能体企业培训：4000-6000/半天，水平更高的讲师报价再提高点。

3、AI智能体定制化开发（无论是联合研发，还是纯项目外包）：10W-50W，确实和需求的多少有关，用的什么工具和技术，产品和开发水平更高的团队报价再提高点。

1）小型Skill可以按照约3000—5000元评估；

2）小应用、小看板或者单流程工具可以按照约1万—3万元评估；

3）陪跑服务可以按照每月3万—5万元评估，常见周期为两到三个月；

4）中小企业验证型项目常见总预算可以控制在10万元以内。

这些数字只是经验区间，不是统一市场价格。

企业咨询、培训和定制项目还需要结合咨询师水平、讲师影响力、行业经验、数据复杂度和客户规模综合报价。

4、同时，在做B端项目的时候，一般会把报价单拆成多个部分，比如

💡第一部分，需求调研费用。

第二部分，方案设计费用。

第三部分，知识库整理费用。

第四部分，智能体和工作流开发费用。

第五部分，系统接口和部署费用。

第六部分，测试与验收费用。

第七部分，培训与文档费用。

第八部分，运维和陪跑费用。

这样客户可以清楚知道钱花在哪里，服务商也能在需求变化时判断新增内容属于哪一部分。账号、模型API、云服务器和第三方平台费用，建议由客户以自己的主体购买和承担。服务商负责方案、配置和交付。

### 05. 实施边界和风险控制

AI智能体面对B端的项目，确实踩坑很多，尤其是开发实施项目，所以有风险意识，能提前规避就规避。

在实际开发和交付的过程中，经常遇到客户增加需求、对AI智能体预期过高、实际开发的AI智能体在数据对接上存在层层阻碍、业务部门和销售觉得AI智能体不好用等卡点。

部分可能会导致实际开发的工作量超过合同约定的范围，客户又不愿意增加预算，应该如何把控风险，做好相应措施？

1.  风险一：客户不断增加需求

AI智能体项目最常见的问题，就是客户看到第一个功能之后，立即提出十个新想法。

解决办法不是拒绝所有变化，而是建立需求变更机制。

1、合同附件中要明确本期交付范围，包括用户数量、业务场景、知识库数量、接口数量、自动化流程数量、部署环境、培训次数和维护周期。同时明确本期不做的内容。

2、新增需求需要填写变更单，说明需求内容、产生原因、对周期的影响、对费用的影响和是否调整验收时间。

3、小范围优化可以包含在约定的修改次数内，新增场景、新增系统接口和重大流程变化必须重新报价。

1.  风险二：客户对AI预期过高

有些客户认为，AI智能体上线后可以完全替代员工，百分之百正确，自动完成所有操作，并且立即带来收入增长。肯定不是这样的哈，是个人都知道无法100%替代，所以：

1、售前阶段就要管理预期。不要承诺无法独立控制的营收、利润或者ROI。毕竟企业业务结果还会受到产品、销售能力、市场环境、客户质量和组织执行等多种因素的影响。

2、我们可以承诺的是项目范围内可验证的变化，例如处理时间缩短、内容产量提高、人工步骤减少、格式合格率提高或者知识检索更方便。

3、对于高风险任务，要明确AI智能体只提供辅助建议，最终结论必须由专业人员审核。

1.  风险三：数据和接口迟迟不到位

很多项目不是开发做不出来，而是客户数据无法提供、系统接口没有开放、权限审批没有完成。

1、项目启动时要建立数据和接口前置条件清单。每一项资料都要有责任部门、责任人、提交时间、格式要求和验收标准。

2、如果客户未按约定提供资料，项目周期应相应顺延。对于尚未开放的接口，可以先用脱敏样例数据完成原型验证，但正式上线前必须完成真实环境测试。

1.  风险四：员工觉得不好用

技术人员认为功能已经完成，但业务人员不愿意使用，原因可能是操作步骤太多、输出格式不符合习惯、结果不稳定，或者系统增加了员工工作量。所以：

1、项目不能只由老板和技术部门验收。需要让真实使用者参与需求梳理、原型测试和试点。

2、试点期间记录员工每次使用的成功、失败、修改和放弃原因。如果AI智能体生成结果之后，员工还要花大量时间重新整理，说明项目还没有真正跑通，对方不愿意用那再正常不过了。

1.  风险五：数据安全和合规

合同和方案中要写清数据范围、使用目的、访问权限、存储方式、保留时间和删除机制。

1、涉及客户隐私、商业秘密和敏感数据时，应采用脱敏、最小权限、日志审计和人工审核。不要把客户资料用于未经授权的模型训练。不要通过不明来源的平台传输敏感文件。

2、如果客户要求绕过平台限制、自动控制个人账号、批量发送信息或者使用未经授权的数据，应该拒绝，或者调整为合规方案。

B端的项目企业一般要求本地化部署和开发，数据方面的问题也容易失控，或者部分报错，有时候多留几个心眼，毕竟企业相比AI智能体建设，更希望原来的系统不要出错。

最后，祝看到这里的伙伴们，都能做好B端企业AI智能体服务，赚钱多多！
