### 01. 本次航海概览

#### 1. 项目本质是什么

许多人已经习惯了让AI帮忙写周报、做会议纪要、生成PPT、回答客服话术，但大多数用法仍然是“你说一句，它答一句”。真正想让它主动干活时，你还是得自己复制资料、交代背景、提醒格式、逐一检查，下一次又得从头来一遍。

Agent想解决的问题，是把那些重复出现、规则固定、流程清晰的工作，整个交给AI自动跑起来。比如每周固定要做的行业信息汇总、周报撰写、会议纪要输出、客户问题回复、数据表格更新、内容初稿生成——这些事本身难度不高，却非常吃时间。如果你能把岗位职责、操作步骤、判断标准、工具接口都接好，Agent就能像一位“AI员工”一样，根据你设定的规则接收任务、调用相应工具、给出结果，并且每一步都有运行记录可查。

这次航海的目标，就是带大家用Codex、Hermes和飞书CLI这三样工具，搭出自己的第一个Agent，把你工作中每周至少重复三次的一项任务交给它自动完成。你可以从身边最常见的场景入手，比如自动整理飞书文档、根据评论生成回复、批量产出内容草稿、归拢客户信息、汇总项目进度、完成数据复盘等。把它做成一个最小可运行版本，先让这个Agent真正能干活，然后再逐步丰富功能、提升稳定性，最后再去理解多Agent协作和企业级AI服务的可能性。

#### 2. 别人已经用Agent做出什么了

动手之前，先看看已经有人跑出什么样的结果了。你不是第一个吃螃蟹的人。

第一个例子来自圈友@天才老师。他搭了一个双Agent组合，代号分别是“煤老板”和“翠花”，一个管策略，一个管执行。靠着这两个AI帮手，他一个人运营了4个YouTube AI Shorts频道，合计订阅数达到130万，总播放量2.25亿。以前做一条视频要花4到5小时，现在只需要大约20分钟。2026年2月他产出了41条视频，其中14条播放量破百万，1条破千万。他的起点不是“会写代码”，而是“懂什么样的AI Shorts能爆”，然后让AI去完成拆解、生成、归档和执行。  
他的完整复盘见这个帖子：《4个频道，1.3M订阅，2亿播放：一个碳基API与两个硅基员工的YouTube矩阵运营实录》。

这次航海，我们只走一条更适合新手的路：从一个小小的Agent Demo开始，跑通Codex+Hermes+飞书CLI这套链路，做出一个能为你真实业务干活的Agent。等掌握了从0到1的搭建本领，再去探索多Agent协作和企业级AI服务也不迟。

#### 3. 这次航海的交付物

在21天的航程里，你要通过必修关卡1到关卡6的全部作业，最终交出一个能运行、能给人展示的Agent。它可以帮你整理资料、写会议纪要、做周报、回复客服消息、整理选题、搭内容初稿、更新数据，也可以是你自己业务中的某个具体小岗位。

为了证明这个Agent是真的，至少需要三样材料：
- 一个Agent网址链接——证明它能被公开看到。注意，这里所说的是展示页，不是在线调用页面。别人可以打开看看它是什么、能做什么，但不能直接在上面和Agent对话或让它干活。
- 一张成功运行截图——证明它最近确实自动执行过任务，最好能看到输入前、运行中、输出后的完整证据。
- 一份使用说明书——让别人知道它省下了哪些人工、该怎么使用，由AI生成即可。

为什么展示页就够，而不是直接部署上线？因为真正的在线使用意味着服务器成本、模型调用费用，别人每次使用都会持续消耗资源。对大多数同学来说，现阶段更应该先做出一个稳定工作的Agent，而不是立刻陷入部署和运维。如果你能力和需求都到位，当然可以自己完成部署，让别人真正在线体验，但这属于跑通基础闭环之后的高阶玩法，不在本期航海的必修范围内。

每一关的作业都是为最终成果铺垫的，所以必修关卡的任务都别跳。至于具体长什么样、有没有模板、到哪里提交，每一关开头的任务卡里都会写得清清楚楚。

#### 5. 为什么选这三样工具？

也许你已经用过Codex，觉得它本身就能完成不少事，为什么还要费力接上Hermes和飞书CLI？因为“让AI做一次任务”和“让Agent长期为你工作”是两码事。偶尔处理一次工作，直接开个Codex对话就够了；但如果你想让这项工作能被反复使用、长期维护、持续优化，甚至到点自动触发，还能让团队其他成员一起使用，那你就得把它做成一个真正落在业务场景里的Agent。

这三样工具各有分工，恰好拼成一个最小闭环：
- Codex是那个“会动手的人”——帮你搭项目、写脚本、跑命令、调工具、检查结果。你把目标和约束说清楚，它就能把工作流变成可执行动作，让Agent不再停留在聊天窗口里。
- Hermes是那个让这个人“长期值班”的调度台——它负责承载任务入口、运行节奏、状态记忆和持续调度。Codex擅长当下动手，Hermes则让这套工作可以被反复调用、长期运行，不需要每次从零解释。
- 飞书CLI则是一个“连接飞书的工具箱”——可以读写文档、表格、消息、日历等真实工作数据。因为很多工作数据都存在飞书里，接上它，Codex才能真正进入你的工作流。

换句话说，Codex负责开发和调试Agent，Hermes负责承载和运行Agent，飞书CLI负责让Agent接触到你真正的办公场景。  
接下来就是开工前准备，我们会带着你安装这三个工具并完成基础配置，为后面的正式搭建铺路。

另外特别提醒一句：能用Codex就优先用Codex。如果你卡在账号或网络问题上，国内可以先拿WorkBuddy顶上，一样能完整跑完整套流程。先把Agent做出来，掌握从0到1的方法；工具和环境问题，之后慢慢解决也不晚。千万别把时间浪费在挑选工具上，先跑通一次，比什么都重要。

## 总结：最小Agent如何成立

最小Agent的本质，就是先让AI为你完整完成一次看得见的任务。本关通过【音视频转录助手】Demo，把“输入→处理→输出”的链路完整贯通。只要Agent能够接收任务、调用工具、生成文件，并让你用截图证明结果存在，第一个最小Agent就算成立。

四步核心动作：
1. 明确输入：选一条公开可访问、时长适中的音视频，让Agent有素材可处理；
2. 搭建入口：用Codex创建Hermes Agent和飞书Bot，完成私聊或群聊的接通测试；
3. 下达指令：把下载、转录、保存文件等步骤描述清楚，让Agent按部就班执行；
4. 核对输出与边界：确认转录结果文件已生成，并让Agent说明自己能做什么、不能做什么。

### 01. 本章重点：为什么需要Agent这个“正式员工”

在关卡1，你已经通过Codex + Hermes +飞书，体验了一个最小Agent Demo：把音视频链接交给它，它就能下载并转录，然后生成一份结果文件。看到这里，你可能会产生一个疑惑：既然直接用Codex对话就能完成这些事，为什么还要引入Hermes和飞书，多此一举地搭一个Agent？

其实，跑通一次任务和配备一名长期在岗的AI员工，是两种完全不同的命题。当你只是偶尔需要转换一段音频时，直接让Codex处理就够了；但当这项工作每天都会发生、需要反复执行，甚至希望团队成员也能共用、并可以长期维护与迭代时，你就需要把它固化成一个Agent。Agent有独立的岗位、固定的工作流程、稳定的入口，还能持续沉淀规则与经验。今后无论自己还是同事，只要把任务丢给它就行，无需每次重复解释背景。

因此，本周课程真正想教给你的，不是“用AI完成一次性任务”，而是“如何培养一名可以长期在职的AI员工”。

你会发现，这位AI员工目前还很像刚入职的实习生：能做基础转录步骤，但文字未必精准；内容只是原始记录，没有重点提炼；文件也只在本地，线上修改、多人同步与长期沉淀都不方便。这并没有错。实习生要成长，需要有人告诉他：负责哪类工作、接收什么信息、按什么流程执行、提交什么成果，以及遇到什么情况必须停下来请示。Agent也是如此。只有在岗位定义、工作流程、交付标准和人工兜底这四件事上足够清晰，它才能从“能跑一次Demo”进化为“能扛住一项具体工作”。

所以这一关，我们把“定岗”放在首位：你要为第一个正式Agent员工明确服务对象、要解决的问题和要交付的成果。这张岗位卡将直接交给后的关卡3（拆工序）和关卡4（写大脑）使用。岗位描述越清楚，后续流程与Profile（岗位说明书）自然越好写。

**1.2 用五个维度筛选**

把候选任务依次放入以下五个问题中检验，每满足一项计 1 分：

1. **它是否每隔一段时间就卷土重来？**每周、每个项目、每次活动里都会占用时间，属于常态性投入。

2. **它收到的输入是否稳定、清晰？**提交上来的材料基本锁定在聊天记录、文档、网页或表格里，不会每次花样百出。

5. **出了岔子能否人工接管？**Agent 交付后，你还有机会在发送、发布或对外提供之前过目，即使有疏漏也不会立刻造成严重后果。

**计分结果**：拿到 4 分及以上，非常值得作为 Agent 化的第一候选；介于 2 到 3 分，可以先化简环节、补充细则，或安排人工复核；不足 1 分，则建议放进“不做清单”，暂不优先处理。

**1.3 一句话岗位定义**

借助下列公式来表达：

```

```

几个已经落地的示例：

• “一旦拿到选题和参考素材，Agent 自动提炼重点、写出大纲与初稿，并将结果建成飞书文档。”

• “每逢周五下午，Agent 自动调取我飞书多维表格里的当周记录，草拟好周报并推送到我的飞书消息。”

**检验办法**：这句话必须包含输入、动作和输出三个要素。缺少哪一个也不往下走，补齐了再续。

### 04. 本关小结

**所谓 Agent 岗位卡，就是把“跑得通的 Demo”升级成“职责讲得清的 AI 员工”。**

**四个关键动作：**

1. **整理重复事务**：先通过 AI 对话，把每日、每周以及被动触发的重复事项汇成一份候选池。

2. **五维评估筛选**：AI 先作初筛，频率、输入、规则、验收方式和风险边界由你最后拍板。

3. **明确一句话定义**：用“收到什么输入、自动执行什么操作、结果落到什么地方”把职责讲清楚。

1. **发一张职位卡给 Agent**

输入、动作、产出、合格标准、人工接管方式、本期不做什么——六项内容一次写齐。

**💡 新手了解下：**

关卡 2 之后，Agent 已经清楚自己的职位和大致职责。

但人和 Agent 做同一件事，最大的差异在哪？

人会不自觉地做很多默认判断：你一眼就知道“这篇素材质量不行”“这位客户是比价的，少花时间”。Agent 没有这种直觉，所以每条判断都必须由你亲手写出来。

先别去琢磨全自动的最优方案，优先把你平时做事的真实顺序写出来，尤其是那些“我一看就懂”的隐含经验。你讲不清，Agent 就更不可能做对。

### 01. 操作指南

#### 第 1 步：让 AI 先写一版你的手工流程，你来校改

先确认 01-岗位卡.md 已保存到 Agent 项目目录。后续操作不要依赖聊天窗口里的旧记录，而是让 Codex 直接读取该文件，确保看到的版本是你最终确认过的。

⬇️ 把下面这句提示语发给 Codex（记得替换【】里的内容）：

Plain Text

```
请打开我在关卡 2 创建的 Agent 项目文件夹：

【替换为你的 Agent 项目文件夹路径】

读取其中的：
01-岗位卡.md

请先告诉我：
1. 是否成功找到并读取文件；
2. 这份岗位卡中的岗位名称和一句话岗位定义是什么；
3. 文件是否存在内容缺失或无法识别的问题。

这一步只读取和确认内容，暂时不要修改文件，也不要开始生成工作流。
```

确认文件读取正常后，再开始拆步骤。不要让 Codex 根据聊天记忆自己脑补岗位卡。

现在，让 AI 按你的工作方式生成一版步骤草稿，你来改。

对于多数重复性任务，AI 的草稿已经能覆盖大部分主干环节。

你要做的是：把错误的删掉，把不准的改对，把漏掉的补上。

👇 复制这段指令，继续在同个窗口发出去：

Markdown

```
请根据你刚刚读取的《01-岗位卡.md》，拆解我人工完成这项工作的完整流程。

请注意：
- 只以岗位卡中的最终内容和我后续的补充为依据；
- 不要依赖聊天记录中更早的版本；
- 不确定的地方先问我，不要自行猜测。

要求：
1. 把每一步都写出来，不跳过任何步骤，哪怕很简单也要写；
2. 每一步标注大概耗时；
3. 至少写出 5-12 步；
4. 用编号列表，格式如下：

人工流程：
1. [动作描述]（x 分钟）
2. [动作描述]（x 分钟）
……写完后先发给我确认，不要直接保存文件。
我会告诉你哪里不对，你再帮我修改。
```

AI 给出草稿后，你只需要关注三类问题：

1. **不存在的行为，删掉**（AI 可能凭想象加了步骤）。

2. **描述不准确的地方，改正**（比如工具名写错了）。

3. **被漏掉的关键环节，补上**（尤其是那些“你顺手就做了、绝不会说出口”的隐含判断）。

💡注意：不要跳过任何一步。哪怕你觉得“这步也太简单了”，Agent 依然需要看到它。

拿“把一期播客的转录稿整理成可读文档”来说，AI 草稿被你改完后的效果如下：

![](img/6e784a07e4a40e1cd6fb6bb34077c072.png)

你的链条不必和这个示例一致——如实照你的实际流程来写。

**验收标准**：至少 5 个环节。如果没有 5 个，说明你对自己工作的观察还不到位，先亲手做一轮，边做边补。

#### 第 2 步：把必须做决定的点圈出来

步骤拆完了，但这项工作还没有完成。

很多时候，你觉得自己只是顺着步骤走，实际上每一步都在做判断。Agent 后续能否稳定运行，很大程度上取决于这些判断有没有被还原。

所以这一步要往下继续挖：

• 为什么用这种方案，而不是另一种？

• 什么条件下走 A 路径，什么条件下走 B 路径？

• 你的判断依据是什么？

• 遇到意外情况怎么处理？

把上一步形成的环节清单重新过一遍，凡是需要你拍板的地方全部标出来，并写明理由。

一下子想不起来也没关系，可以和 AI 多聊几轮，把隐藏的判断一点点挖出来。

还在同一个窗口👇 把这段提示语发过去：

Markdown

```
你是一名 Agent 工作流教练。

你的任务不是帮我分析流程。

而是通过连续提问，帮我挖掘我在工作中的真实判断。

规则：

1. 一次只讨论一个步骤。
2. 每次只问我一个问题。
3. 根据我的回答继续追问。
4. 不要一次问很多问题。
5. 当你认为已经挖出了这个步骤真正的判断，再帮我总结。

重点不是动作。

而是：

- 我为什么这么做？
- 我怎么知道应该这么做？
- 我什么时候会换一种做法？
- 我依据什么判断？
- 有没有踩过坑？
- 有没有例外？
- 有没有新人最容易做错的地方？

如果我回答得太泛，请继续追问。

例如：

我说：
&quot;这里我会修一下错字。&quot;

不要结束。

继续问：

你是怎么知道哪些地方错了？

我回答后，再问：

有没有一些词你一定会检查？

再问：

有没有什么时候你不会改？

最后总结成：

## 判断

......

## 判断依据

......

## Agent 将来应该如何判断

......

然后进入下一步。

整个过程中，你不要替我回答。

你的任务是把我脑子里的经验挖出来。
```

继续用“播客转文档”这个例子来看：

| 环节 | 你要做的决策 | 决策依据 |
| --- | --- | --- |
| 获取音源 | 这个链接可以直接下载吗？ | 是公开链接，还是要登录？平台有没有下载限制？ |
| 用哪个转录工具 | 哪个工具效率最高？ | 音频是中文还是英文？时长多少？本地工具够不够快？ |
| 修正识别错误 | 哪些词被转错了？ | 人名、公司名、专业术语是高发区；需要结合上下文判断 |
| 分段并加小标题 | 按什么规则切段？ | 话题切换、讲话人变化、抛出新议题的位置 |
| 质量终检 | 这版整理稿能否交付？ | 是“提纯稿”而非“摘要”？案例和数字是否完整？格式是否规范？ |

每个决策点，都要给 Agent 一条可执行的标准。

拿“数据是否有来源”举例，规则可以写成：如果引用了具体数字却没标来源，先标记为待确认，不能直接发布。

💡如果被追问时答不上来，可以请 AI 先给几个选项，你来挑一个更贴近实际的：

![](img/713e572a28e0242338b1ca0ebeb16163.png)

**如果 AI 连番追问、节奏太慢，直接告诉它：只抓关键决策点，提速。**

![](img/d8c24cf82a53d9dea631ce06dfdcd3ee.png)

说到底，**AI 挖得越深、规则越细，Agent 后续的表现就越稳，来回返工也越少。**时间允许的话，建议把这一步做得更扎实。

#### 第 3 步：用 RFC 2119 把经验转成 Agent 指令

前面两步已经把流程和决策依据理顺了。

现在，要把这些内容“翻译”成 Agent 实际能执行的指令。这里会采用一种行业里常见的规范——RFC 2119，用于标注要求的强度：

• MUST：**强制要做**；

• SHOULD：**建议要做**；

• MAY：**可选，做不做都行**；

• MUST NOT：**绝对不做**。

不用在这些英文术语上花心思，AI 会按这套规范帮你整理内容。

继续在同个窗口👇 将这段提示语发给 AI：

Markdown

```
你现在是一名 AI Agent 架构师。

将上面的【工作的流程】和【判断标准】汇总

请不要简单润色，而是把它抽象成一个真正适合 AI Agent 执行的工作流。

要求：

第一步，理解人工真正完成的目标，而不是照抄步骤。

第二步，删掉所有属于人的操作，例如：
- 打开网页
- 点击按钮
- 复制粘贴
- 登录网站
- 上传文件
- 下载文件
- 手动整理

改成 AI 真正应该执行的能力。

第三步，把流程改写成下面结构：

## Agent 工作流：xxx

### 触发条件

什么时候开始执行。

### 步骤

每一步描述 AI 的行为。

遵循 RFC2119 规范：

- MUST：必须执行，没有例外。
- SHOULD：通常应该执行，特殊情况可以调整。
- MAY：可选执行，根据情况决定是否进行。
- MUST NOT：禁止执行，任何情况下都不能做。

每一步尽量写成：

动作
判断
异常处理

不要写人成本。

### 成功标准

什么叫真正完成。

要求尽量可验证。

### 失败处理

所有可能失败情况。

每一种失败都给处理方案。

### 人工兜底

哪些情况必须暂停交给人确认。

不要写实现代码。

不要考虑具体平台。

重点描述 Agent 应该如何思考和执行。
```

生成后的参照样例：

Markdown

```
## Agent 工作流：音视频转录整理

### 触发条件
用户发送一个播客/视频/音频链接，或上传一个本地音频文件。

### 步骤
1. MUST 确认收到链接或文件。如果格式不明确，MUST 反问&quot;请发送播客/视频链接，或告诉我本地文件路径&quot;。
2. MUST 判断来源类型：小宇宙、B站、YouTube、飞书妙记、本地文件、其他。
3. SHOULD 优先查找是否有现成字幕/逐字稿（如 YouTube 字幕、飞书妙记转录）。有字幕则直接使用，跳过 ASR。
4. 没有现成字幕时，MUST 使用 yt-dlp 下载音频（或直接读取本地文件）。
5. MUST 检查音频格式和时长。超过 2 小时的音频 SHOULD 分段处理。
6. MUST 使用 faster-whisper 或 mlx-whisper 进行语音识别转录。
7. MUST 清洗转录稿：去时间戳、去说话人标签、去口水话和重复句、修正常见 ASR 错词（尤其人名、公司名、术语）。
8. MUST 按话题分段，加简短标题。标题 MUST 来自真实内容，MAY NOT 使用&quot;其他有效观点&quot;&quot;补充说明&quot;等模糊标题。
9. SHOULD 对重要判断、金句、关键数据适度加粗。
10. MUST 把整理稿写入飞书文档，标题为&quot;[来源平台]-[原标题]-整理稿-YYYY-MM-DD&quot;。
11. MUST 验证飞书文档目录结构和权限，确认用户能打开。
12. MUST 把飞书文档链接交付给用户。

### 成功标准
- 无时间戳、无说话人标签
- 无&quot;其他有效观点&quot;等垃圾桶标题
- 不是摘要式要点，是分享式提纯稿
- 保留了关键案例、数字、判断链和重要原话
- 主要 ASR 错词已修正
- 飞书文档目录正常、用户有访问权限

### 失败处理
- 链接无法下载 → 报告原因（平台限制/需要登录/地区不可用），建议用户换链接或提供本地文件
- 音频超长（&gt;2小时） → 自动分段处理，每段独立转录后合并
- ASR 转录质量极差（大量乱码） → 标注&quot;转录质量异常，建议人工校对&quot;，仍交付初稿
- 飞书权限授予失败 → 交付文档链接，附注&quot;文档已创建但协作者权限未完成，请手动添加&quot;

### 人工兜底
- 涉及非公开音视频（付费课程、私密会议）时，MUST 停下来问用户确认授权
- ASR 无法确认的专有名词标注[待确认]，由用户最终校对
- 整理稿交付前，用户可选择先看大纲再决定是否继续
```

💡**第一次生成不追求完美。** 先确认目标、步骤、决策规则、异常分支和人工接管是否符合你的真实工作方式。缺了什么，就用对话让 AI 补充。

每个环节都应该给出 MUST/SHOULD/MAY 的标注。

#### 第 4 步：把作业链路画成流程图

当前得到的文本指令已经很具体，但只看文字时，结构问题不容易暴露，比如：

• 某个节点之后没有对应分支；

• 异常路径没有回到正常环节；

• 人工接管介入得太迟；

• 步骤之间存在重叠或中断。

所以这一步，要把写好的 Agent 作业链路画成流程图，从整体上确认它是否完整、连贯。

画图这步可以不亲自动手。继续在原来的对话窗口，让 AI 根据上面的步骤和决策规则生成 Mermaid 绘图代码。

#### 第 6 步：不同类型 Agent 的侧重点

各类 Agent 的关注点有较大差别。你可以对照下面的列表，为自己的 Agent 补上合适的信息。

**6.1 文档型 Agent**

（内容创作、会议纪要、报告生成等）

• 输入素材的读取顺序与优先级；

• 输出格式、语气、篇幅等限制；

• 质检标准：事实核查、格式检查、关键信息是否遗漏；

• 引用出处、敏感信息的边界规则。

**6.2 表格型 Agent**

（数据整理、报表汇总、信息统计等）

• 字段之间的映射关系；

• 数据更新的策略：新增、覆盖或合并；

• 缺失值、重复值、异常值怎么办；

• 何种情况要告警或者请求人工确认。

**6.3 消息型 Agent**

（客服回复、通知推送、私聊助手等）

• 由什么事件触发执行；

• 回复边界：哪些问题能答，哪些不能答；

• 不同业务场景下的回复策略；

• 什么情况下必须暂停并转人工。

**6.4 流程自动化 Agent**

（审批、文件流转、多工具协作等）

• 每一步具体调用哪个工具；

• 工具失败后的重试办法；

• 上下游数据如何传递；

• 哪些环节要等结果，哪些可以并行执行；

• 中断后如何续跑。

每个 Agent 各有特点，也可能同时具备好几种类型的属性。没有一套规则能通用于所有场景。

比起一开始就追求面面俱到，更重要的是结合自己的业务，让作业链路在实践中不断生长。

# 遇事先让 AI 跑一轮，再考虑找人

不妨把求助的次序调个个儿：碰到难题，先丢给 AI 试一遍，再判断要不要查资料、问同事。这个习惯养稳之后，许多原先让人头疼的活儿反而会顺利不少。

| 卡壳点 | 习惯操作 | 核对标准 |
| --- | --- | --- |
| 流程写得虚，接手方抓不住重点 | 堆砌笼统描述 | 每个动作动词打头，接收方扫一眼就明白该干什么 |
| 判断关卡缺失，接手方凭感觉发挥 | 等事后靠人补救 | 提前说清“到什么状态算过关”，人也能用同一套尺子复查 |
| 步骤数冲过八道 | 硬着头皮往下堆 | 先折成“接收→处理→产出→人工验收”四段，主干压在八步以内 |
| 工具还没敲定 | 急着把命令写死 | 先挂“工具待接入”的标记，别在这一环死磕 |

| 受阻情形 | 可以这样对 AI 开口 |
| --- | --- |
| 不清楚手工流程该拆几道 | “我平时处理[任务名]时，动作大概是这些。请帮我拆成至少五步，每步写明我做了什么、花多久、看哪些材料。” |
| 凭感觉的判断写不出来 | “下面是我手工做的步骤（粘贴）。请标出哪些地方需要我拍板，说明判断依据，再给每个节点起草一条 Agent 能执行的规则。” |
| MUST / SHOULD 分不清 | “这是我的工作流（粘贴）。请逐条判定：MUST 是不做就出错，SHOULD 是尽量做但不致命，MAY 是可选，并说明理由。” |
| 流程太长不会精简 | “我的 Agent 流程有 X 步（粘贴）。请指出哪些能合并、哪些可降为可选，目标是主干不超八步。” |
| 流程图不知从何下手 | “按这份工作流（粘贴 MUST/SHOULD 步骤）生成 Mermaid 图代码，至少包含两个判断分支。” |

![](img/df22f3a6e3535f57eb50289b542f9ae0.png)

### 03. 本关收尾：把职责拆成动作

**Agent 工作流，本质上是把岗位卡上的职责，转成执行方读得懂、照做得了、事后查得着的操作序列。**

关卡 2 里，第一个正式 Agent 的岗位已经敲定：它给谁干活、收什么材料、交什么结果。这一关补的是从“岗位”到“流程”的缺口——先还原你亲自做这件事的每个环节，再把藏在经验里的判断、例外情形和需要人接手的节点挖出来，最终归拢成一份能照章执行的清单。

让 Agent 出问题的，往往不是任务多复杂，而是流程太模糊。人靠经验可以跳步、随手补、当场拍板；Agent 不行，它要求你把这些隐性内容摊开：哪些非做不可，哪些尽量做，哪些可以省，哪些必须停下来问人。

**这一关要落实四个动作：**

1.  **还原人工流程**：先让 AI 出一版手工操作的底稿，再由你删掉不真实的、修正不准确的、补上遗漏的环节。
1.  **挖出关键判断点**：把“我一眼就明白”的经验讲清楚，写成能判断的条件和依据。
1.  **翻译成 Agent 工作流**：用 MUST / SHOULD / MAY，把动作、判断、异常处理和人工兜底统统写成规则。
1.  **画出流程图**：把主干步骤和至少两个判断分支画出来，方便人复核，后面也能写进 Profile。

这一关做完，Agent 不仅清楚自己扛什么，还知道每一步怎么走。

下一关会拿着关卡 2 和关卡 3 的成果，把 Agent 的身份、目标、规则和自检标准补得更完整。

3. 不同类型的 Agent，侧重点不同

上面那套步骤是共通的，可不同类型的 Agent，真正非写不可的规则并不一样。你不需要把下面这些统统塞进 Profile——挑和你最接近的那一类，对着检查相应内容写没写透就行。

**3.1 内容生产类 Agent**

比如：文章写作、短视频脚本、选题策划、社交媒体文案等。

Profile 里该写透的：

• **读者是谁：**目标读者是哪群人，他们在意什么，能读懂什么。

• **产出长什么样：**文章结构、字数区间、语气、格式以及常用表达。

• **哪些不能碰：**哪些词、哪些语气、哪些表达方式一律不许出现。

• **素材从哪来：**能用哪些资料，哪些内容不许编。

• **怎么自检：**有没有跑题、有没有重复、有没有空话、是否达标。

• **何时问人：**主题不清、资料不够或写作要求打架时，别自己猜。

这类 Agent 最常见的毛病是：看着写完了，味道却不对你的路子，或者为了凑完整而凭空编料。

**3.2 音视频转录与资料整理类 Agent**

比如：音视频转录、会议纪要、课程笔记、采访整理等。

Profile 里该写透的：

• **能接哪些输入：**音频、视频、网页链接、飞书妙记还是本地文件。

• **原内容怎么处理：**时间戳、口水话、重复内容和无意义语气词，去还是留。

• **能改到什么地步：**只顺表达，还是可以重新概括、重新总结。

• **哪些必须守住：**关键原话、数据、案例、结论、任务和负责人。

• **听不清怎么办：**无法确认的地方怎么标记，不许自己编。

• **怎么交付：**发到聊天窗口、飞书文档，还是指定文件夹。

• **怎么自检：**重点漏没漏、原意变没变、文档结构正不正常、用户有没有权限。

这类 Agent 的要害在于：整理可以更清爽，但原意不能走样。

**3.3 办公整理类 Agent**

比如：周报整理、日报汇总、资料归档、报表更新、信息收集等。

Profile 里该写透的：

• **要哪些字段：**每条信息必须带什么，哪些字段允许为空。

• **字段怎么落位：**输入里的内容分别该填到哪一格。

• **格式怎么统一：**日期、金额、姓名、链接等按什么规范写。

• **怎么排序分类：**按时间、部门、项目、优先级，还是别的规则。

• **碰上重复怎么办：**删掉、合并，还是留最新一版。

• **信息缺了怎么办：**留空、标待补，还是回头问用户。

• **异常怎么处理：**格式错、数据打架或识别不了时怎么办。

• **怎么自检：**漏项没有、位置填错没有、重复录入没有、原始数据被改没有。

这类 Agent 的要害在于：内容可以朴素，但字段不能错位，数据不能乱动。

**3.4 客服与销售类 Agent**

比如：售前咨询、客户跟进、社群答疑、销售回复等。

Profile 里该写透的：

• **能答什么：**哪些常见问题在职责范围内。

• **不能答什么：**哪些问题超权限，不许自行承诺。

• **用什么口气：**正式、亲切、简洁，还是带点销售味。

• **怎么判断用户状态：**是在咨询、犹豫、投诉，还是准备下单。

• **哪些话不能说：**不许虚假承诺、不许夸大效果、不许泄露隐私。

• **什么时候才推产品：**满足哪些条件后才谈推荐，别一开口就推销。

• **什么时候转人工：**投诉、退款、价格特批、合同、隐私或复杂问题必须交给人。

• **怎么记录：**该留存哪些客户信息和沟通结果。

• **怎么自检：**有没有答非所问、承诺过头、语气不对或漏答用户的问题。

这类 Agent 的要害在于：先把回复的边界划清，再琢磨怎么把话说漂亮。

**3.5 数据分析与判断类 Agent**

比如：用户分析、内容评分、商品筛选、风险审核、线索判断等。

Profile 里该写透的：

• **凭什么判断：**用哪些数据、哪些条件、哪套标准。

• **标准怎么排优先级：**几条条件打架时，先看哪一条。

• **结果怎么分类：**通过、不通过、待确认，还是按等级打分。

• **分数怎么算：**每项多少分，什么结果对应什么结论。

• **证据怎么摆：**结论要引用哪些原始信息。

• **信息不够怎么办：**不许直接下结论，得标清缺了什么。

• **模糊地带怎么办：**哪些情形必须转给人判断。

• **怎么自检：**依据够不够、结论和证据对不对得上。

这类 Agent 的要害在于：不能光甩结果，还得讲清为什么这么判。

**3.6 流程自动化类 Agent**

比如：收集信息后自动整理、生成文件、发送消息、更新表格等。

Profile 里该写透的：

• **何时开跑：**用户发指令、收到文件，还是定时启动。

• **先后顺序：**哪一步在前、哪一步在后。

• **要调哪些工具：**每个工具各自管什么。

• **上一步挂了怎么办：**重试、跳过、停住，还是请人处理。

• **哪些操作不能重来：**防止重复发消息、重复建文档、重复写数据。

• **数据怎么往下传：**上一步的什么结果交给下一步用。

• **什么算完成：**文件建成了、表格写进去了，还是消息发出去了。

• **怎么留痕：**要不要记执行时间、结果和失败原因。

• **何时找人：**登录失败、权限不够、数据异常或涉及重要操作时及时踩刹车。

这类 Agent 的要害在于：不光写顺路怎么走，还得写清出岔子之后怎么办。

**3.7 文件与知识库问答类 Agent**

比如：公司知识库助手、课程答疑助手、制度查询助手等。

Profile 里该写透的：

• **能查哪些材料：**知识来源和文件范围要明确。

• **资料打架怎么办：**优先哪一版，要不要看更新时间。

• **查不到怎么办：**直接说没找到，不许凭经验补。

• **怎么标来源：**回答要不要附文件名、章节或链接。

• **能答到什么深度：**只复述资料，还是可以再整理、再解释。

• **哪些不能答：**超出资料范围、牵扯隐私或权限不够的内容。

• **怎么自检：**答案是否真有出处，有没有引用错版本。

这类 Agent 的要害在于：只按已有资料说话，不知道就明说不知道。

不过，一个 Agent 也可能同时横跨几类。

例如：

并非每个智能体都只归入单一分类：周报生成并推送到飞书的助手，同时涉及办公整理与流程自动化；会议纪要助手既要处理音视频转写，也要整理办公资料；销售复盘助手则兼顾资料汇总与数据分析。碰到这种交叉定位，先圈定最相近的一到两类，再回看自己的 Profile 是否配齐了对应规则。

细节不必一次补完，优先写清最影响结果的几项：输入长什么样、处理路径怎么走、达到什么标准算合格、哪些行为禁止、异常时如何兜底。框架立住后，就让智能体先跑一轮真实任务，再依据实际反馈继续完善。

| 样本 1 | 最常出现、最有代表性的那类输入 | 主链路能否顺利走完 |
| 样本 2 | 稍复杂或处在边界的输入 | 异常兜底与边缘情况处理 |
| 样本 3 | 你最在意的实际业务场景 | 它对工作是否真有用 |

准备时，也建议顺手记下三点相关思考。

拿音视频转写助手小D来演示：样本 1 选一期约十分钟的公开播客链接，看常规流程；样本 2 用一条十到二十分钟的 B 站公开视频链接，看链接识别与下载；样本 3 拿一条两小时的 YouTube 链接，看长音视频分段处理和转写稳定性。

如果你的助手不属于音视频转写类，也照这个思路来。日报助手可以备：日常素材、信息残缺的素材、你真实要交给团队的那份日报。客服回复助手可以备：常见客户问题、情绪强烈或信息不全的问题、你最怕回复出错的真实问题。

**2. 全链路跑一遍，留存凭证**

每份样本都要把全链路走完，不能只截配置页。你要证明的不是“我配过助手”，而是“它确实完成了一次工作”。每一步都留下凭证。

作业至少要交一张成功执行截图。

| 档位 | 应包含什么 |
|---|---|
| 合格 | 至少有：输入样本、执行过程截图、飞书端产出；更好的是再加人工复核意见与修正复盘 |
| 不合格 | 只剩配置页或脚本页，看不出它实际干过活 |

如果你拿不准凭证够不够，可以把截图发给 Codex，问一句：
```
我会给你提供几张截图，请帮我检查这次 Agent 测试证据是否完整，

我的截图应该至少包含：
1. 输入样例；
2. 运行过程截图；
3. 输出结果链接或截图；

请你帮我判断：
- 这次测试是否能证明 Agent 真的完成了任务；
- 证据链里缺了哪一步；
- 还需要补什么。
```

**3. 人工复核**

有产出，不等于产出能用。复核时可看四个角度；不过最实用的判断只有一句：看完这份结果，你满意吗？它真的帮你解决了问题吗？你敢把这项工作放心交给它吗？

即便答案是否定的，也不要紧。把不满意的地方写下来：哪里做错了、哪里漏了、哪里不符合预期——这些正是下一轮调优最要紧的方向。

拿音视频转写助手来演示，可以按这个思路检查。若你自己拿不准好坏，还有个简单办法：另开一个对话窗口，把产出粘过去或传截图，请它按内行视角帮你挑毛病。

把下面提示词发给它即可（【】内替换成你的信息）：
```
你是一名资深的【Agent 所负责工作】从业者。
请不要评价 Agent 本身，而是站在真实使用者的角度，帮我验收下面这份工作成果。

请重点检查：
1. 是否完成了目标；
2. 哪些地方做得好；
3. 哪些地方存在问题或风险；
4. 如果这是你团队同事交付给你的，你会不会直接采用？为什么？
5. 给出具体的修改建议，而不是泛泛评价。

【粘贴图片或者文字】
```

**4. 把毛病归档，再打磨配置档**

**4.1 先汇总问题**

三份样本都跑完后，先别忙着加功能，把测试中暴露的毛病收拢起来。格式不用一开始就很正式，按 1、2、3 用大白话记下即可，例如：

1. 第一份样本漏了部分内容；
2. 第二份样本排版不符合要求；
3. 第三份样本专有名词识别错误；
4. 飞书文档标题不统一。

把上面这些内容一次性交给 Codex，请它分类并做成表格。飞书里的助手窗口也能做这一步，但长文本交给 Codex 更稳，表格通常也更清楚，后面逐项改起来方便。

可以直接发送下面这段提示词（【】内替换成你的信息）：
```
下面是我测试 Agent 时记录的问题。

【粘贴你的问题】

请帮我整理成一张表格，并按照&quot;问题现象、可能原因、优化建议、优先级（高/中/低）&quot;进行归类。

如果发现多个问题本质相同，请帮我合并；如果有些问题应该先解决，也请说明原因。
```

整理完成后，你会拿到一张清晰的优化台账，例如：

**4.2 调整配置档**

接下来就可以和它一起改。你只需要把发现的问题用自然语言说出来，让它判断毛病可能出在哪，并把要改的内容整理成清楚、可执行的条款。你的任务是核对条款是否贴合业务要求，确认后再让它写进配置档（Profile）。

每次只抓一个最痛的点，别贪多。大致流程是：

1. 先描述故障表现，再说你期望的样子；
2. 请它定位配置档中该补或该改的位置；
3. 让它把你的要求翻译成可执行条款；
4. 你逐条核对；
5. 确认后写入配置档；
6. 拿同一份样本复测，看毛病是否消失。

你完全可以这样对它说：
```
刚才测试时发现了一个问题：

【描述出现了什么问题】

我希望正确结果是：

【描述你期待的结果】

请你：
1. 判断这个问题可能是 Profile 中哪条规则不清楚或缺失；
2. 将我的要求整理成明确、可执行的规则；
3. 告诉我准备修改或补充到 Profile 的哪个位置；
4. 先把修改内容发给我确认，不要直接更新；
5. 我确认后，再帮我更新 Profile。
```

仍拿默认案例来说。假设音视频转写助手小D总把“生财有术”听成“升财有数”，直接告诉它：
```
刚才测试时，“生财有术”被识别成了“升财有数”。

正确结果应该是“生财有术”。

请判断 Profile 中需要补充什么规则，把它整理成可执行的写法，并先发给我确认。
```

它会把你的话整理成：
```
MUST 在清洗阶段检查并修正常见的 ASR 错词。

已知高频错误包括：
- “升财有数”必须修正为“生财有术”；
- “一仁”必须修正为“亦仁”；
- “飞输”必须修正为“飞书”。

无法确认的专有名词 MUST 标记为“[待确认]”，MUST NOT 自行猜测。
```

再比如，如果每次产出排版都飘，也可以直接说：“以后请按固定框架出稿，别每回换样。”它大概会归纳出类似条款：
```
MUST 按以下固定结构输出：
1. 转录稿链接
2. 内容摘要
3. 关键结论
4. 行动项
5. 待确认问题

MUST NOT 自行新增、删除或修改一级标题。
```

条款不用你亲手写，你只要核对它归纳出的内容是否贴合实际需求。确认无误后，再让它写入配置档，并用同一份样本复测。

再叮嘱一句：别一口气改一堆规则。一轮只处理一个最关键的问题，用同一样本确认真的修好，再动下一个。这样更容易看出是哪条规则起了作用，也能减少多处改动互相干扰。

**5. 进阶优化：让助手稳定嵌入业务流**

完成前面的测试和简单调优后，它已经“能用了”。但“能用”和“好用”之间还有距离。

一个真正能进入日常工作流的助手，不只是跑通一两次任务，还要做到：结果越来越稳；出错时能被发现；重要动作不会误执行；能在固定时间或固定条件下自动运行；后续出问题时，能继续迭代和回滚。

所以，还可以从下面两个方向继续优化。

**5.1 提升结果正确率**

刚跑出来的结果，多半不会一上来就完美，甚至离你心里的标准还有距离。关键动作是反复打磨配置档：每次发现产出不对，就和它沟通，把规则继续改细。

可以按这五点来做：

1. 把每次“不对劲”的具体症状记下来：漏关键案例、标题含糊、排版跑偏、顺序乱跳；
2. 回到配置档找对应条款，判断是没写、写虚了，还是写了却没被稳定执行；
3. 把条款改得更硬、更能验证，例如“标题要具体”改成“标题必须带正文关键词，禁止用‘其他有效观点’这类空泛说法”；
4. 拿原输入再测；
5. 一轮只修一处，确认好了再碰下一处。

拿音视频转写助手来演示：若转写稿总把“生财有术”听成“升财有数”，可在质量规范里加一条：清洗阶段必须纠正高频听写错误，例如“升财有数”应改为“生财有术”，“一仁”应改为“亦仁”。

若经常漏掉会议行动项，可以加：会议行动项必须单独列出，包含负责人、事项、截止时间；原文未写明的，标“未明确”。

若产出排版总变，可以加：固定为四段——会议摘要、关键结论、行动项、待确认问题；一级栏目不得自行增删。

配置档不可能一稿定型，它得在真实使用里慢慢长出来。每修掉一个错误，助手就离可靠更近一步。

**5.2 保障长期可靠**

基础配置完成后，你已经能手动发命令或消息让它执行任务。这说明它可以按你的指示，接管一部分工作了。

但要想让它真正融入日常流程，光靠手动喊它还不够。还得结合业务现场，补上这些设定：何时启动、资料从哪来、结果发往何处、出问题如何处理、哪些动作必须先经人同意。并非每个助手都要全配，但这些设置会决定它只是临时搭把手，还是能长期稳定干活的数字员工。

进阶能力不必一次配齐。若开局就追求自动唤起、自动读资料、自动判断、自动发布、自动复盘全都要，反而更容易翻车。更稳妥的路径是先跑通一条最小工作流，再按真实使用中的堵点逐项补齐。

可以考虑按这个顺序来：

1. 先稳定输入：明确它每次从哪里拿资料，比如飞书文档、多维表格、固定文件夹，还是你手动发给它；
2. 再稳定输出：明确结果写到哪里，比如飞书群、飞书文档、多维表格，还是本地文件；
3. 再加人工把关：如果它会对外发送、修改数据、触达客户，建议先加一道“确认后再执行”；
4. 再加故障告警与执行记录：保证它出错时你能知道，后续也能查到问题发生在哪一步；
5. 最后考虑自动唤起：等手动运行稳定后，再配置预约执行或事件触发，让它自动进入工作流。

要不要现在做进阶配置？可以先问自己几个问题：

• 这件事会不会反复出现？
• 资料来源是否固定在某个位置？
• 结果是否需要归档到固定位置？
• 失败时你是否需要马上知道？
• 它有没有误发、误删、误改的风险？
• 以后是否需要回看历史执行情况？
• 这套流程是否可能交给同事共用？

如果有两个以上回答“是”，就可以考虑补一项进阶配置。若你刚跑通第一个助手，可以先不急，手动运行两三次，从实际痛点里找需求。

举例来说：老忘运行，就先加预约执行；每次复制资料很麻烦，就先固定来源；结果散在聊天里不好找，就先固定落点；担心误发客户，就先加二次确认；经常不知道失败在哪，就先加执行记录和故障告警。

先让它稳定帮你完成一件事，再慢慢把它养成更可靠的数字员工。

**5.3 示范：日报助手的进阶设置**

假设你做了个“AI 日报整理助手”。初级玩法大概是：每天手动把资料丢给它，再说一句“帮我整理今天日报”。日报能出来，但发资料、发指令、复制结果仍得你来。

进阶配置后，可以逐步变成这样：
![](img/a6d1e8deaa12405da5541f9a1a2c293f.png)

升级后，它就不只会写日报，而是被放进一条可追踪、可检查、能长期运行的工作流里。

操作并不复杂：把下面这段内容贴进 Codex 的聊天窗口，按提示补齐信息、完成授权即可：
```
请帮我给当前这个 【你的Agent名字】 增加一个定时运行配置。

我的目标是：让这个 Agent 在固定时间自动执行一次任务，而不是每次都由我手动触发。

请你先检查当前 Agent 的配置，包括：
1. Agent 名称和 Profile 是否存在；
2. 当前任务的启动方式；
3. 是否已经接入飞书；
4. 是否有固定输入来源；
5. 是否有固定输出位置。

然后请你一步一步带我完成定时配置。

如果当前条件不足，请先告诉我缺什么，并给出最小补齐方案。
如果需要我提供信息，请一次只问我 1-3 个问题。
如果需要飞书授权、Hermes 配置或本地命令执行，请直接告诉我下一步要做什么。

我希望最终实现：
- 每天上午 9:00 自动运行一次；
- 运行后把结果发送到指定飞书群；
- 如果运行失败，要在 Codex 对话里说明失败原因；
- 如果能配置运行日志，请帮我记录每次运行时间、执行结果和输出链接。

注意：
不要直接覆盖我现有的 Agent 配置。
在修改前，请先说明你准备改哪些文件或配置项。
修改完成后，请帮我做一次手动测试，确认 Agent 仍然可以正常运行。
```

它一般会先检查当前状态，然后问你几个问题，比如：

• 这个助手现在叫什么名字？
• 你希望每天几点运行？
• 结果要发到哪个飞书群？
• 输入资料来自哪里？
• 失败后要通知谁？

如果你暂时不确定，可以先用最简参数：
```
Agent 名称：日报整理 Agent
运行时间：每天上午 9:00
输入来源：先使用手动测试材料
输出位置：发送到我指定的飞书群
失败提醒：先在 Codex 对话里提醒我
```

配置过程中，如果提示需要飞书授权，照着指引操作就行。

不建议一开始就开长期预约。更稳的顺序是：

1. 先让 Codex 手动唤起一次助手；
2. 检查结果是否正常生成；
3. 确认结果是否发到了正确位置；
4. 再让 Codex 开启预约配置；
5. 最后确认下一次自动运行时间。

你也可以继续发给 Codex：
```
请先不要开启长期定时任务。先帮我手动触发一次测试，确认输入、输出和飞书推送都正常。
测试通过后，再帮我开启每天上午 9:00 的定时运行。
```

当 Codex 处理完后，至少应看到三项结果：

• 助手仍然可以被手动唤起；
• Codex 已说明预约任务的运行时间；
• 飞书群里能收到一次测试输出或测试提醒。

三项都达成，才说明它已从“人喊它动”升级为“按时值守”。

做进阶配置不是把助手搞复杂，而是让它更安全、更稳、更贴近真实业务。所有能力不必一次加完，每次补一个最影响体验的配置就够。

### 02. 包装成果并对外展示

**1. 整理对外操作手册**

走到这里，助手基本能正常运转了。可一旦你希望同事共用、客户直接用，或把它包装成产品、服务出售，问题就来了：外部使用者未必清楚它的用途、用法和适用场景。

所以，还需要为它配一份操作手册。这份手册就像一个产品的使用指南，帮人快速看懂：

• 它擅长解决什么？
• 在哪些场景下最合适？
• 输入应该给什么？
• 最终会产出什么？

# 把智能体交给别人之前

上手时该留意什么？答案很简单：先备好操作手册。文档写清楚，哪怕换个人接手，也能迅速把智能体用起来。

一个智能体若想被反复使用、对外分享、顺利交付，仅仅能执行还不够；旁人要能看明白、跟着操作。按下列统一结构，交给 Codex 补全即可：

Markdown
```
请根据帮填写一下Agent使用说明书，要求其他人拿到说明书能清晰的知道该如何使用这个Agent

# 【Agent 名称】

## 它是什么
（一句话定位，比如&quot;这是一个内容初稿助手，把选题和素材变成可发布的公众号初稿&quot;）

## 省了什么人工
- 之前：怎么做，每次花多少时间
- 现在：Agent 怎么做，每次花多少时间
- 量化：原来 X 小时 → 现在 Y 分钟

## 用了什么工具
- Codex（负责什么）
- Hermes（负责什么）
- 飞书 CLI（负责什么）

## 输入

- 输入 1：（是什么 + 格式 + 从哪里获取）
- 输入 2：（如果有多个）

## 如何触发
（具体怎么让它开始干活：什么命令/什么时间/什么条件）

## 输出示例
（真实跑出来的输出截图或样例，不是效果图）

## 成功运行截图
（证明它最近真跑过的截图，带时间戳更好）

## 圈友怎么用
（一个陌生人看了这一段，能不能复现你的 Agent？）

## 注意事项
- 什么事情它做不了？
- 什么情况需要人工介入？
- 已知问题和后续改进方向
```

小D 操作手册示例，可拿来参照：

Markdown
```
# 音视频转录整理助手（小D）

## 它是什么
这是一个音视频转录整理Agent，把播客/视频/会议录音链接变成干净可读的飞书文档。

## 省了什么人工

1. **为智能体做一张展示网页**

落地载体并不唯一，业务场景不同，呈现方式也不同。比如：
- 聊天机器人（Bot）：接入飞书、微信、Slack、Discord 等平台，在对话中服务用户。
- 网页应用（Web App）：给出一个网址，任何人点开就能用。
- 企业内部工具：嵌入公司业务系统、OA 或工作流。
- API 服务：作为后台接口，供别的系统或应用调用。
- 桌面或移动应用：做成独立软件或 App；不同平台可承载机器人、网页应用、小组件等，也能组合使用。

本期采用 Bot 作为交付入口，但方法本身并不绑定这一形态。若某个系统可以读懂目标、安排步骤、使用工具、反馈进度并守住安全边界，那么搭建思路就能复用。差别通常出现在入口、触发器、上下文维护和风险控制细度上。

接着要做的是：让这个智能体拥有一个别人能打开的链接。先说明白，这个页面并不代表正式部署。若要让外部用户长期使用，一般还需要服务器、域名、运行环境，并持续承担模型接口（Token）等开销，同时处理稳定与安全问题。其他人调用时，这些成本照样会发生。

我们即将生成的链接，性质更接近一张智能体名片：展示它的介绍、本事和产出，方便转发。它不会实际执行智能体，访客也不能从页面直接调用，自然不占用你的 Token。

先做展示页的意义在于，让你提前体验智能体由“只有自己会用”过渡到“旁人也用得上”的阶段。许多人完成搭建后，只能在个人电脑或开发环境中运行。把公开链接发出去，对方无需配置环境即可试用。此时它不再只是演示样本，而开始接近产品。后续不管是团队共用、向客户交付 AI 流程、做成内部工具，还是发展为对外服务，都很难跳过这一环。

对这期航海多数成员而言，现阶段更要紧的是先让若干智能体稳定、持续地替自己分担任务，而不是一开始就投入较多成本做部署与维护。若能力和需求都已成熟，当然可以继续上线；上线后，别人才能在线实际使用，而不只是浏览展示页。这属于打通基础闭环后的进阶内容，不在本期学习范围内。

所以这一关不要求完成部署，而是先跨出产品化的第一步：让旁人了解你的智能体、明白它能处理什么。等出现真实业务需求，再根据情况判断是否上线，把它变成可长期运行、供他人使用的线上产品。

## 交作业前逐项核对

小D 的验收线共有 7 条，全部满足才算复刻成功。若你练的是音视频转录智能体（小D），交作业前请逐条对照：
1. 可以取得公开播客/视频地址。
2. 能抓取或下载音频。
3. 能跑完 ASR 转写。
4. 产出的是分享式整理稿，不是摘要。
5. 能创建飞书文档。
6. 文档权限能落到本人账号上。
7. 最终链接可打开，目录和格式都正常。

小D 常见失误，交前逐项排查：
1. 只搬了提示词，工具链没配齐：得到的只是一个“口吻像小D”的助手，实际下载、转写、建文档都做不了。关卡5要求安装好的 yt-dlp/whisper/lark-cli 不能缺。
2. 把提纯做成了摘要：输出是一串要点，而非可读的原文整理。回关卡4核对 Profile 里“不要写成核心要点/一句话总结”的要求。
3. 专有名词未修正：长音频中的人名、机构名容易被 ASR 听错。请在 Profile 中加入常见错词对照表。
4. 飞书权限链没走通：机器人虽然建了文档，本人却打不开，这属于交付失败。
5. 敏感凭据外泄：app secret、token、cookie 都不得出现在对话、文档或截图中。

### 04. 这一关的收尾

所谓跑闭环，是拿真实样例来证明：智能体并非只能演示一回，它还要经得起验收、修正和交付。

前五关里，你已经从体验演示走到正式搭建：明确岗位、拆解流程、编写 Profile、接入工具、连上飞书。到第 6 关，重心不再是继续堆功能，而是用真实输入多跑几轮，把“我认为可用”推到“旁人也看明白、能验收、可复用”。

四个关键动作：
1. 准备测试样例：至少三份真实或接近真实的输入，覆盖日常情况、边界情况和最在意的业务场景。
2. 留下运行痕迹：把输入、执行过程、输出结果和人工验收结论记下来，旁人能看出它最近确实在干活。
3. 做一轮校对与优化：按影响程度给问题排序，回到 Profile、工具链或流程规则中逐项处理，再用同一份样例复跑。
4. 归拢交付物：公开链接、成功运行截图、操作手册和测试记录都备好，让智能体由“跑得动”变成“交得出”。

至此，必修部分结束。你手里至少有一个能独立完成任务、走通闭环的智能体：岗位明确、流程完整、具备决策能力、工具齐备，也有可核验的交付材料。

后续选修关卡会再进一步：视线不只停留在一个智能体内部，而是把它放回真实业务，看输入从何处来、产出交给谁、值不值得同其他人员、工具或智能体衔接。

选修部分更开放，难度也更高。从下一关起，不再安排必交作业；你只需参照任务目标和说明，按步骤练手。若暂时没有自己的业务场景，也可以沿用默认案例，先吃透方法，再迁移到自己的业务中。

它更接近一份进阶指南，无需一口气做完。先挑与当前智能体最相关的内容完成，日后需求变化，再回来继续探索。

**1. 从智能体提炼 Skill 的操作说明**

一个智能体常常承担不少工作，但并非每个环节都要独立成一个智能体。有些能力本身就够独立、够通用，更适合抽成可反复调用的 Skill。可以从以下方向考虑：

比如，在【音视频转录助手】中，就可以单独拆出【转录稿清洗 Skill】。它的完整流程大致如下：

Plain Text
```
接收音视频链接；
下载音视频；
提取音频；
调用转录工具生成文字稿；
清洗转录稿里的错词、口癖和断句；
整理摘要、行动项和待确认问题；
写入飞书文档；
把结果链接发到飞书群。
```

整套智能体虽然完整、能做事，却未必适合直接转发。它可能依赖你的飞书空间、本地程序、账号权限、文件路径、业务资料以及固定输出位置……旁人拿到整套东西，不一定能顺利运行。

但其中有一项能力很适合单独抽出：对转录稿做清洗，再按既定结构归纳出摘要、行动项和待确认问题。它既不需要账号，也不依赖飞书空间，旁人只要有一份转录稿就能用，因而适合沉淀为 Skill。

从智能体里拆 Skill，可分三步：
1. 回看智能体流程，找出反复出现、价值较高、旁人也可能需要的那一小段能力。
2. 把它从整体流程中剥离，不要上传整套智能体；只留一个边界清楚的小能力：输入什么、处理什么、输出什么。
3. 写成旁人可复用的 Skill，讲清适合谁、解决什么问题、怎样使用、使用前后有何变化。

当然，不必自己苦想“哪个节点适合做成 Skill”。更省力的做法是：把智能体流程交给 AI，让它帮你拆节点、评估价值，并挑出最适合发布到 Skill Hub 的能力。

# 选修篇：从单打独斗的 Agent，走向协作团队与商业化服务

## 关卡 7：摸清上下游链路，再定要不要连

### 00. 本关任务卡

🎯任务目标：拿关卡 6 已验收通过的 Agent 当起点，把它的上游和下游都挖出来，弄清楚每个环节究竟是谁在干，然后判断眼下有没有哪段关系值得先接上。

🗒️任务内容

• 写明当前 Agent 收什么、干什么、交什么。
• 往前追：输入从哪儿冒出来，又是怎么钻进当前 Agent 的。
• 往后追：谁会接着用这个结果，还得再补哪些动作。
• 把每个环节的执行者分清楚：人、Agent、工具、固定流程，还是业务系统。
• 判断这些环节之间属于各自单干、共用资源、前后交接，还是先判断再分流。
• 要是有合适的关系，只挑一段进关卡 8；要是暂时没有，就把“本轮暂不连接”的理由写明白。

💡入门提示

从本关起就迈入选修篇了，这部分属于进阶内容，不再设必须提交的作业。你只要对照任务目标和任务内容，顺着步骤把练习走完就行。

这一关考的不是你能连上多少个 Agent，而是你的判断到不到位。

自己业务里眼下还没有稳定的交接点，那就照实写“本轮暂不连接”。别为了交差硬捏一个新 Agent 或者一段交接关系出来。默认案例照样能带你走完关卡 8。

![](img/9da1650ba3cec625186a5e1d93960497.png)

### 01. 本关要点

前六关下来，你已经把一个 Agent 单独干活的闭环给跑通了。

它现在门儿清：

• 自己该管哪摊事；
• 输入打哪儿来；
• 按什么路子干；
• 手头能调哪些工具；
• 最后交出什么；
• 碰上什么状况必须停下来喊人。

可现实里，一个 Agent 往往只扛整条链路中的一截。

它的输入是谁递过来的？干完之后成果又落到谁手里？前后还站着哪些角色？

关卡 7 要干的，就是把这个 Agent 塞回完整的工作全局里，看清它的来路和去向。

不妨先用下面这条线帮着理一理：

```
输入从哪里产生
→ 通过什么方式进入
→ Agent 完成处理
→ 结果保存在哪里
→ 谁继续使用
→ 哪一步需要人确认
```

这儿有两个常用说法：

• **上游**：给当前 Agent 喂输入的那段工作环节；
• **下游**：接着用当前 Agent 结果的那段工作环节。

先把整条工作链捋清楚，再琢磨要不要连。

![](img/ab1fe44b90a87adab6ec6708f5793d59.png)

### 02. 实操步骤

**1. 先看最终输出长什么样**

下面拿小 D 当例子，看看关卡 7 走完大致会得到什么。

```

```

小 D 交出来的东西：

• 飞书整理稿；
• 内容来源；
• 当前版本；
• 听不清或需要确认的内容。

智能纪要 Agent 接手之前，先把第一站检查做了：

• 文档能不能读；
• 材料是不是归当前任务管；
• 是不是最新版本；
• 待确认的内容有没有标清楚。

• 检查没过关的话，退回给小 D，或者交给人工处理，别让智能纪要 Agent 自己动手补。

哪一步需要人确认：

```
智能纪要 Agent 生成纪要
→ 按交接规则检查
├─ 普通纪要通过 → 归档
└─ 正式任务或高风险事项 → 人工确认
```

智能纪要 Agent 生成纪要之后，先按交接规则过一遍。普通纪要过关就能归档，用不着每次都得找人点头。

但要是需要落成正式任务，或者牵扯到承诺、金额、发布、权限这类事，那就得交给会议负责人或者指定的确认人再核一遍：

• 需要人工确认的结论或行动，到底准不准。

动手之前，先把信息分成四档：

- 哪些是已经拍板的定论，哪些还停在商量阶段；
- 哪些动作已经真正生效；
- 责任人与交付期限有没有填对；
- 是否牵涉钱款、对外许诺、公开发布、操作权限，或者其他需要有人担责的事项。

凡是需要人来把关的分支，确认完毕之后，才可以排进正式任务，或流入其他后续系统。

下面只是一份完成样例，不必照抄，请按你自己的 Agent 和真实业务来填。

**2.** 以飞书 AI 录音豆为例**

前六关一路打磨出来的小 D，和飞书 AI 录音豆的内核是不是颇为相近？

声音来源可能是手机、电脑、录音硬件，也可能来自飞书会议或飞书妙记。小 D 接住这些音视频，先转录、再整理，最后交出一份可以直接接着用的飞书文档。

```

→ 小D转录和整理
→ 飞书整理稿
```

录音豆录完之后，还会顺带产出智能纪要，下文就简称“录音豆”。

系统预设的纪要样式足以应付常见需求，却未必符合每个人干活时的习惯。场景不同，关注点自然也不一样：

- 会议刚散场，更在意议题、结论、待定行动、责任人和时间；
- 课程听下来，更想拿到知识点、案例、方法以及练习建议；
- 线下分享参加完，更关注核心观点、实例和之后还能复用的内容。

前六关的小 D 管的是把音视频做成可用文稿。顺着往下，还可以再安排一个 Agent 按照你的要求生成智能纪要。为方便练习，这个承担纪要工作的 Agent，我们称它为“智能纪要 Agent”。

![](img/de4a1d90c95827646f276c1a2f885776.png)

上面那张图圈出的，是需要落成正式结论或行动的分支；普通纪要只要验收合格，直接归档即可。

在使用者看来，整个过程是连贯的。拆开来瞧，小 D 与智能纪要 Agent 各自承担一段：上一棒的产出，正好是下一棒的原料。

考虑到第一次交接要便于核对，关卡 8 的默认跟做案例会再收窄范围，仅采用会议材料。至于课程、线下分享这类场景，等基础交接跑顺了，再改 Profile 也不迟。

**3.** 为自己的 Agent 理清上下游**

请先翻出这几份材料：

- 关卡 2 的岗位卡；
- 关卡 3 的工作流；
- 关卡 4 的 Profile；
- 关卡 6 的测试记录与使用说明书。

试着用一句话概括它：
它接收【输入】，承担【主要工作】，交出【结果】。

**3.1** 先往上游追：输入从哪来**

依次回答：

1. 这份输入最初诞生在何处？
1. 眼下由谁把它递到 Agent 手上？
1. 它经由什么入口进来：飞书群、文档、表格、邮箱、文件夹，还是别的通道？
1. 处理何时启动：有人手动提交、按计划定时跑，还是新消息一到就被唤起？
1. 递交之前，是否需要先做筛选、确认或授权？
1. 万一输入缺了、过期了或重复了，该由谁收拾？

1. 一条 Agent 工作链里都有什么**

完整的 Agent 工作链，主角并不只有 Agent。

输入得先进系统，任务得有人触发；某些情况下，还得先判定任务属于哪一类，再分派给对应的 Agent。

干活时它会调用工具，收工后把成果写进文档、表格或业务系统，其中关键的部分再送到人手里复核。

建议从以下七处逐一排查：

![](img/1b417240e297d5c16863dcf3b97ec63c.png)

**4.1 人的位置**

授权、核实事实、扛业务责任，这些都由人来做。

例如：

- 核对纪要准不准；
- 拍板哪些行动算真正生效；
- 确认责任人与交付期限；
- 审核钱款、对客户的许诺、公开发布以及敏感信息。

**4.2 Agent**

Agent 承担的是一段相对完整的工作：读懂上下文、做出判断，最后交出可被检验的成果。

三个问题可以帮忙界定：

1. 这算不算一段完整的工作？
1. 过程中需不需要结合上下文来判断？
1. 完成后有没有独立的成果可供核查？

4.3 工具、Skill、MCP 或 API**

这类能力用来帮 Agent 落成一个具体动作。

例如：

- 把音视频下载下来；
- 转换文件格式；
- 做语音识别；
- 读取或新建飞书文档；
- 查询表格或外部数据；
- 发出消息。

工具由 Agent 来调用，但工具自身未必是 Agent。

**4.4 固定流程**

当规则足够清晰，只剩下触发、转发、按点执行或改字段这些动作时，交给机器人、脚本或工作流即可。

例如：

- 收到固定格式的消息就转发出去；
- 每天到点自动开工；
- 把结果写进指定字段；
- 按规则推送提醒。

**4.5 业务系统或内容来源**

这一类环节，负责把内容生产出来、存下来或者托住。

例如：

- 飞书会议；
- 飞书妙记；
- 飞书文档；
- 文件夹；
- 邮箱；
- 多维表格；
- CRM；
- 项目管理系统。

架构师要做的，并不是把每个步骤都改造成 Agent，而是想清楚每一步交给谁最合适。

5. 判断这些环节之间是什么关系**

上下游摸清之后，接着要分辨它们彼此的关系。

![](img/939ab9f16adf06668eeee8d90e20b639.png)

**5.1 各干各的活**

两个 Agent 面对的是不同类别的任务，各交各的成果，彼此之间无需连线。

```
音视频
→ 音视频整理 Agent

其他类型内容
→ 对应 Agent
```

**5.2 共用同一批工具、资料或系统**

两个 Agent 也许读同一份知识库、待在同一个飞书空间，或调用同一套工具，但它们之间并不互传结果。

资源共享，并不等于上下游关系。

**5.3 一棒接一棒**

如果上游 Agent 的产出经常被下游 Agent 当作原料，且先后次序稳定，那就适合把交接建起来。

```
小D
→ 智能纪要 Agent
```

挑选时逐条核对：

1. 这样的交接发生得频繁吗？
1. 上游那边有没有清晰的交付物？
1. 下游这边知不知道该怎么验收？
1. 连起来之后，能否少掉复制、等待和反复说明？
1. 一旦出岔子，能不能判断该退回哪一端？
1. 哪一步需要人来把关，是否心中有数？
1. 两个 Agent 是否都能独立运行？

**5.4 先判定类型，再分流派活**

当同一个入口涌进各种类型的任务时，可以先辨认类型，再分派给对口的 Agent。

```
收到任务
→ 判断任务类型
├─ 类型 A → Agent A
└─ 类型 B → Agent B
```

关卡 8 只练最朴素的前后衔接。分流、自动触发、写入业务系统这些，等基础交接跑通了再往外扩。

6. 给出这一轮的判断**

前面的梳理做完，就该下这一轮的结论了。

![](img/223d440aa081558357b9f1d473edac8d.png)

**6.1 这一轮决定连接**

若存在合适的关系，就挑一段 Agent 之间的前后衔接。

写清六件事：

- 上游是谁；
- 下游是谁；
- 上游交出来的是什么；
- 下游如何验收；
- 验收没过时退回到哪一方；
- 哪一步必须由人拍板。

关卡 8 先做第一次验证，把交接规则跑通；确认没问题，再谈稳定运行。

**6.2 这一轮先不连**

碰到下面这些情形，可以判为“暂不连接”：

- 交接本身很少出现；
- 输入与结果都还没定型；
- 权限与责任尚未讲清；
- 后续工作交给人做更合适；
- 两个环节只是共享资料，并非一前一后；
- 连起来之后的维护开销，比省下的时间还大。

写清四件事：

- 已经找到的上游与下游；
- 暂不连接的理由；
- 接下来打算继续观察或补齐什么；
- 哪些条件具备后可以重新评估。

判定“暂不连接”，同样是一种有效的架构结论。

**6.3 用默认案例往下走**

已经挑好关系的，就带着自己的场景进入关卡 8。

若这一轮判为暂不连接，或手头还没有第二个 Agent，就跟着默认案例继续练：

```
小 D
→ 智能纪要 Agent
```

普通纪要检验合格即可归档；一旦要落成正式任务，或触及高风险事项，就得请人来确认。

## 关卡 8：让两个 Agent 在飞书群里接力一次，全程可追溯

### 00. 任务卡**

**🎯 目标**

让分别代表两个 Agent 的飞书机器人，在同一个群内真正跑完一回自动接力，并把交付、接收、处理、验收的痕迹都留下来。万一中途卡住，你能定位到是哪一环，并判断该退回、叫停，还是转交人工。

**🗒️ 任务说明**

- 沿用关卡 7 选中的那段固定接力；暂时没有合适关系的，就跟着做“音视频转录 Agent → 智能纪要 Agent”。
- 给上下游各配一个飞书应用机器人和一个 Hermes Profile，并把两个机器人都拉进同一个测试群。
- 先各自单独测一遍，再由你手动@下游机器人，确认材料、权限与处理规则都没问题。
- 人工转交跑通之后，再让上游机器人发出完整交付，并真正@下游机器人接棒。
- 下游 Agent 先验收收到的材料，合格才继续处理；不合格就写明原因并退回。
- 每个步骤都留下任务编号、消息、结果链接、待确认事项与当前状态。
- 第一次自动接力结束后，用 Codex 检查权限、交付格式、触发结果和异常处理方式。

![](img/46e07fa9fb748c837acc5e0f5958c3d4.png)

**💡 新手提示**

头一回跑，别一上来就盯着“全自动”。先确认这几件事：

- 两个机器人单打独斗都没问题；
- 上游交出的结果，下游确实打得开；
- 人工转交时，下游能准确接住；
- 自动转交用的是真正的飞书@，而非消息里的一串普通文字；
- 自动触发失败时流程会停住，不会没完没了地重试。

![](img/99afa12306234fa0ad9748446f5598bb.png)

### 01. 本关聚焦**

关卡 7 已经替你回答了两个问题：

哪两个 Agent 之间有稳定的先后关系？哪一段最值得优先接起来？

关卡 8 要落地的，是让它们在飞书群里先走一遍人工接力，再跑通一次自动接力，整个过程都要留下能回看的痕迹。

不妨把这条接力看作两道相连的工序：

```
人先启动上游 Agent
→ 上游 Agent 完成工作并交付结果
→ 上游机器人真正 @下游机器人
→ 下游 Agent 检查并接手
→ 完成下一段工作
→ 输出最终结果
```

每一环都得留下三笔账：

1. **收到什么**
1. **做了什么**
1. **交付什么**

等到最终结果出了岔子，就顺着记录往回倒查：

```
最终结果
→ 下游 Agent 使用了什么材料
→ 下游接收时是否发现问题
→ 上游 Agent 当时交付了什么
→ 原始材料是否完整
```

这样便能分清，毛病是出在原始材料、上游整理、交接环节、下游处理，还是落在需要人来定夺的业务事项上。

1. 为何要放在同一个飞书群**

一个飞书群，能同时担起三重角色：

- **作业现场**：两个 Agent 在同一处领任务、交成果；
- **交接入口**：上一棒跑完，用@把下一棒叫醒；
- **过程档案**：每一步的消息、链接、验收结论都留得下来。

![](img/f401d9a4715f5216f793db1acbffe9e3.png)

默认案例要走的路径是这样：

```
会议材料进入飞书群
→ 人工 @音视频转录 Agent
→ 音视频转录 Agent 完成转录和整理并发布飞书文档
→ 音视频转录 Agent 发送完整交付消息
→ 音视频转录 Agent 真正 @智能纪要助手
→ 智能纪要 Agent 检查材料
→ 检查通过后生成纪要
→ 普通结果归档
→ 需要承担业务责任时 @确认人
```

2. 一回完整的接力，至少要有哪些动作**

至少得走完这几步：

1. 两个机器人各自通过人工@测试；
1. 上游 Agent 接收真实材料并处理完毕；
1. 由人把上游结果转给下游，确认材料与权限可用；
1. 上游 Agent 发出完整交付消息，并真正@下游机器人；
1. 下游 Agent 先做接收检查；
1. 检查放行后再继续下游处理；
1. 留下最终结果与检查结论；
1. 按实际情况收尾：完成、退回、暂停或转人工。

1. Codex 在本关负责什么**

Codex 主要用来搭建与调试：

- 帮你创建或调整两个飞书机器人与 Hermes Profile；
- 检查两个 Agent 的职责划分是否清楚；
- 检查机器人接收其他机器人消息所需的权限与配置；
- 帮你把交付消息的格式固定下来；
- 帮你生成真正的飞书@，而非普通文字；
- 帮你查看第一次运行留下的证据；
- 帮你判断问题出在哪个环节；
- 帮你修改 Profile、检查规则与触发规则；
- 协助配置并测试 Agent 自动@下一位的接力方式。

接力日常跑顺之后，普通任务就在群里直接流转。碰上异常、规则调整，或者流程需要升级，再回头找 Codex。

```

6.2 何时可转为日常做法

首次自动交接通过后，再做几轮稳定性测试。满足以下条件，才可日常化：

• 上游角色连续几次输出结构一致的交付消息；

• 下游角色能稳定读取上游结果；

• 下游角色能明确回复接收通过或退回；

• 没有重复点名与循环触发；

• 权限和结果链接保持稳定；

• 异常时能暂停并通知人。

在做稳定性测试以前，接力记录里如果要留状态，只能说“自动接力首次验证通过”，不能用“已经稳定运行”这种说法。

![](img/a816b6b95f76cb9d1a78da331ae58c37.png)

6.3 Codex 该在什么时机介入

普通日常任务，完全没必要每单都过一遍 Codex。一旦遇到以下几种情境，再让 Codex 上场：

- 上游机器人已经真正 @ 了下游机器人，但下游没有被唤起；
- 同样的任务被重复执行；
- 交付的格式变了，下游读不了；
- 看不出故障到底在哪一环；
- 要动 Hermes Profile；
- 想再加一条检查规则；
- 接力的环节变多了，准备引入脚本或工作流工具来管。

**6.4 哪些节点必须由人来介入**

出现下面这些情况，必须拿给人确认：

- 规则给不出明确结论；
- 事实层面有争议；
- 要定正式任务、负责人或截止日期；
- 跟金额、报价或客户承诺挂钩；
- 计划对外正式发布；
- 碰到敏感数据或权限问题；
- 同一步已经连续失败；
- Agent 的产出有可能引发实际业务责任。

![](img/f3906eae41c2a37383d18985ef131013.png)

### 04. 进阶演练与拓展

1. 稳定性测试要怎么做

第一次自动接力跑通之后，可以再做这些事：

- 连续跑三轮；
- 至少换两种不同的材料；
- 穿插一次可控制的问题；
- 每一次都要由上游机器人实打实 @ 下游机器人；
- 看有没有重复触发或循环点名；
- 看下游能不能正确退回；
- 看高风险事项会不会暂停并知会到人；
- 判断这套接力链路适不适合复用为日常流程。

每次测试都换新的任务编号，并在测试群里发：

Plain Text

```
@音视频转录 Agent

请执行第【X】次稳定性测试。

任务编号：STABLE-【X】
材料版本：v1
材料链接：……
本轮类型：正常运行 / 重复 handoff_id / 无权限链接 / 材料缺失
本轮要求：按已经验收的规则完成；遇到停止条件时不要猜测，也不要触发下一步。

请在完成后留下本轮 handoff_id、交付消息、下游处理结果和最终状态。
```

具体怎么操作，记录模板长什么样，直接去实操工具包里拿。

2. 从一份智能纪要，到专属智能伙伴

这一关，我们用会议材料把第一条接力跑通了：

Plain Text

```
小 D 整理会议材料
→ 智能纪要 Agent 接收并检查
→ 按当前场景生成结果
```

这条接力链路并不限定于某一种会议。小 D 还能接着管音视频、飞书妙记或者已有的整理稿；智能纪要 Agent 则可以按不同场景调整整理的方式：

- 项目复盘会：把结论、问题、根因、风险和行动项理出来；
- 客户访谈：提炼需求、原话、异议、机会和后续跟进；
- 销售沟通：记下客户答应的、我们答应的，以及还没敲定的条件；
- 课程分享：归拢知识点、案例、学员提问和课后练习；
- 周例会：梳理本周进展、现阶段的卡点和下周规划。

所以，第一版智能纪要 Agent 完全不必固定成一种格式，也不需要非得用飞书官方纪要模板不可。先把一种场景跑扎实，再逐步增加第二种处理规则；同一个智能纪要助手，就会慢慢适应各种会议和业务。

再往前跨一步，就是飞书早已开放给用户的官方智能伙伴。它能按你的权限范围，调用飞书里的消息、文档、会议、日历和任务，帮你梳理工作进度、总结待办，还能回答和当前工作相关的问题。

![](img/d08c0bd81cce17cca7c41891eadf00e6.png)

飞书 aily 怎么进

官方智能伙伴确实能开箱即用，但它终究是飞书的一款标准化产品；用的时候会消耗飞书 AI 额度，遇到复杂任务还可能产生模型与工具调用的额外支出。

过了这一关，你就开始拥有另一种选项。你已经能把一项工作拆成这些部分：

Plain Text

```
从哪里取得信息
→ 哪个 Agent 负责整理
→ 哪个 Agent 负责继续处理
→ 怎样检查结果
→ 哪些事情必须交给人
```

照着这个方法，你也能拼出属于自己的智能伙伴。比如：

Plain Text

```
我的项目伙伴
= 群聊和会议整理
+ 项目进度汇总
+ 风险检查
+ 每日待办
```

Plain Text

```
我的客户跟进伙伴
= 客户沟通整理
+ 需求与异议提取
+ 跟进事项生成
+ 到期提醒
```

Plain Text

```
我的航海伙伴
= 学习记录整理
+ 每日进度总结
+ 卡点检查
+ 下一步行动
```

它不一定非得是那种什么都能做的超级 Agent。同一个入口背后，完全可以安排几个 Agent 各负责一段工作。用哪些模型、工具和资料，由你自己决定；结果存在哪里、哪些步骤要人工确认，也由你说了算，这样一来调用成本的管理也更透明。

自己搭也不等于零成本，模型和工具依然可能产生费用。真正的转变在于：你知道钱消耗在什么地方、信息源于哪里、每个 Agent 承担什么职责，以及结果出问题时该查哪一环。

从直接用飞书现成的智能伙伴，到能拆解并组装出自己的智能伙伴，这正是 Agent 架构师继续前进的下一步。

![](img/0caaf6955980ee20f7702d6eed8f9d0b.png)

### 05. 本关常见的卡点

遇到问题先不用急着放弃，完全可以先问问 AI。这期最推荐优先用 Codex 或 WorkBuddy，把报错信息、截图或者你的需求，另开一个任务窗口发给它们，让 AI 帮你诊断原因、排查故障，甚至直接就把问题解决了。

![](img/d5014ad0a30a423df9a24126962d5737.png)

慢慢形成“先问 AI、再找人帮忙”的习惯，很多问题都会迎刃而解。

![](img/ae8a0c94c99ca2028aee7fd2c132a899.png)

### 06. 本关回顾与小结

这一关，你在两个 Agent 之间完成了一次真实的自动接力：

1. 两个机器人放在同一个飞书群里，分别进行测试；
2. 先用人工 @ 的方式，把接力测试完整跑一遍；
3. 上游 Agent 搞定任务，同时留下完整交付成果；
4. 上游机器人真正 @ 了它的下游；
5. 下游 Agent 先做第一站检查；
6. 检查通过后，继续下一段加工；
7. 最终结果还要过第二站检查，并注明保存在哪里；
8. 有异常时，能定位到对应环节，然后退回、暂停或转交给人工。

第 7 关帮你看清楚哪段关系值得连接；第 8 关让这段关系真正运转起来，每一步都有产出、有检查、有记录。

## 关卡 9：把 Agent 做成企业服务来变现（选修）

### 00. 任务卡

**🎯 这关的交付目标：** 让已经跑通的 Agent，变成一份边界清楚、可试点的企业 AI 服务方案。

**🗒️ 具体任务：**

- 从一个已经跑通的 Agent 出发，选定一个清晰的企业 AI 智能体业务场景；
- 不从工具功能讲起，而是先写清楚客户到底痛在哪里、需要什么；
- 把 AI 智能体项目的落地交付方案、客户流量来源、风险规避措施都摸清楚。

这一页企业 AI 智能体服务落地方案，得能回答出以下几件事：

- 正在接触的客户，他们最实际的痛点是什么？
- 怎么借助场景实操提示词，一步步把客户需求理顺？
- 客户规模不一样，AI 智能体交付方案该怎么做差异化设计？
- 我的 AI 智能体客户，未来从哪里开拓？
- 做这类 AI 智能体项目，会遇到哪些风险？又该怎么躲开？

**💡 新手注意：**

这一关属于选修拓展，不纳入必修最终成果，你可以自己练，不需要交作业。

写企业服务方案，别写“我会做 Agent”，要写“我能帮这个业务问题把试点跑通到哪种程度”。先拿一个能验收的小试点去谈，别一上来就承诺全公司智能化。

请把这句话刻进脑子里：

**企业真正愿意掏钱的，从来不是那个叫“AI Agent”的技术产品，而是一个以前做不快、做不好、成本太高或者根本跑不通的业务问题，终于被重新跑通了。**

![](img/aa832422feee80ff5e7aab43ffc74151.png)

### 01. 识别客户痛点，找到变现路径

只有先搞清楚钱从哪来，你才知道该往哪个方向使劲。

1. 企业级 AI 智能体咨询

痛点场景：老板想用 AI 智能体成事，却不知从何下手。

交付上通常有两种做法：

第一种：线上咨询

线上咨询的重点是听清老板的具体诉求，然后给出对症的解决思路；最好能直接回应老板心里最惦记的几个问题：

💡 第一，业务盘完了一遍后，当前究竟该不该用 AI 智能体来改进？
第二，真要做，是直接套用现成工具（选哪一款），还是自己开发？
第三，同行是怎么推进的？投入了多少？走的是哪条路？最后效果如何？

第二种：线下沟通

线下咨询要讲的东西和线上差不太多，但好处是信息量更大、能对接到的资源也更多。想靠一次见面就让老板认可你，进而愿意采购你公司的 AI 智能体服务，下面这些内容必须备好：

💡 第一，客户所在行业在 AI 智能体进来前后的明显差别：效率是否提高了？成本是否降低了？盈利是否增强了？资源是否变多了？
第二，能够在线下见你，说明老板多半已经对市面上的通用工具有过一轮了解。你至少要准备几个能现场操作的标准化工具，比如 WorkBuddy、Codex、企业垂直赛道智能体。不要只做一个，因为要留出选择余地；可也别做太多，不然和没做没什么两样。
第三，得拿出同行案例，具体到投入成本、建设周期、最终效果；同时把你公司成套的解决方案、准备怎么落地也讲清楚。

这些内容不能只靠口头讲，得放进 PPT 里，最差也要有文档；凡是涉及实操的部分，最好再配一段工具演示或视频。

目的只有一个：让客户看出你够专业，同时留好后续的钩子。比如：

💡 “老板，您刚才看了这么多内容，不如先安排一次全公司的企业培训。将来不管高管还是基层，总得先明白 AI 智能体是怎么回事、怎么用起来，后面的事情才好推。”——这句话抓住的是“老板自己不用干活，干活的是下面人”的特点，先把 AI 企业培训服务推出去。

“老板，您看，不管是买现成工具还是自己开发，成本都得先算清楚，效果也得提前预估。要不我们安排一次深度的售前交流或者轻咨询，我把所有细节摊开讲一遍，您再决定选哪套方案。”——这句话对应的是老板“想知道又不愿多花钱”的心态，可以同时推荐 AI 企业咨询服务和轻量化产品。

“老板，您的同行 XX 已经动手布局 AI 智能体了，他们在 XX 场景已经跑出效果。我建议咱们也先找一两个场景做测试，看看值不值得继续把资源放大。”——这句话针对的是“想做但怕亏钱”的心理，先拿下一两个场景的小合同，再接后面的大单。

2. 企业级 AI 智能体培训

痛点场景：员工不太会配置和使用 AI 智能体，一实操就卡住。

交付变现可以分三类：

💡 第一种，标准课：核心是给企业做普及和输入，适合那些基本没碰过 AI 智能体、正在早期探索、打算把一部分工作换成 AI 智能体来做的企业。

第二种，标准课加部分定制：在普及基础的同时，还要结合企业自己的产品和服务来展开。关键是定制部分，因为员工最在意的是“这跟我手头的活有什么关系”。

第三种，近乎全定制：培训要完全贴着企业的实际业务流程走。这种企业的老板已经有了认知，不需要再扫盲，他要的是培训后马上有变化：效率提高（能多接项目、多带客户）、项目收入增长（直接落到员工业绩上）。

想干这一行，至少要满足两个条件：

💡 一是得有打磨课程的功夫，并且经过多次线上或线下 AI 智能体企业培训的历练，标准课说讲就能讲。

二是真懂业务需求。你要熟悉企业的产品和经营活动，最好是在某个垂直行业里扎下去，比如电商、教培、工业自动化。这样才能构建护城河，做“AI 智能体垂直领域”的培训或者产品定制开发。

3. AI 智能体联合研发或项目外包

痛点场景：老板心里有想法、手上也有建设方案，就是缺一个牵头的人。

这里面还能再分出几种情况，每一种都有成交的可能：

💡 第一种：客户知道自己要什么方案，但预算有限，只能先覆盖一部分场景；想再往深做，就可能要找其他公司联合研发，成果两边共享。

第二种：客户方案清楚、预算也充足，只是自己人手排不过来，于是选择把项目外包。但这个外包不能只做交付，要带着客户公司的骨干一起参与；项目做完了，骨干也练出来了，以后的 AI 智能体需求才有继续合作的机会。

第三种：客户方案清楚，但需求很分散，得用好几种手段拼到一起：插件和 Skill 要自己开发，工具可以借用成熟大平台，场景和数据要跟现有系统打通。这样的项目必须靠综合落地方案来收口。

![](img/9e8226a4673af1b84bafd3546d7fdbff.png)

### 02. 场景实操与需求梳理

想梳理 B 端企业的需求，照样可以先让 AI 智能体帮一把；再不济，用 AI 大模型也能顶一下。

1. 场景一：老板想用 AI 智能体做事情，但不知从何入手

把下面这段【企业 AI 智能体业务诊断顾问】提示词发给 AI，让它陪你对一轮话。

**对话结束后，你会拿到一份企业 AI 智能体建设方案，里面会写清楚优先场景、实施路径和试点建议。**

Plain Text

```
你是一名具有企业管理咨询、业务流程梳理、AI智能体规划和数字化转型经验的高级顾问。现在需要帮助一家企业判断应该从哪些业务场景开始建设AI智能体。

请不要直接推荐工具，也不要一开始就设计复杂系统。请先通过提问方式完成需求诊断，每次只提出3—5个最关键的问题，并根据我的回答继续追问，直到能够形成初步方案。

你需要重点了解以下内容：

1、企业所在行业、主营产品、客户类型和团队规模；
2、老板最希望改善的经营目标，是降本、增效、增收、获客、提升服务还是降低风险；
3、当前最耗时间、最依赖人工、最容易出错的业务流程；
4、每项工作的发生频率、参与人数、单次耗时和当前成本；
5、输入资料来自哪里，包括文档、表格、聊天记录、CRM、ERP或其他系统；
6、数据是否完整、是否涉及客户隐私、商业秘密或敏感信息；
7、出错会造成什么损失，是否可以设置人工审核；
8、企业目前使用了哪些AI工具、软件系统和自动化工具；
9、客户希望在多长时间内看到效果，大概可接受的预算范围；
10、谁负责推动项目，哪些部门需要参与。

完成诊断后，请输出：

1、企业当前AI应用成熟度判断；
2、最值得优先验证的5个AI智能体场景；
3、每个场景的业务痛点、输入、处理流程、输出和人工审核节点；
4、按照价值、难度、数据基础和风险进行评分；
5、推荐的第一期试点场景；
6、适合采用成熟工具、低代码平台还是定制开发；
7、预计实施周期、人员投入和预算区间；
8、试点验收指标；
9、客户需要提前准备的资料；
10、本期不建议开展的高风险场景。

要求方案务实、具体，避免“提升效率、赋能业务”等空泛表述。每个建议都要说明为什么值得做、怎样落地、怎样验证。
```

这里得特别提醒一句💡：提示词只能用来快速搭框架，没法替代真正的客户访谈。

客户在第一次接触时讲出来的话，常常不等于完整需求。比如说客户来一句：“我们想搞个商机分析系统，自动分析微信聊天里的客户需求。”这句话可没法直接丢给开发，必须先做一轮追问：

💡
1. 这里的“客户”指谁？他们有统一的客户档案吗？
2. 聊天记录从哪来？拿到授权了吗？
3. 企业销售的是什么产品？产品资料齐不齐？
4. 怎么判断一句话是高意向信号？
5. 销售看到信号之后，下一步该干什么？
6. 售前和售后各自有什么标准作业流程？
7. AI 只负责提建议，还是可以直接自动发消息？
8. 哪些操作一定得等销售点头？

拆到这里，第一版的项目定义大概就长这样：

💡
1. 每天读合规拿到的聊天记录，再结合 CRM 里的客户档案、产品知识库和销售 SOP，整理出高意向客户名单、判断依据、客户需求摘要以及建议跟进的行动；等销售确认后，才允许联系客户。
2. 到了这个层面，输入内容、知识库、智能体的动作、输出结果以及人工节点才算基本清楚，项目周期、费用和验收方法也才能估得出来。
3. 另外要小心：客户要是提出绕开平台规则、控制没授权的个人号、批量群发营销信息，或者处理没授权数据，你必须直接拒绝，或者把方案改成符合平台和相关法律要求的做法。

做培训的时候，别只演示“帮我整理一份会议纪要”这种单点操作，得把一套完整流程设计出来：

💡
第一步：员工先输入客户的基本信息、拜访录音转好的文字，以及这次拜访要达成的目标。
第二步：AI 来提取客户目前的问题、采购意向、预算线索、决策链、竞争对手和风险点。
第三步：AI 按照企业 CRM 里的字段，生成一条标准记录。
第四步：AI 参照销售 SOP，给出接下来的行动建议。
第五步：销售人工核对这些事实是否准确，确认无误后，再写回公司的 CRM 系统。

这个案例的意义，不在于“纪要写得更漂亮”，而在于帮企业沉淀出一套统一的客户信息记录标准，把销售管理的质量提上去。

培训结束后，还能把它升级成真正的系统：自动读取合规取得的会议记录，生成结构化客户信息，再推送给销售做确认。

# 动工之前，四张底表先对清

动工之前，团队最好把四张底表逐一过筛；若能把甲方也拉到同一张桌上敲定，后面会顺很多。不少交付拖到后期，问题往往不在技术，而在于信息没摊开、责任没落人。

1. **场景盘点单**：场景名称、使用部门、当前痛点、发生频次、单次耗时、输入材料、输出成果、风险级别、预期收益，逐项记全。
2. **接口对接单**：涉及系统、交换的数据、对接方式、归口负责人、权限要求、测试环境、计划开放时间，都要落到纸面。
3. **资料登记单**：资料名、来源部门、格式、数量、更新时间、密级、保管人，以及能否用于模型，一并登记。
4. **人员分工单**：甲方项目、业务、技术、数据、验收负责人，加上服务商对应角色，全部明确到具体人选。

这四张底表若有缺项，执行阶段很容易碰上资料交不齐、接口开不了、需求来回改，进度自然被拖慢。

### 03. 交付路径怎么排，知识底座怎么垒

企业规模不同，交付思路不能一把尺子量到底。下面分通用和定向两条线来讲。

**通用路线：多数项目可先试“代理＋资料库＋流程自动化＋人工卡点”**

先提醒一句：这只是可尝试的组合，不匹配就别硬套。

- 代理：接住任务、读懂意图、调用外部能力，最后把结果交出来。
- 资料库：沉淀客户信息、产品信息、制度文件、操作流程、历史案例等上下文。
- 流程自动化：负责按时触发、发提醒、推任务、存档结果。
- 人工卡点：盯高风险内容、接异常情况，并做最终拍板。

人工卡点不是系统不聪明的遮羞布。放到企业场景里，人机配合通常比一味追无人化更稳、更安全，验收时也更容易过关。

搭资料库之前，建议先清点三类材料：

1. CRM与客户档案：能回答谁在买、客户长什么样、过往聊过什么、现在推进到哪一步。
2. SKU与产品资料：能回答企业卖什么、规格价格如何、适用边界和限制在哪里。
3. SOP与流程标准：能回答员工按什么顺序做事、做到什么程度算合格、哪些情形必须上报升级。

这三类材料如果都残缺，就不要幻想“接上大模型就万事大吉”。更靠谱的做法是先做一个最小可用资料库。

最小可用资料库，不是把公司所有文件一股脑塞进去，而是紧贴首个试点场景，只整理真正用得上的内容。业务和销售根本不看的材料，先别放，放了也是白耗人力。比如做客服问答，第一期只收产品说明、高频问题、售后政策、退款规则、转人工条件即可，其余内容后续再补。

**大型企业：环节多、链条长，必须拆阶段推进**

这类客户往往组织层级多、系统数量大、数据敏感、权限管控严、决策链长。直白说，国企央企的流程可能很长，项目容易堵在审批上，交付和尾款回收都可能受影响。

阶段1：做企业级诊断。访谈对象不能只有老板，还要覆盖业务线、信息科技、数据、安全合规以及一线使用者。顺序上先把老板的共识拿到手，领导发话后，下面配合度才会高。

阶段2：建场景池并排优先级。大企业一口气提几十个场景并不稀奇，需要按业务价值、实施难度、数据基础、风险大小、可复制性来打分，优先挑使用频率最高的先做。

阶段3：补统一基础能力。包括模型接入、资料库、权限认证、日志审计、智能体编排、运营看板等。这里尽量选成熟产品，别把时间花在重复造轮子上。

阶段4：找一个部门试跑。预算再充裕，也不建议第一期全公司铺开。选一个部门、一个场景、一组真实用户连续用一段时间；小闭环先让领导看到效果，二期才有说服力。

阶段5：做安全与稳定测试。正常输入、缺失输入、异常输入、越权访问、敏感信息、网络中断、接口失败、模型不可用、并发压力，都要覆盖。最终好不好，客户方使用者说了算，得让他们觉得顺手。

阶段6：挑典型场景复制。试点稳住后，再把标准化能力往其他部门推，同时给不同业务线留个性化配置空间。一个场景跑通了，复制才容易，老板也更容易认可这种可复制的成果。

大型企业项目常见的交付清单包括：总体规划、业务场景地图、技术架构、数据架构、资料库标准、安全方案、试点系统、测试报告、培训材料、运营制度、推广计划等。

**中型企业：成熟平台加场景定制，求快、求稳、求可见**

中型企业通常有一定业务基础和数字化系统，但预算、技术团队、管理能力都有限。一开始就上复杂平台并不合适，更稳妥的是成熟平台加场景定制。说得直白点：有钱，但不宽裕。

动作一：选一个和收入或核心交付强相关的场景。比如销售商机分析、客户方案撰写、客服知识问答、项目资料整理、内容生产。销售场景优先，先把它拿下再谈其他。

动作二：整理最小资料库。只收与试点直接相关的客户资料、产品资料和SOP。

动作三：用成熟平台搭智能体和工作流。尽量少做底层重复开发，把预算投向业务规则、资料质量、系统接口和员工体验。很多企业不习惯国外知识库产品，直接用乐享等国内产品更接地气。

动作四：安排两到四周试点。让真实员工连续使用，记录成功任务、失败任务、人工接管情况和改进建议。用客户自己的数据跑任务，边跑边改。

动作五：验收后再决定扩不扩。扩展方向可以是增加用户、增加场景、对接更多系统，或者把临时工具升级为正式系统。二期项目需要有人推动，老板也需要成绩来证明判断。

中型企业交付的关键词就是快、稳、可见，方案别铺得太复杂。

**小型企业：先控范围，再谈见效**

小型企业更在意价格、速度和马上能看到的结果。直白说：预算紧，能省则省，但确实想做，收益更多在后头。

切入点可以是咨询、培训、Skill、小工具或自动化流程。例如：每天自动汇总销售记录；根据客户资料生成跟进建议；根据产品资料生成短视频文案；自动归拢客服问题；根据会议记录生成任务清单。

尽量复用客户已有工具和成熟平台，别让客户一开始就背上服务器、开发、维护的重成本。小型项目最好在一到两个月内拿出看得见的结果。

交付物可以包括一个可用工具、一套提示词、一份资料库、一本操作手册和一次员工培训。小企业项目最怕范围失控，客户看到效果后很容易不断冒新想法，所以合同里必须写清第一期只解决哪些问题。

### 04. 客源怎么找，报价怎么拆

流量这件事得摆在前头。大家都知道智能体有用、也该建，但真正稀缺的是把它卖出去的能力。

**公域获客**

主阵地是公众号软文、朋友圈投放、抖音快手视频号等短视频平台。

与其喊“我会做智能体”，不如讲清一个具体业务问题是怎么被改善的。比如：

1. 销售拜访纪要的整理时间，如何从40分钟压到10分钟。
2. 怎样从两千条客户聊天记录里捞出高意向线索。
3. 如何让客服智能体只回答有企业知识依据的内容。
4. 企业AI项目为什么不适合一开始就追全自动。
5. 十万元以内的中小企业AI项目该怎么设计。

内容里要放进：客户原来怎么做、卡在哪里、用了哪些资料、AI承担什么、人工保留什么、最后发生了什么变化。多展示真实流程和边界，少放漂亮但空泛的界面截图。同时要突出垂直行业方案和产品差异点。

**私域获客**

主要靠转介绍、线下沙龙、行业论坛、B端大客户销售渠道。

和客户聊流量时，重点问三个问题：

1. 现在最花时间的重复工作是什么？最怕哪个环节出错？哪个环节比较标准、不容易出岔子？
2. 这件事目前几个人在做？每次耗时多久？成本大概多少？
3. 如果先改善一部分，什么结果最值得付费？预计想省下多少钱？

第一次合作可以从诊断、小培训、小工具或短周期试点切入。小订单的价值不只是金额，更重要的是让你进入现场，看到老板没讲清楚的真实问题。很多大项目也不是第一次沟通就签，通常先做咨询，再做培训，再做小场景，最后才进入更大的智能体建设与陪跑。

**报价区间**

各家公司的服务报价差异很大。以一人公司和20人以内小团队为例，可参考以下区间：

1. 企业咨询：2000—3000元/半天，资历更深的顾问可以再往上谈。
2. 企业培训：4000—6000元/半天，影响力更大的讲师可以再提高。
3. 定制开发（联合研发或纯外包）：10万—50万元，具体看需求范围、工具技术选型、产品与开发团队水平，能力更强的团队报价自然更高。
   - 小型Skill：约3000—5000元；
   - 小应用、小看板或单流程工具：约1万—3万元；
   - 陪跑服务：每月3万—5万元，常见周期两到三个月；
   - 中小企业验证型项目：总预算通常压在10万元以内。

这些数字只是经验参考，不是统一市场价。实际还要看顾问水平、讲师影响力、行业经验、数据复杂度和客户规模。

做B端项目时，报价单一般拆成多个模块：

- 模块一：需求调研
- 模块二：方案设计
- 模块三：资料库整理
- 模块四：智能体与工作流开发
- 模块五：系统接口与部署
- 模块六：测试与验收
- 模块七：培训与文档
- 模块八：运维与陪跑

拆开之后，客户能看清钱花在哪，服务商也能在需求变化时快速判断新增内容该归到哪一块。账号、模型API、云服务器和第三方平台费用，建议由客户用自己的主体购买并承担；服务商负责方案、配置和交付。

### 05. 实施边界与雷区怎么防

B端智能体项目，坑确实不少，尤其是开发实施类。提前有风险意识、主动设防，远比事后救火划算。

实际交付中常见这些情况：客户不断加需求、对AI能力期待过高、数据对接层层卡住、业务和销售觉得不好用。这些都可能让实际工作量超过合同范围，客户却不愿加预算。怎么防？得提前立规矩。

**风险一：需求越滚越大**

最常见的剧情是，客户看到第一个功能后，立刻冒出十个新想法。

应对不是一口回绝所有变化，而是建立需求变更机制。

1. 合同附件里写清本期范围：用户数量、业务场景、资料库规模、接口数量、自动化流程数量、部署环境、培训次数、维护周期，同时注明本期不做什么。
2. 新增需求必须填变更单，写明内容、原因、对工期的影响、对费用的影响，以及是否调整验收时间。
3. 小范围优化可以放在约定修改次数内消化；新增场景、新增系统接口、重大流程调整，必须重新报价。

**风险二：预期被抬得太高**

有些客户会认为，系统上线后能完全替代员工、百分之百正确、所有操作自动完成，还能立刻带来收入增长。显然不现实。

1. 售前就要管理预期。不要承诺自己无法独立控制的营收、利润或ROI，因为企业结果还受产品、销售能力、市场环境、客户质量和组织执行等多重因素影响。
2. 可以承诺的是项目边界内可验证的改进：处理时间缩短、内容产量提升、人工步骤减少、格式合格率提高、知识检索更方便等。
3. 高风险任务要明确：AI只提供辅助建议，最终结论仍由专业人员复核。

**风险三：数据和接口迟迟不到位**

很多项目卡住，不是开发做不出来，而是客户数据拿不到、系统接口没开放、权限审批没走完。

1. 项目启动时就列出数据和接口前置清单。每项资料都要对应责任部门、责任人、提交时间、格式要求和验收标准。
2. 客户未按约定提供资料，项目周期应相应顺延。尚未开放的接口，可以先用脱敏样例数据做原型验证，但正式上线前必须完成真实环境测试。

**风险四：员工不愿意用**

技术人员觉得功能做完了，业务人员却不想碰。原因可能是操作步骤太多、输出格式不顺手、结果不稳定，或者系统反而增加了工作量。

1. 验收不能只看老板和技术部门的脸色，要让真实使用者参与需求梳理、原型测试和试点。
2. 试点期间记录员工每次使用的成功、失败、修改和放弃原因。如果AI生成结果后，员工还要花大量时间重新整理，说明流程还没真正跑通，用户不想用是再正常不过的反应。

**风险五：数据安全与合规**

合同和方案里要写清数据范围、使用目的、访问权限、存储方式、保留期限和删除机制。

1. 涉及客户隐私、商业秘密和敏感数据时，要做脱敏、最小权限、日志审计和人工审核。不要将客户资料用于未经授权的模型训练，也不要通过不明来源的平台传输敏感文件。
2. 如果客户要求绕过平台限制、自动控制个人账号、批量发送信息或使用未经授权的数据，应当拒绝，或者调整为合规方案。

B端项目通常要求本地化部署，数据方面的问题容易失控，偶尔还会冒出各种报错。多留个心眼总没错——对企业而言，核心系统稳定运行，比任何新项目建设都重要。

最后，祝看到这里的伙伴们，在B端智能体服务上做出成绩，赚得盆满钵满！
