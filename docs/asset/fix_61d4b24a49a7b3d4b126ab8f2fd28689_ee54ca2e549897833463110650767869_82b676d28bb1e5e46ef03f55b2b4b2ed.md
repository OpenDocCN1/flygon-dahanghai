# 可复现的活，别让模型猜

先分清一个容易混淆的来源：有些检查结论并非模型自己想出来，而是它触发了一段代码，代码跑完再把数字送回来。关卡 4 拆 gzh-design 时看到的 scripts/ 目录，装的就是这类程序。

两者差别很直接：

• 模型说“我查过了，没问题”，这是口头保证，是否认真核对，外部很难验证。
• 程序会报出“总计扫描 136 项”，这是算出来的数字；输入不变，重复跑一百次仍是 136。

模型强在组织表达，程序强在给出稳定数字。

这次要做的事，就是让 Skill 也具备程序执行能力。

有人会想到关卡 3 加过的“体检 Skill”。两者不是一回事。那次是在内容生成后，再调 content-risk-detector 检查，本质仍是再调一个技能包。

**现在新增的是脚本程序本身的能力。**

统计、计数、格式转换这类需要稳定答案的工作，应派给程序，而不是让模型推测。

对比起来有三处不同：

• 规则来源：关卡 3 的体检看平台限制，比如哪些词不能发；这次的脚本看你的个人禁区，比如哪些表达你不想用。
• 执行者：前者由模型阅读，可能看漏；后者由程序逐项计算，不容易漏。
• 稳定性：同一篇内容查两遍，前者可能给出两个说法；后者重复运行结果一致。

界线只有一句：同样输入必须永远得到同样输出，这种规则就该交给程序。

**2. 哪些条目适合程序处理**

打开关卡 2 做好的 my-writing-style，找到「我的禁区」。

先别急着写代码，先问自己：这条规则不看含义、只看字面，能不能判断？如果能，就适合交给程序。

例如：

• 卖货的禁区：不能出现“家人们”“宝子们”——程序可查，字在不在有确定答案。
• 开店的禁区：不能写“最好吃”“第一”——程序可查，广告法不允许，字面就能比对。
• 上班的禁区：不能出现客户真名——程序可查。
• 知识付费的禁区：不能承诺“包学会”“一定涨粉”——程序可查。
• 一段不超过三行——程序可查，数行即可。
• 不能连续打两个以上感叹号——程序可查，数字符即可。
• 读着别太端着——模型处理，“端着”没法按字符比对。
• 开头别太平淡——模型处理，同上。
• 别替我编经历——模型处理，要对照资料，关卡 5 那份文件管这事。

一句话：能靠固定比对得出同一种结论的，就派给程序。

第一次不必把全部禁区都改掉。先挑两三条最关键、最容易判定的条目，让 Skill 先稳定跑起来，后面再逐步补充。

如果“我的禁区”写得比较笼统，比如“不要 AI 味”“不要太官方”，一时挑不出适合程序核对的条目，也没关系。先把要求拆细：

• 某几个口头禅不要出现；
• 每段不超过三行；
• 感叹号不要连续堆叠到三个以上。

规则越具体，程序越容易自动核对。

这次虽然以写作 Skill 为例，但学的是通用方法：凡是需要每次稳定执行、不能靠模型临场判断的工作，都可以考虑交给程序完成。

**4. 验证工具是不是真的执行了脚本**

Codex 和 WorkBuddy 桌面版都支持执行脚本。但如果你以后把这个 Skill 分享给别人，或者换到其他 AI 工具（尤其是网页版）使用，就不一定了。

有些工具无法直接执行脚本，却不会明确说明，而是根据脚本内容推测一个“运行结果”，让你误以为脚本已经真的执行。

### 03. 本关常见卡点

遇到问题先别急着放弃，可以先问 AI。本期推荐优先使用 Codex 或 WorkBuddy，把报错信息、截图或你的需求新开一个任务窗口发过去，让 AI 帮你分析原因、排查问题，甚至直接帮你解决。

[PRE9]

慢慢养成先问 AI、再求助他人的习惯，很多问题都会解决。

• 禁区那节为空或太笼统：先核对关卡 2 采访时是不是没说清；不用重做，补两三条具体的，回它“把这几条加进我 skill 的‘我的禁区’那一节”。
• 脚本报错看不懂：核对是否把需要理解语义的条目也塞了进去；回它“把必须读懂意思才能判断的从脚本删掉，只留字面可查的”。
• 提示找不到 scripts/check.py：核对脚本建在哪儿；让它“把 my-writing-style 的文件夹结构画出来”，多半是建到别处了。
• 说要装库才能跑：核对之前“不许装任何额外的库”是否漏了；回它“别装库，只用 Python 自带模块重写一遍”。
• 结果明显不对，没犯规也报：把那段文字再跑一次给它看；回它“这几行没犯规，检查脚本哪里写错了，改完再跑”。
• 它说自己不能跑代码：正常，不少工具如此；05 节最后一条已说，脚本存着、判断力拿走，照样过关。
• 工具存不了文件：核对是否沿用了关卡 2 的路径；仍让脚本写出来，存记事本或发给自己；把“先用脚本扫一遍”记在 SKILL.md 文本末尾。05 节自测可跳过，判断与脚本都在手里，照样过关；换桌面工具可直接用。

### 04. 本关小结

完成这一步，你手上的 Skill 不再只会写规则、读资料，还多了一项本领：把不同性质的任务分派给更合适的工具。

你也会发现，并非所有事都该让模型包办。某个词是否出现、字数够不够、格式对不对、段落有没有超过三行，这类规则固定、答案唯一的核对，更适合程序；至于怎么表达、语气像不像你、判断是否合理，这些要结合上下文和场景，仍应交由模型。

关键不在于代码写得多复杂，而在于换一种思路：

能固定计算、固定核对的，给程序；需要理解、判断与创造的，给模型。

以后搭更复杂的 Skill，你不会再把所有事都丢给模型临场发挥，而会分清：哪些让模型思考，哪些写成程序去执行。

**核心三个动作：**

1. 挑出机器能查的规则：从“我的禁区”中筛出标准清楚、每次检查方式一致的内容。
2. 让 AI 写成脚本：把规则变成可重复运行的程序，放进 scripts/，并让 Skill 知道何时调用。
3. 当场跑一遍验证：确认脚本真的被执行，输出能点出具体问题，而不是只信 AI 说“我查过了”。

做完这一步，你完成了第一次 Skill 脚本能力搭建，也明白了：Skill 不止能写规则、放资料，还能调程序做稳定检查。

### 01. 本关重点

前六关下来，你已经有一个真正能用的 Skill：它会按你的风格写内容、引用真实资料、自动检查固定规则。到这里，你掌握了 Skill 最基础也最常见的用法——处理文字。

可如果 Skill 只会写内容，省下的多半还是“动手”时间。更有价值的是把脑子里的经验沉淀下来，帮你思考。

很多时候，真正耗时间的不是写，而是判断：

• 今天接不接这个客户？
• 这个选题值不值得做？
• 这批新品要不要上？
• 这个合作方案划不划算？

它们没有标准答案，却反复出现，每次都得重新分析。

因此这一关做一个 Skill，专门解决“怎么判断”。

你把判断逻辑、历史案例和决策标准交给它。以后再遇到类似情况，不用从头分析，只要提供信息，它按你的标准给出判断、解释理由，并提醒过去类似案例，最终决定仍由你做。

当然，一个 Skill 不可能一次替代你全部判断。行业里的经验、例外和临场判断很多，很难全装进去。

所以别追求“万能助手”。先挑一件隔三差五就要拿主意、判错容易吃亏的小事，把它做好。越具体，越容易做出来，也越容易用起来。

卖货的，隔几天要判断一批新品值不值得上；开店的，常要判断一个活动值不值得参加；做内容的，反复判断一个选题值不值得做。

做成后什么样？仍以卖货为例：供应商再推新品，你把品名、进价、起订量发过去，它按你的标准给出判断和理由，还会提醒你过去在哪类产品上踩过类似的坑。

工具没换，只是把重复称量的动作省掉了。

[PRE12]

写作风格沉淀的是你怎么表达；判断类 Skill 沉淀的是你积累的判断经验。前者更多模仿你的表达方式；后者保存你一次次踩坑、总结、复盘后形成的判断标准。

因此，这一关尽量用真实案例来做，做出来的 Skill 才真正有价值。

### 02. 动手做一个判断 Skill

1. 找一件值得交给 Skill 判断的事

前面说过，一个 Skill 很难装下多年积累的经验、判断和例外。所以一开始别想做万能判断器。

真正好用的判断类 Skill，常只解决一件具体小事。

标准就三条：

• 会反复遇到；
• 每次都需重新分析；
• 判断错容易吃亏。

满足这三条，就值得先做成 Skill。

不必是天天发生的大事。一个月碰上一两回、每次却要犹豫半天的，反而最合适。

下面几个行业举例，可找最接近的参考：

• 卖货的：可判断新品上不上、价格怎么定、差评怎么回；供应商推新品、想调价、客户在评论区发难时会用上。
• 开店的：可判断新品上不上、活动值不值得做、兼职留不留；想加新口味、平台推团购、试用期小工是否留下时会用上。
• 上班的：可判断需求接不接、活派给谁、汇报说到什么程度；别的部门甩活、人手不够、跟老板过进度时会用上。
• 知识付费的：可判断学员问题要不要单独做课、合作接不接；群里有人提问、有人来谈分销时会用上。

若还是不知道挑什么，翻最近聊天记录。凡是你回过“我想想”“我再看看”“我过两天回复你”，或当时犹豫的事，大概率就是它。
