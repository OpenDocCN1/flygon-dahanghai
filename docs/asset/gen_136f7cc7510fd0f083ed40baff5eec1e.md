1. **做一个 Agent 展示网页**

Agent 的落地形式有很多，业务场景不同，交付载体也会不同。例如：
- 聊天机器人（Bot）：嵌入飞书、微信、Slack、Discord 等聊天工具，与用户直接对话。
- 网页应用（Web App）：以网址形式提供，用户打开链接就能使用。
- 企业内部工具：接入公司业务系统、OA 或工作流，作为内部工具使用。
- API 服务：以接口形式提供后台能力，让其他系统或应用调用。
- 桌面或移动应用：打包成独立软件或 App；不同平台可支持机器人、网页应用、小组件等形态，也能混合使用。

这次落地，我们选的是聊天机器人（Bot）形态，不过这套方法并不只适用于 Bot。只要系统能理解目标、规划任务、调用工具、反馈状态并做好安全控制，就能套用同一套 Agent 构建思路。形态之间的差别，主要落在入口、触发方式、上下文管理以及风控颗粒度上。

下一步，就是给它一个可公开访问的网址。但要说清楚：这个页面并不等于把 Agent 真正部署上线。若想让外部用户长期使用，通常得备好服务器、域名和运行环境，还要持续支付模型 API（Token）等费用，并处理稳定性和安全问题。别人使用你的 Agent 时，这些资源同样会被消耗。

接下来生成的网址更像一张 Agent 名片页：用来呈现 Agent 的信息、能力和成果，便于分享；它不会真正运行 Agent，别人也无法从网页直接调用，更不会消耗你的 Token。

为什么要先做展示页？因为想让你提前感受 Agent 从“自己能用”走向“别人也能用”的过程。不少人搭完 Agent，只在自己的电脑或开发环境里跑得通。一旦有了公开网址，把链接发出去，对方不用配环境就能直接体验和使用。这时它就不只是 Demo，而开始有了产品雏形。以后无论是给团队同事共用、向客户交付 AI 工作流、做成企业内部工具，还是打磨成对外服务产品，这一步都绕不开。

对本期航海的大多数船员来说，当下更关键的是让几个 Agent 稳定、持续地替自己分担一部分工作，而不是一上来就砸成本做部署和运维。当然，若能力和需求都到位，也可以继续完成部署上线；上线之后，别人才能真正在线体验和使用你的 Agent，而不只是看展示页。这部分属于跑通 Agent 基础闭环后的进阶探索，不在本期航海学习范围内。

因此，本关目标不是部署，而是迈出 Agent 产品化第一步。先让别人看懂你的 Agent、知道它能解决什么问题；等有真实业务需求，再按实际情况决定是否上线，让它成为能长期运行、供他人使用的在线产品。

## 提交前自检

小D 的最终验收标准，7 项全过才算复制成功。若你跟着做的是音视频转录 Agent（小D），提交前逐条核对：
1. 能拿到一个公开播客或视频链接
2. 能获取或下载音频
3. ASR 转写能完成
4. 能产出分享式提纯稿，而非摘要
5. 能新建飞书文档
6. 能把文档权限开放给本人
7. 能给出可正常打开、目录与格式都正常的飞书链接

小D 容易踩的坑，提交前逐项检查：
1. 提示词抄了，工具链却没装：只会得到一个“说话像小D”的助手，无法真正下载、转录、建文档。关卡5必须把 yt-dlp/whisper/lark-cli 装好。
2. 提纯写成了摘要：交出来的是“十条要点”，不是可读的原文整理稿。回关卡4看 Profile 中“不写成核心要点/一句话总结”的规则。
3. 术语没校正：长音频里的人名、公司名常被 ASR 听错，要在 Profile 中补一份常见错词对照表。
4. 飞书权限没闭环：Bot 建了文档，用户却打不开，这算交付失败，不算成功。
5. 凭据泄露：app secret、token、cookie 一律不能出现在聊天、文档或截图里。

### 03. 本关常见卡点

卡住时别急着放弃，先让 AI 帮忙。本期建议优先用 Codex 或 WorkBuddy：把报错、截图或需求新开一个任务窗口发过去，让 AI 分析原因、排查问题，甚至直接动手解决。

先问 AI、再找他人，慢慢养成这个习惯，很多问题会迎刃而解。

[PRE6]

**卡点、默认动作与判定标准**
- Agent 只成功跑过一次，换个输入就失败：回关卡 3 看工作流判断点是不是写死了特定输入；判定标准是 3 个不同样例里至少 2 个跑通。
- 截图看不出“Agent 在干活”：按“输入前→运行中→输出后”拍三连图；每张图时间顺序要清楚。
- 不知道说明书怎么写：套用步骤 5 的固定模板，一项项填；判定标准是陌生人能照文档复现。
- 总想做到完美再交：先交最低合格三件；有链接、截图和说明书就能提交。

**现象与可直接对 AI 说的话**
- 手动能跑，定时任务却跑不了：让 AI 对比手动和定时运行时的 Profile、工作目录、环境变量、MCP 与飞书 CLI 身份，列出差异。
- 任务成功了，飞书消息却没收到：让 AI 分开检查运行摘要里的数据处理结果和消息发送结果，并确认真实群 ID 或用户 ID。
- 同一天跑了两遍：先暂停正式任务，排查是否存在两条相同调度，再用日期加主题 ID 去重。
- 不会暂停或删除任务：让 AI 把任务名称、ID、暂停、恢复、删除方法写进 README，并实际查看一次状态。
- 整理稿质量差：让 AI 对照 Profile 中的质量标准与真实输出，逐条标出未达标项，并指出该改 Profile 哪一行。
- 总想做到完美再交：先交最低合格三件。

### 04. 本关小结

跑闭环，就是用真实样例证明：Agent 不只可以演示一次，还能被验收、被修正、被交付。

前五关，你已经从 Demo 体感走到正式 Agent 搭建：定岗位、拆流程、写 Profile、接工具、接飞书。到关卡 6，重点不再是加功能，而是拿真实输入反复跑，把“我觉得能用”推进到“别人看得懂、能验收、可复用”。

四个核心动作：
1. 备测试样例：至少 3 个真实或接近真实的输入，覆盖常规、边缘和你最关心的业务场景。
2. 留运行证据：记录输入、执行过程、输出结果和人工验收结论，让别人看出 Agent 最近确实干过活。
3. 校对并优化一轮：按影响大小排序测试问题，回到 Profile、工具链或流程规则逐个修，再用同一样例复测。
4. 整理交付材料：公开链接、成功运行截图、使用说明书和测试记录都要备齐，让 Agent 从“能跑”变成“能交”。

到这里，必修篇已全部完成。你至少拥有一个能独立完成任务、跑通闭环的 Agent：有岗位、有流程、有大脑、有工具，也有可验证的交付材料。

接下来的选修关卡会继续往前：不再只盯一个 Agent 怎么工作，而是把它放回真实业务，观察输入从哪来、结果交给谁、是否值得与其他人、工具或 Agent 连接。

选修篇更开放，也更难。下一关开始不再设必须提交的作业，只需对照任务目标和描述，跟着步骤练习。若暂时没有自己的业务场景，也可以继续用默认案例，先理解方法，再迁移。

选修篇更像进阶指南，不必一次做完；先完成与当前 Agent 最相关的内容，未来需求变化再回来探索。

必修关里做 Agent，本质是把真实工作流交给 AI 执行。但完整 Agent 常绑定本地文件、飞书空间、业务资料和个人流程，别人未必能直接复用；真要部署上线也有难度和成本。因此，更适合共享的往往不是整个 Agent，而是其中一个小能力：一个节点、一段判断逻辑、一个提示词模板、一个整理流程或一个输出格式。把它单独抽出来，就能做成 Skill，让更多圈友看到、下载、复用。

这个 Agent 本身完整、能干活，但未必方便直接分享。它可能依赖你的飞书空间、本地工具、账号权限、文件路径、业务资料和固定输出位置……别人拿到整个 Agent，不一定跑得起来。

不过其中有一个能力很适合抽出：清洗转录稿，并按固定结构整理成摘要、行动项和待确认问题。它不依赖账号，也不依赖飞书空间，只要别人有一段转录稿就能用，所以适合沉淀成 Skill。

从 Agent 抽 Skill，可以按 3 步走：
1. 回看 Agent 工作流，找出重复出现、价值高、别人也可能需要的一小段能力。
2. 把它从完整流程中拆出来，不要上传整个 Agent；只保留清晰的小能力：输入是什么、处理什么、输出什么。
3. 写成别人能复用的 Skill，说明适合谁、解决什么问题、怎么用、用前用后有什么效果。

当然，不必自己硬想“哪个节点适合抽成 Skill”。更简单的办法是：把 Agent 工作流交给 AI，让它帮你拆节点、判断价值，并筛出最适合上传 Skill Hub 的能力。
