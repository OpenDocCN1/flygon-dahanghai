调教判断类 Skill 时，你遇到过这些场景吗？模型给出的答案让你总觉得哪里不对，但又说不出具体问题。别急，这不是你的 Skill 没救了，而是还没做“问题定位”。下面这份清单，把最常见的七个异常现象、背后的原因和对应的处理方式一次说清。

**现象一：编的五个案例，看着就不像真的。**  
原因：它根本不懂你这行的实际场景。  
处理：直接回复它“这几个不像我这行会碰到的，按我第一步说的场景重编五个”。案例编得不像，就等于没有测试到你的真实标准。

**现象二：你说不出为什么不做，就是感觉不行。**  
原因：它可能是在硬凑一个“听起来合理”的理由。  
处理：让它“猜猜我为什么不做，给三个可能的理由，我挑”。你要知道，认出一个对理由比凭空说出来容易得多。

**现象三：它给的结论全是“建议谨慎评估”。**  
原因：SKILL.md 里“怎么给我结论”那部分可能被删了或写漏了。  
处理：把这一节补回去，核心要求是：必须给结论、必须逐条说理由、拿不准就直说拿不准。

**现象四：它回了一整段，你根本数不清有几条。**  
原因：还是“怎么给我结论”那节的问题。  
处理：直接说“按我 skill 里说的格式重来：先给结论，再一条一条列理由，每条说清命中了我哪条标准”。

**现象五：它说的理由，一条都对不上你说过的话。**  
原因：采访环节你可能答得太笼统，它没拿到具体的标准。  
处理：回到 04 节，告诉它“我给的标准太虚了，再问我一遍，逼我说出具体的数和具体的情况”。

**现象六：它说的听着有理，但全是放之四海皆准的大道理。**  
原因：它可能是在说套话。  
处理：把它那段理由复制走，对它说“我把这段话套到我另一件事上好像也成立，那你这是不是在说套话？重新按我 SKILL.md 里那几条标准逐条说”。

**现象七：你的工具存不了文件（比如网页版）。**  
原因：你走的可能是关卡 2 的那条路。  
处理：按关卡 5 的做法：SKILL.md 和案例都存备忘录，每次开工把两样一起粘进对话框。注意，采访那轮的对话别粘，粘了等于开卷。04 节那段采访照样能用，作业里需要截图的地方就用备忘录截图，一样算数。

### 04. 本关总结

恭喜你，现在你已经从零做出来一个判断类 Skill，而且用真实案例验证过它会不会按你的标准来判断。

做完这一关你会发现：Skill 不仅能帮你完成任务，还能把你的判断经验沉淀下来。前面几关你教它怎么写、怎么查资料、怎么调脚本；这一关开始，你把自己过去一次次判断、踩坑、复盘得到的经验，也变成了 Skill 的一部分。以后再遇到类似问题，你不需要从头分析，可以让 Skill 先按你的标准给出结论和理由，你再做最终决策。

这一关最重要的方法是：挑一件具体的小事，把这一类问题的判断标准沉淀下来。凡是反复遇到、每次都要重新分析、判断错了容易吃亏的事情，都值得慢慢做成 Skill。

验证 Skill 是否成功，不是看结论是否和你完全一样，而是看它给出的理由是否来自你的标准。如果它引用的是你的硬指标、软判断和踩过的坑，而不是一堆通用道理，就说明你的经验真正沉淀进去了。

**核心三个动作：**

1. 选一个具体判断场景：别做万能助手，先挑一件你反复遇到、总要重新想、判错会吃亏的小事。
2. 把判断标准挖出来：通过 AI 采访和五个案例，把硬指标、软判断、边界条件和踩过的坑整理成 SKILL.md。
3. 用真实案例验证：新开对话，只给案例不说倾向，看它的理由能不能对上你写进的标准。

从现在开始，Skill 不只是帮你完成工作，还在帮你保存经验、复用经验，并让经验持续积累。

**下一关**，我们将学习另一项同样重要的能力：迭代。当你发现 Skill 漏了标准，或者判断不够准，不需要推倒重来，而是学会一次只改一条规则，再用同一个案例验证，让 Skill 一点一点变好。

### 01. 核心要点

前面几关，你一直在给 Skill 加能力：关卡 3 让它学会调用其他 Skill，关卡 5 给它补充资料，关卡 6 让它能跑脚本。这些都是“增加东西”。

这一关，我们要修改一个已经能工作的 Skill。因为上一关之后你可能会发现：Skill 不会一次做到完美。有些判断不到位，有些标准你后来才想起来，有些经验是用着用着才沉淀出来的。

所以，Skill 做出来不是结束，而是开始。它需要像你的工作经验一样，不断迭代。

但修改 Skill 最容易踩的坑是：看到哪里不满意，就全部一起改。结果新问题解决了，原来正确的地方反而坏了。

因此这一关最重要的一条原则只有一句：**每次只动一条规则，动完立刻用同一个案例重新验证。**

这样你才能知道：这次修改有没有生效？有没有影响原来正确的判断？

[PRE3]

你的业务一直在变：产品会变，客户会变，市场会变，你自己的判断标准也在更新。如果 Skill 做出来之后一直不改，它最准确的时候就是刚做完的那一天。只有持续迭代，它才能一直跟着你的经验成长。

这一关结束后，你会掌握一套修改 Skill 的固定流程：发现问题 → 保存旧版本 → 修改一条规则 → 用同一个案例重新验证。以后不管是补充判断标准、增加脚本，还是扩展 Skill，这都是最常用的一套迭代方法。

- **最影响判断结果的那一条**。大多数人都会先改“我最在意的那一点，它没提到”。
