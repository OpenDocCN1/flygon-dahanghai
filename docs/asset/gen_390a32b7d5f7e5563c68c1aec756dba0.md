# 三分钟看懂 MCP

官网：https://modelcontextprotocol.io/introduction

MCP 的全称是 Model Context Protocol。官方对它的定义是：让各类应用能够用统一的方式，把上下文信息提供给大语言模型（LLM）。如果这句话有点绕，可以换个说法：它就像 AI 世界里的 USB-C 式标准接口，把数据源、工具和模型之间的连接统一起来，不再各用各的线。

你可以联想一下日常设备：电脑、手机、相机、移动硬盘，过去常常要配 USB-A、HDMI、Micro-USB 等不同接口，线材一堆、体验混乱；如今 USB-C 正在把这种局面收拢。MCP 想做的，就是类似的事情。

来看一个具体场景：

🎯 前后效果对比

没有 MCP 时：

你：帮我查一下数据库里今天的订单

Claude：我没法直接访问数据库，你得自己查完再把结果告诉我

你：😫（打开数据库工具，写 SQL，复制结果……）

有了 MCP 后：

你：@database 查询今天的订单

Claude：查好了，今天一共 156 个订单，总金额……[结果直接展示]

你：😊 爽！

所以，MCP 的本质是让 AI 从“参谋”变成“执行者”，从只会动嘴升级为能够动手操作各种工具的助手。也可以说，它给 AI 装上了手脚。

# 2.2 为什么需要 MCP

大模型发展越来越快，如何让模型更好地与周边应用结合、对接，是一个绕不开的挑战。最早常见的形态是 function calling，但用起来相对繁琐。

除此之外，还有几类问题需要解决：

- 上下文提供方式混乱：不同应用各有一套向 LLM 发送上下文的办法，导致重复开发，也容易不兼容。
- 模型切换成本高：比如从 OpenAI 的 GPT-4 换到 Google 的 Gemini，可能得重写不少与模型交互的代码。
- 安全与隐私：怎样保证只把经过授权的特定上下文（例如当前打开的文件）发给 LLM，而不是把整个文件系统都交出去？
- 工具集成复杂：如何让 LLM 安全、可靠地调用本地工具，比如代码编译器、Linter、API 客户端？

MCP 的出现，正是为了解决这些痛点。它提供了一个标准化的中间层，把“应用本身”和“AI 模型”解耦开来。对 Claude Code 来说，MCP 也是很关键的一张牌，能连接各种外部工具。

# 01.不同平台的部署方法

部署，就是把“只能在我电脑上跑”的东西，变成“大家随时随地都能用”的服务。

打个比方：你做了一顿饭（代码/应用），如果只放在自家厨房，别人吃不到；把它端到餐桌（服务器/线上环境），大家才能一起享用。

前面项目开发时都运行在本地电脑上，只能本机访问。如果你希望别人也能访问，比如在另一台能上网的电脑上打开，或者在手机上也能用，那就需要做部署上线。

并且部署后，程序运行在专门的环境里（服务器、容器），比个人电脑更稳定，不会随便断电、关机。

注意：这里介绍的部署平台，针对的是网页（浏览器访问）和后台服务（提供 API 接口形式）类型。小程序和 App 属于另外的操作，更复杂，这里不展开。
