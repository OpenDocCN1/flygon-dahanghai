# B端AI智能体：先别急着开工

项目还没启动，最好先把四张表跟项目组一起对齐；如果还能拉着客户逐项确认，那就更稳妥。很多延期，并不是技术做不出来，而是前期底账没摊开。

1. **业务场景表**：写清场景叫什么、哪个部门在用、眼下卡在哪、多久发生一次、目前要耗多少时间、需要哪些输入资料、最终产出什么、风险等级如何、预期价值有多大。
2. **系统接口表**：列明系统名称、涉及哪些数据、接口采用什么方式、由谁负责、需要什么权限、测试环境是否就绪、预计何时开放。
3. **知识库资料表**：登记资料名称、来源部门、文件格式、数量、更新频率、保密级别、责任人，以及能否用于模型。
4. **项目责任表**：把客户侧的项目负责人、业务负责人、技术负责人、数据负责人、验收负责人，以及服务商对应人员全部明确。

这四张表缺位，项目中途很容易因为资料不齐、接口没开、需求反复而拖慢节奏。

### 03. 交付方案与知识库怎么搭

企业规模不同，交付路径也不能一刀切。这里给两类思路：通用方案和定向方案。

**通用版：多数企业可以先试“Agent+知识库+自动化+人工节点”**

注意，是“可以试”，不是万能公式，不合适就别硬套。

- Agent负责接任务、理解意图、调用工具、输出结果。
- 知识库负责补上客户、产品、制度、流程、历史案例等企业上下文。
- 自动化负责定时触发、消息通知、任务流转、结果归档。
- 人工节点负责审核高风险内容、处理异常、做最终决策。

别把人工节点当成“系统不够聪明”。在企业项目里，合理的人机协同往往比一味追求全自动更安全、更稳定，也更容易验收。

知识库建设前，先盘三类资料：

1. **CRM和客户档案**：回答谁在买、客户有什么特征、过去沟通过什么、现在处在哪个阶段。
2. **SKU和产品资料**：回答企业卖什么、规格价格如何、适用范围和限制在哪里。
3. **SOP和流程标准**：回答员工该按什么步骤做、什么结果算合格、什么情况要升级处理。

这三类资料都不完整，就别假装“接上大模型就能解决”。先把最小可用知识库做出来。

所谓最小可用，不是把公司所有文件一股脑导进去，而是围绕第一个试点场景，只整理真正用得上的内容。业务人员、销售人员用不到的，先别放，放了既耗时间又耗人力。比如做客服问答智能体，第一期只整理产品说明、常见问题、售后政策、退款规则和转人工条件就够了，其余资料后续再补。

**大型企业：组织复杂，更要分阶段推进**

大型企业往往组织层级多、系统多、数据敏感、权限严格、决策链长。说白了，国企央企流程长，项目容易卡在流程上，交付和尾款都可能被拖住。

第一阶段，做企业级诊断。不能只访谈老板，还要访谈业务部门、信息科技部门、数据部门、安全合规部门和一线使用者。顺序上，先访谈老板，领导发了话，下面的人更容易配合。

第二阶段，建立场景库和优先级。大型企业可能一次提出几十个场景，要按业务价值、实施难度、数据基础、风险、可复制性来评分。再按使用频次排序，先把最常发生的场景挑出来。

第三阶段，建设统一基础能力。包括统一模型接入、统一知识库、统一权限认证、统一日志审计、统一智能体编排、统一运营看板。这里最好用成熟产品，避免重复造轮子。

第四阶段，开展单部门试点。即使预算充足，也不建议第一期全公司上线。选一个部门、一个场景、一组真实用户，连续用起来。小闭环先跑通，让领导看到成效，二期项目才有基础。

第五阶段，做安全和稳定性测试。正常输入、缺失输入、异常输入、越权访问、敏感信息、网络中断、接口失败、模型不可用、并发压力，都要测。关键不是技术自嗨，而是让客户方人员觉得好用，客户说好才算真的好。

第六阶段，找典型场景逐步推广。试点稳定后，把标准化能力复制到其他部门，同时保留不同业务条线的个性化配置。一个场景建好了，才容易复制，老板也更愿意看到可复制的成果。

大型企业的AI智能体项目，常见交付物包括总体规划、业务场景地图、技术架构、数据架构、知识库标准、安全方案、试点系统、测试报告、培训材料、运营制度和推广计划等。

**中型企业：成熟平台加场景定制，快稳可见**

中型企业通常有一定业务基础和数字化系统，但预算、技术团队和管理能力有限。一开始不适合搭过于复杂的平台，更适合“成熟平台+场景定制”。直白点说，有钱，但不算多。

第一步，选一个和收入或核心交付强相关的场景。比如销售商机分析、客户方案生成、客服知识问答、项目资料整理、内容生产。销售，销售，销售，先把这个场景拿下再说其他。

第二步，整理最小知识库。只整理与试点场景直接相关的客户资料、产品资料和SOP。

第三步，用成熟平台搭智能体和工作流。尽量少做底层重复开发，把预算放在业务规则、知识库质量、系统接口和员工使用体验上。很多企业并不习惯国外知识库，直接上乐享等国内知识库更现实。

第四步，安排两到四周试点。让真实员工连续使用，记录成功任务、失败任务、人工接管情况和改进建议。用客户自己的数据跑任务，边跑边迭代。

第五步，验收后再决定是否扩展。扩展方向可以是增加用户、增加场景、对接更多系统，也可以把临时工具升级为正式系统。二期项目需要引导，老板也需要成绩来证明自己。

中型企业交付的重点就三个字：快、稳、可见。方案别追求太复杂。

**小型企业：控制范围，尽快见效**

小型企业更在意价格、速度和立刻能看到的结果。直白点说，没钱，能省则省，但又确实想做，收入更多在后期。

可以从咨询、培训、Skill、小工具或自动化流程切入。例如：自动整理每日销售记录；根据客户资料生成跟进建议；根据产品资料生成短视频文案；自动汇总客服问题；根据会议记录生成任务清单。

尽量使用客户已有工具和成熟平台，别让客户一开始就承担高额服务器、开发和维护成本。小型企业项目最好在1到2个月内看到结果。

交付物可以包括一个可用工具、一套提示词、一份知识库、一套操作手册和一次员工培训。关键是控制范围。客户看到效果后，很容易不断冒出新想法，所以合同里必须写清楚：第一期只解决什么问题。

### 04. 流量入口与报价拆解

流量必须重视。大家都知道AI智能体有用、要建，但谁能把它卖出去，更重要。

**公域流量**

以公众号软文、朋友圈投流、抖音快手视频号等短视频平台为主。

比“我会做AI智能体”更有效的，是讲清楚一个具体业务问题怎么被改善。比如：

1. “我们如何把销售拜访纪要从40分钟缩短到10分钟。”
2. “如何从两千条客户聊天记录里筛选出高意向线索。”
3. “如何让客服智能体只回答有依据的企业知识。”
4. “为什么企业AI项目不能一上来追求全自动。”
5. “一个十万元以内的中小企业AI项目应该怎么设计。”

内容里要包含：客户原来怎么做、遇到什么问题、用了什么资料、AI负责什么、人工负责什么、最终有什么变化。多展示真实流程和边界，不要只放漂亮界面。同时要突出AI智能体垂直化的解决方案和产品优势。

**私域流量**

主要靠转介绍、线下沙龙、行业论坛、B端大客户销售渠道。

搞流量时，和客户重点问三个问题：

1. 你们现在最花时间的重复工作是什么？最怕哪个环节出错？哪个环节不怕，比较标准化？
2. 这件事现在几个人做，每次花多久？成本大概多少？
3. 如果先改善一部分，什么结果你们觉得最值得付费？预计想省下多少钱？

第一次合作可以从诊断、小培训、小工具或短周期试点开始。小订单的价值不只是订单金额，更重要的是让你进入现场，看到老板没有说清楚的真实问题。很多大项目并不是第一次沟通就签下来的，而是先做咨询，再做培训，再做小场景，最后进入更大的智能体建设和陪跑项目。

**订单报价**

不同AI智能体服务的报价，各家公司差异很大。以OPC一人公司和20人以内小团队为例，可以参考：

1. AI智能体企业咨询：2000—3000元/半天，水平更高的咨询师可以再提高。
2. AI智能体企业培训：4000—6000元/半天，水平更高的讲师可以再提高。
3. AI智能体定制化开发，无论是联合研发还是纯项目外包：10万—50万元，具体和需求多少、工具技术、产品与开发水平有关，更强的团队可再提高。
   - 小型Skill可按约3000—5000元评估；
   - 小应用、小看板或单流程工具可按约1万—3万元评估；
   - 陪跑服务可按每月3万—5万元评估，常见周期为两到三个月；
   - 中小企业验证型项目，常见总预算可控制在10万元以内。

这些数字只是经验区间，不是统一市场价格。企业咨询、培训和定制项目，还要结合咨询师水平、讲师影响力、行业经验、数据复杂度和客户规模综合报价。

做B端项目时，一般会把报价单拆成多个部分：

- 第一部分，需求调研费用；
- 第二部分，方案设计费用；
- 第三部分，知识库整理费用；
- 第四部分，智能体和工作流开发费用；
- 第五部分，系统接口和部署费用；
- 第六部分，测试与验收费用；
- 第七部分，培训与文档费用；
- 第八部分，运维和陪跑费用。

这样客户能清楚知道钱花在哪里，服务商也能在需求变化时判断新增内容属于哪一部分。账号、模型API、云服务器和第三方平台费用，建议由客户以自己的主体购买和承担；服务商负责方案、配置和交付。

### 05. 实施边界与风险防线

B端AI智能体项目踩坑不少，尤其是开发实施类项目。风险意识越早建立，越能提前规避。

实际交付中，常见卡点包括：客户不断增加需求、对AI预期过高、数据对接层层受阻、业务部门和销售觉得不好用。这些问题可能导致实际工作量超出合同范围，客户又不愿意加预算，所以必须提前设好边界。

**风险一：客户不断增加需求**

AI智能体项目最常见的问题，就是客户看到第一个功能后，立刻提出十个新想法。

解决办法不是拒绝所有变化，而是建立需求变更机制。

1. 合同附件中明确本期交付范围，包括用户数量、业务场景、知识库数量、接口数量、自动化流程数量、部署环境、培训次数和维护周期，同时明确本期不做什么。
2. 新增需求需要填写变更单，说明需求内容、产生原因、对周期的影响、对费用的影响，以及是否调整验收时间。
3. 小范围优化可以包含在约定的修改次数内；新增场景、新增系统接口和重大流程变化，必须重新报价。

**风险二：客户对AI预期过高**

有些客户认为，AI智能体上线后可以完全替代员工，百分之百正确，自动完成所有操作，并且立刻带来收入增长。肯定不是这样。

1. 售前阶段就要管理预期。不要承诺无法独立控制的营收、利润或ROI。企业业务结果还会受到产品、销售能力、市场环境、客户质量和组织执行等多种因素影响。
2. 可以承诺的是项目范围内可验证的变化，例如处理时间缩短、内容产量提高、人工步骤减少、格式合格率提高、知识检索更方便。
3. 对于高风险任务，要明确AI智能体只提供辅助建议，最终结论必须由专业人员审核。

**风险三：数据和接口迟迟不到位**

很多项目不是开发做不出来，而是客户数据无法提供、系统接口没有开放、权限审批没有完成。

1. 项目启动时建立数据和接口前置条件清单。每一项资料都要有责任部门、责任人、提交时间、格式要求和验收标准。
2. 如果客户未按约定提供资料，项目周期应相应顺延。对于尚未开放的接口，可以先用脱敏样例数据完成原型验证，但正式上线前必须完成真实环境测试。

**风险四：员工觉得不好用**

技术人员认为功能已经完成，业务人员却不愿意使用。原因可能是操作步骤太多、输出格式不符合习惯、结果不稳定，或者系统反而增加了员工工作量。

1. 项目不能只由老板和技术部门验收。需要让真实使用者参与需求梳理、原型测试和试点。
2. 试点期间记录员工每次使用的成功、失败、修改和放弃原因。如果AI智能体生成结果后，员工还要花大量时间重新整理，说明项目还没有真正跑通，对方不愿意用也很正常。

**风险五：数据安全和合规**

合同和方案中要写清数据范围、使用目的、访问权限、存储方式、保留时间和删除机制。

1. 涉及客户隐私、商业秘密和敏感数据时，应采用脱敏、最小权限、日志审计和人工审核。不要把客户资料用于未经授权的模型训练，不要通过不明来源的平台传输敏感文件。
2. 如果客户要求绕过平台限制、自动控制个人账号、批量发送信息或使用未经授权的数据，应该拒绝，或者调整为合规方案。

B端项目通常要求本地化部署和开发，数据方面的问题容易失控，也可能出现部分报错。多留几个心眼，毕竟企业相比建设AI智能体，更希望原来的系统不要出错。

最后，祝看到这里的伙伴，都能做好B端企业AI智能体服务，赚钱多多。

### 06. 收尾复盘：带走一套方法

恭喜你，完成了本次Agent航海的全部关卡。

回头看，你完成的不只是一个Agent。你从一个真实业务问题出发，学会了拆岗位、拆流程、写Profile、连接工具、完成闭环，再到今天，把一个Agent包装成一套企业愿意试点、愿意付费的服务方案。

一路走下来，真正的变化不是学会了几个工具，而是开始拥有一种新的工作方式。

遇到一个业务问题，你会先想：它真正的问题是什么？哪一部分可以交给Agent？怎么把它做成边界清楚、结果可验收的小闭环？又怎么一步步扩展成更大的业务价值？

这就是Agent企业服务最核心的能力。

企业最终购买的，从来不是“AI Agent”这个名字，而是一个原本效率低、成本高、容易出错的业务流程，被重新跑通了。

所以，不要急着做一个无所不能的Agent。先做好一个真正解决问题的小闭环，让它稳定运行、创造价值，再不断迭代、不断放大。

希望这只是你企业AI服务的第一个项目，也是未来更多项目的开始。

回头看看，这21天，你可能从第一次接触Codex、Hermes和飞书开始，一步步完成了环境配置、岗位设计、Profile编写、Agent搭建、飞书接入和真实测试，也拥有了属于自己的第一个AI员工。

更重要的是，你带走的不只是一个Agent，而是一套把真实工作拆解、交给AI、不断优化迭代的方法。

从今天开始，当你遇到重复、标准明确、可以验收的工作时，想到的不再只是“自己做”，而是会多问一句：这件事，能不能交给Agent？

希望本次21天做出的Agent，只是你的第一个。未来，你会拥有第二个、第三个，甚至一整个属于自己的Agent团队。

期待未来的某一天，在SkillHub、黑客松，看见你创造出的作品。

恭喜圆满靠岸，也祝你一路创造🚀
