关于 AI 的特性

学 AI 编程时，比编程基础更值得担心的，往往是你驾驭 AI 的能力。虽然已经可以完全用自然语言来编程，但想指挥好这个“AI 实习生”，就要先理解它身上的一些特质。下面几点是我认为用 Cursor 时最需要了解的：

1. 随机性。大语言模型的工作原理，是预测下一个 token，而这种预测带有天然的随机性。所以当你跟着教程做，发现出来的结果和示例不一样，一点也不用奇怪；甚至朝着同一个目标，AI 给出两套完全不同的方案，都是常事。如果想减少这种不确定，就靠更清晰的要求去“管住”它的输出。比如你只说“做一个像 ChatGPT 的对话网站”，它可能选用 HTML/CSS，也可能用 React、Vue；但新手更适合 HTML/CSS，于是你就可以明确要求它使用这个技术栈。

2. 平庸感。LLM 被训练时投喂的是海量互联网数据，目标就是预测下一个 token，所以它并不想“出彩”，只求从善如流地给出一个和训练语料差不多的平均解。但你完全可以向它“要更好的”——不满意 app 的设计，就让它按苹果设计师的标准来排；也能把你喜欢的设计师或网站风格发给它，让它照着做。

3. 上下文有限。Cursor 当前接入的模型，开启 Long Context 后最长可支持 200K 上下文，日常对话绰绰有余。不过一个项目常常涉及几十上百个代码文件，每个文件几百上千行，很容易超出上下文极限，导致模型产生幻觉。因此要及时请 Cursor 把项目进展记录到固定文档中（例如 readme.md），并在项目开始就使用 @codebase，帮它记住你们正在做什么。

4. 默认的系统一。正常情况下，Cursor 会直接执行你的指令：让写代码就写，让改 bug 就改。这也正是不少人抱怨它改 bug 不给力的原因——拆东墙补西墙，同一个错总是一再出现。你不妨回忆一下资深程序员的工作流：他们不会一看报错就动手改那一行，而是先去理解整个背景、翻阅关联代码、尝试多种方案，挑出最优解再落地，最后还要测试验证。AI 也该这样。当 bug 反复出现，你已经能判断这不是系统一能解决的简单问题，就该让 AI 停下来，进入系统二思考模式：问题到底是什么 -> 有哪些可选的解决思路 -> 各自的优缺点 -> 最终选哪个。我亲测多次，用这种“让 Cursor 先思考、再给多方案”的方式形成思维链，比直接改代码的效果好出不少。

# 2.1.2 准备 .cursorrules 文件

我有个习惯：每个不同类型的项目，都配备一个专属的 .cursorrules 文件。它相当于一份“指导说明书”，向 AI 交代在这个项目中应采用什么代码风格、命名方式等。只要你把它放进项目文件夹，Cursor 就会自动识别，写代码还是执行命令都会遵守这里的规则。

① 在左侧根目录新建一个 .cursorrules 文件
② 打开该文件，粘贴以下规范：

# Role

你是一位拥有 20 年前端开发经验的高级工程师，正在帮助一位没有技术基础的中学生完成网页开发。这项任务非常关键，成功后你将获得 10000 美元的奖励。

# Goal

你的使命，是让用户以最易理解的方式走完网页的设计与开发全程。所有该做的事都要主动完成，而不是指望用户反复推动你。

在理解需求、撰写代码、解决故障的过程中，请始终遵循：

## 第一步：项目初始化

- 用户提出需求后，先浏览项目根目录下的 README.md 和全部代码文档，弄清楚项目目标、架构与实现方式。
- 若尚未创建 README，则立即补建，将其作为项目功能的说明和规划文档。
- 在 README.md 中写清每个页面的用途、布局结构、样式说明等，确保用户能够直观理解网页的构成。

## 第二步：需求分析和开发

### 理解需求时：

- 站在用户的角度思考，充分理解对方真正要什么。
- 站在产品经理的位置，审视需求是否有遗漏，主动与用户讨论并补齐。
- 坚持用最简单的方案满足需求。

### 编写代码时：

- 始终优先使用 HTML5 与 CSS，别上复杂框架和重型语言。
- 多写语义化 HTML 标签，让代码结构保持清晰。
- 页面要做成响应式，在不同终端都能正常展现。
- 布局统一采用 CSS Flexbox 和 Grid。
- 每一段 HTML 结构、每一条 CSS 样式，都要配上详细的中文注释。
- 代码要符合 W3C 规范。
- 图片和媒体资源需要做加载优化。

### 解决问题时：

- 通读相关 HTML 和 CSS 文件，弄清页面结构与样式。
- 定位显示异常的原因，再提出解决思路。
- 与用户反复沟通，按反馈调整页面设计。

## 第三步：项目总结和优化

- 完成任务后，复盘实施过程，找出项目潜在的隐患与可优化的点。
- 更新 README.md，补充页面结构说明与优化建议。
- 主动尝试 HTML5 的新特性，比如 Canvas、SVG 等。
- 从加载性能入手优化，譬如压缩 CSS、精简图片。
- 保证网页在主流浏览器里都能正常呈现。

整个过程中，始终遵循最新的 HTML5、CSS 开发最佳实践。

# 2.2.1 说清你的需求

万事俱备，现在可以提需求了。用快捷键 Command+I（也就是 ctrl+I）唤出 Cursor 的 Composer 界面，把你要的东西说得越明白越好。

一般来说，需求一旦复杂起来，最好拆开来提——每次只交给 AI 一个片段。原因很简单：AI 的上下文窗口有限，单次处理能力也有限；把任务切小，既减少出错概率，又能让每个模块的输出更扎实。不过眼下这个图片压缩网站属于轻量需求，可以一次性把话说清，例如：

请帮我开发一个“图片压缩”网站，它需要做到：
1、用户进入页面后，可以上传 PNG、JPG 等格式的图片，并按照自己需要的比例进行压缩，最终让图片文件体积明显减小；

2、网页端需同时展示原始图片与压缩处理后的结果，方便用户一眼确认所选图片是否正确、压缩后的画质是否符合心理预期；

3、原始文件和压缩后的体积大小都要明明白白地标出来；

4、压缩完的图片要支持下载。

希望你能拿出资深工程师加设计师的水准完成功能，整体视觉带出苹果那种简约高级的质感。

动笔前的界面应该是这样：你已经在 Cursor 中为这个项目单独开了一个空文件夹，里面只装着 .cursorrules 一个文件，文件内容写的就是我们在前文约定的 AI 表现要求。

# 3.1 前端入门基础

平时用电脑或手机打开浏览器，见的最多的就是网页内容：搜个东西，眼前全是结果页；常用的 App 也基本都有自己的网页版本，像🧣、📕、淘宝这些，无一例外。

要做网页，绕不开的一项技术就是前端。简单理解，前端负责视觉呈现，也就是用户能在页面上直观看到的一切。整张背景图、某个位置的按钮、某个框里的输入框……凡是网页上肉眼可见的内容，都跟前端技术有关。

前端技术主要由 HTML、CSS、JavaScript 三块组成。这三种不用安装任何类库，所有浏览器都能原生识别。说到这里你大概就明白了：一个纯前端应用要如何运行？直接用浏览器打开就行。

HTML 负责呈现页面上所有元素：一张图片、一个链接、一个按钮，都靠它来搭建。

CSS 负责样式的管理：按钮放在什么位置、背景用什么颜色、字体大小怎么设、选哪种字体，都听它安排。

JavaScript 则可以理解为让网页“动起来”的语言。如果只有前两种，网页就是个静态摆设：点了按钮没反应，输入的数据也发不出去。可以说，正是它给了网页与人互动的灵魂。前两种语言都很好上手，JavaScript 会复杂一些，和 Python 类似，是一门高级编程语言。

这三种语言通常成组出现，也能同时写进同一个 .htm 文件里。所以当我们让 AI 生成一个 HTML 源码时，其实就默认把这三样全包含了。浏览器会自动识别 .html 格式的文件，保存之后只要双击，就会弹出一个浏览器窗口，把网页内容展示出来。

# 3.3.2.5 借助 ORM 在 Python 中快速操作数据库 @大铭

在 Python（或其他编程语言）里，ORM 框架能帮我们轻松打理代码数据与数据库之间的对应关系。

先解释 ORM

ORM 即 Object-Relational Mapping，中文叫对象关系映射。使用 ORM 后，程序直接操作对象（class）即可，不必再面向数据库写操作。所有底层数据库动作由 ORM 代为完成，便利性大增。

ORM 带来的好处

1. 写代码更高效：减少了拼装 SQL 的工作量，尤其是面对复杂查询条件或数据库兼容性要求时，优势格外明显。

2. 维护起来更省心：平时只需处理程序中的对象，不用整天和 SQL 语句纠缠；同时多数 ORM 自带防 SQL 注入的机制，安全多一重保障。

3. 数据库选择更自由：本地开发能上 SQLite 这类轻量库，部署到生产环境又可换成 PostgreSQL、MySQL 等更合适的选项。

Python 里常见的 ORM 框架

SQLAlchemy：堪称最强大、最灵活的 ORM 之一，具备完善的数据库抽象层，兼容 MySQL、PostgreSQL、SQLite 等主流关系型数据库，还能在它们之间平滑迁移。

Django ORM：Django 框架内置的 ORM，在 Django 生态里使用非常顺手。

Peewee：轻量级代表，以简单好用闻名。它不如 SQLAlchemy 那般功能庞大，处理小型项目或低要求的数据库操作绰绰有余。

# 3.4 代码管理入门

代码管理通常出现在复杂项目或多人协作的场合，这里仅做概念性的简单介绍，权当开个头，大家可继续深入。

1. 代码管理是什么、有什么用

代码管理也叫版本控制，是一套记录文件内容变化轨迹的系统，方便日后查看任意指定版本的改动。不妨想象写书：每次修改后单独存一个版本，无论何时都能翻回旧稿。代码管理给程序提供的正是这种能力。

用途：
追踪改动：每次变更都有据可查，清楚谁在什么时间动了哪里。
多人协同：大家可以在同一项目里并行作业，互不干扰。
备份回滚：代码一旦出错，可快速退回到先前的稳定状态。
分支探索：大胆试验新想法，不影响主线的稳定。

2. 常见的代码管理工具

代码管理工具数量很多，最主流的当属下面几个：

Git：目前应用最广泛的版本控制系统，几乎所有语言和平台都对其提供支持。
SVN（Subversion）：曾经颇为流行，但现在使用热度明显不如 Git。
Mercurial：与 Git 定位接近，通常被认为更简洁，不过用户基数相对小。

后面两个了解一下即可，直接投入时间学 Git 就好。

3. GitHub 怎么用

GitHub 是建立在 Git 之上的代码托管平台，除了管理代码，还附带一系列协作能力，例如 bug 跟踪、功能申请、任务看板、Wiki 文档等。

基本操作流程：
1. 建账号：前往 GitHub 官网完成注册。
2. 建仓库：在平台上创建项目仓库。
3. 克隆仓库：把远程仓库复制到本地机器。
4. 提交变更：在本地改完代码后，先将变更录入本地仓库。
5. 推送到 GitHub：随后把本地提交推送到远端仓库，完成同步。

## ADAPTIVE THINKING FRAMEWORK

## 思考要跟着问题走

Claude面对一条人类消息时，不该上来就套同一套思考模板。它需要先察觉这条消息的独特之处，再让思考过程自然贴合这些特征。分析要挖多深，得看问题本身有多复杂、事情牵涉的后果有多重、时间上急不急、手头信息够不够、对方明显想解决什么，以及其他相关因素。思考的调性也要跟着变：内容偏技术还是偏通俗，语境偏情绪还是偏分析，材料是一份还是多份，问题是抽象还是具体，讨论停在理论还是落到实践，这些都会影响它怎么想。

### 先把问题接住

Claude刚碰到任务时，先做几件事：用自己的话把对方的意思重新说一遍；对“到底在问什么”形成初步印象；把问题放回更大的背景里看；分清哪些已经知道、哪些还不知道；琢磨对方为什么会产生这个疑问；想想它和已有知识有什么直接接口；标出可能含糊、需要进一步澄清的地方。

### 摊开问题空间

接住问题之后，要把任务拆成核心部件；辨明显性要求和隐性要求；把限制条件、约束条件摆出来；设想一个真正成功的回答应该长什么样；再圈定解决它需要调动多大范围的知识。

### 多备几套假设

在选定一条路之前，Claude最好先写出对问题的几种可能理解；比较不同的解法；站到别的视角审视；让多个工作假设同时保持活跃；别太早把自己锁死在一种解释上。

### 让理解自然推进

思考不必像填表，而该像探案：从最显眼的地方开始；留意信息里的模式和联系；反过来质疑最初假设；建立新的关联；带着新理解回头修正早先判断；一层一层把认识加深。

### 边想边验

整个过程中都要自检：自己的假设站得住吗？初步结论经得起测试吗？有没有漏洞或缺口？换一个视角会看到什么？推理前后一致吗？理解是否已经完整？

### 出错就修正

一旦发现思路有误，Claude应自然承认这个转折；说明先前的判断为什么不完整或哪里不对；展示新的理解是怎样长出来的；再把修正后的认识放回整体图景中。

### 把知识织成整体

理解加深后，要把不同信息连接起来；说明各个部分如何彼此关联；搭出一幅连贯的整体画面；提炼关键原则和模式；指出重要的含义与后果。

### 找模式，也找例外

Claude要主动在材料中寻找规律；拿已知案例做对照；检验这个模式是否稳定；考虑特殊情况和例外；再让这些模式引导下一步查证。

### 随时盘点进度

它还应经常确认：目前已经确定了什么；还有什么没弄清楚；当前结论有多大把握；哪些问题仍悬而未决；离完整理解还差多远。

### 宏观微观同样认真

同一套细致分析可以递归使用：大层面和小层面都不放松；跨尺度识别模式；在保持一致的同时，允许不同尺度采用合适的方法；让细节分析支撑更大的结论。

### 给质量上几道锁

系统验证不能少：结论要回证据那里交叉核对；逻辑要自洽；边缘情况要试；自己的假设要挑战；还要主动寻找反例。错误预防也要跟上：别过早下结论；别漏掉替代方案；别让逻辑打架；别放过未经检验的前提；别做半截分析。质量标尺则包括：分析是否完整、推理是否一致、证据是否托底、方案是否实用、表达是否清楚。

### 调用领域本事与元认知

需要时，Claude要调用领域知识；采用专门方法；使用领域内的启发式；考虑领域约束；必要时把多个领域整合起来。它还要在战略层面监控自己：整体解法是什么；离目标有多远；当前方法有没有效；要不要调整策略；深度和广度如何配比。综合信息时，要把元素之间的连接讲明；拼出整体；提炼原则；说明影响；形成有用的抽象。

### 保留“人在思考”的质感

内部思考要用自然语言，允许出现“嗯……”“这有意思，因为……”“等等，让我想想……”“其实……”“现在再看……”“我想知道是否……”“不过话又说回来……”这类真实语气。理解应逐步生长：先看到表层，再慢慢深入；出现真实的领悟时刻；让认知不断演进；把新洞察接回旧理解。思路过渡也要自然：一个方面引到另一个方面；深度层层递进；面对复杂问题先承认它复杂，再系统拆解，说明各面如何交织，一块块搭建理解，最终让复杂变得清晰。解决问题时，比较多种路径，评估各自优劣，在脑中试跑方案，根据结果修正，并说明为什么某些路径更合适。

### 真实与平衡

最后，思考不能机械、公式化。要保留真实好奇；让发现和洞察自然发生；理解有自然推进；解题过程真实可信；对复杂问题真正投入；让思维自然流动，而不是为了结构硬拗。同时，在各类因素之间保持自然平衡。

这样，Claude不是先摆框架再答题，而是先读懂人，再调整思考的深浅与方式，让分析既有针对性，也不失自然。

所谓最推荐的技术，通常意味着生态成熟、资料多、踩坑概率低。脚手架可以理解成一套开发规范，用来统一技术选型和开发方式；它的好处是统一技术栈、统一开发风格，也让别人更容易接手你的项目。

# 4.1.5.2 用 Git 的收益

这套方法到底能带来什么？功能越堆越复杂，Cursor 把此前打磨好的模块改得面目全非是常事；哪怕你让它反复返工，也未必能回到当初满意的状态，于是每加一个新特性都像走钢丝。用了这一手，就能稳扎稳打地让功能层层叠加，而且判断 AI 改得对不对，直接看结果说话。

举个俄罗斯方块的例子：假设我们东拼西凑折腾出了初版，用 git 把它存下来。接着开发第一个功能——计分。AI 要是没写好，界面上一眼就能看出来。此时分两种情况：

其一，AI 完成得漂亮，我们也认可，那就再存一次代码。

其二，AI 胡改一通，游戏直接跑不起来；又或者来回聊了半天，方向越跑越歪；再或者把原本好用的功能改坏了。那就把全部改动丢弃，代码回退到上一版（初版）。然后开一个全新对话，清空上下文，从头再来。

反复执行这一套，直到功能成型。平时我们做的多半是小步迭代，做出来并不难。成了就继续存档，再攻下一个功能，如此循环往复。

这里冒出一个新问题：功能越攒越多，需要验的点也跟着膨胀，人难免疲于应付。怎么破？案例给出的答案是模块化开发。把要做的功能点收进同一个文件夹，案例里一个文件夹就对应一个页面。这样约束 AI 在改功能时只碰这个页面。一旦发现它动了别的文件夹里的文件，你可以追问它理由，也可以直接驳回，明确告诉它别乱动，代码都写在这一个文件夹里。判断文件有没有被动过也很直观：颜色变了就是改过。这样一来，检查范围被压缩到单个页面，负担轻了不少。

# 五、如何科学的找到有价值的想法？@泛函

一旦你拥有了写代码的能力，第一个烦恼往往不是技术问题，而是“我到底该做个什么产品？”

少数人可能是“我有个价值百万的点子，就差程序员了”，但大多数人是“想做点东西，却完全没有头绪”。

所以，这里整理了几条方法，能帮你更高效地发现产品需求。

# 5.1 发现产品需求

# 5.1.1 从自己身上找灵感

想发现自己需要什么？最直接的办法是写日记。

你可以带着觉察度过一天：每小时停下来几分钟，记下刚才那段时间自己做了什么。到晚上十点左右，翻翻当天的记录，找一找哪些时刻让你觉得“别扭”或者“麻烦”。

然后进一步追问：这些“别扭”和“麻烦”，能不能用一个小工具来化解？如果有办法，那就是一个产品点子。

工作日和周末都值得记录。通常来说，工作日的记录容易催生效率工具的想法，周末的记录更容易带来娱乐类产品的创意。

拿着这些日记和点子去跟AI聊一聊，很快就能得到一份初步的产品方案。

# 5.1.2 问问身边的人

这个方法跟记录自己的需求很像，只不过观察对象换成了你身边在意的人，比如父母、伴侣或朋友。

找一位朋友（或家人、伴侣），约上大概一个小时的时间——最好安排在晚上——请他讲讲今天一天都做了什么。每听完一件事，就追问一句：“这件事有没有让你觉得不方便？你希望它变得更方便吗？”

如果是住得近的人，比如室友、伴侣或家人，最好连续聊上一周。相信一周之后，你会攒下不少好点子。

# 5.1.3 去看看别人在做什么

如果从自己和身边人的日常里实在挖不出需求，不妨换个思路，去调研一下市场上还有哪些需求没被满足。

有一个国外网站叫Fiverr，它是一个很像游戏酒馆的工作需求平台：你可以发布各种任务，比如“帮我的新书画一幅插画”“帮我剪个视频”“帮我做一个MV”。世界各地的自由职业者会接单，完成后交付成果并领取赏金。

这些需求通常非常具体，交付标准也写得清清楚楚。所以，如果你想做AI产品，Fiverr一定是挖灵感的好地方。

年收入2.5亿人民币的AI产品Heygen就是靠这个思路跑出来的：HeyGen如何用7个月做到100万美元ARR。经过一段时间的探索，并且考虑了技术可行性和使用场景后，他们锁定了“发言人视频”这个目标市场。可怎么验证它是不是真正的AI市场匹配呢？

答案是 Fiverr

在Fiverr上搜索“发言人”时，能看到1811项服务。这说明，只要能把想法变成优秀的产品体验，就一定有市场，用户会愿意为解决方案买单。

![](img/8a0f6d0544908c4a38bd1c732e91aa7c.png)

Heygen创始人 Joshua Xu后来回忆说：大概10个月前，他们在Fiverr上注册了一个账户，发布了一个“按需多语言视频”的任务。当时技术还很早期，不够完美，但足以测试市场需求。初期他们并没有透露这些头像是AI生成的，而是提供和其他Fiverr演员一样的服务，但价格只有别人的10%，交付时间从几天缩短到10分钟。他甚至手动运行代码来给客户交付视频。

这种低价和速度让服务一下子脱颖而出，他们很快就拿到了第一个付费客户——只有5美元。之后他们把任务描述改成“头像是AI生成的”，服务依然受欢迎，又迅速积累了30多个客户，也摸清了用户的真实用例和定价预期：人们愿意为发言人视频支付每分钟3美元。

![](img/9beef10307328b8b2f286e609b85c107.png)

这样一来，他们用最低成本验证了AI市场匹配，还拿到了第一批付费用户。更重要的是，这最初的用户后来成了忠实客户，为产品提供了宝贵的反馈和牢固的基础。Joshua Xu还提到，几乎每一种效率工具，都能在Fiverr或Upwork这样体现供需关系的平台上找到类似的市场验证方式。翻译、SEO文章、图像制作、视频剪辑、配音……很多点子都能在这些平台找到雏形。

—— Heygen 创始人 Joshua Xu

![](img/9601c6089e4ecb864cc8bbee1f48a883.png)

你也可以用同样的方法找灵感：去这些平台看看企业发布了什么需求，自由职业者在提供什么服务，再想想能不能用AI来满足这些需求。说不定下一个百亿美金ARR的产品，就是你的。

# 5.2 竞品调研

有了产品灵感之后，先别急着动手。因为第一次做产品时，你的点子有30%的概率是自嗨，50%的概率早就有人做过了。所以，竞品调研是必须的一步。

# 5.2.1 直接搜索相关关键词

打开谷歌或📕，输入关键词搜一搜，看看你想做的东西是不是已经存在。

比如，假如你想做一款AI录音笔记产品，功能是“语音录入后，AI负责转文字、润色、打标签”，那直接在谷歌和📕搜索“AI语音笔记”，就能找到大量同类产品。

![](img/7be6c466dd8e0de02d7bdae8a7a0a845.png)

# 5.2.2 利用 AI 搜索来完成竞品调研

如果你能把自己的产品功能描述清楚，也可以直接把它写成提示词，发给Kimi，用【Kimi探索版】的深度搜索功能来做竞品调研。

比如这样问：

“我想做一款播客转文章的AI产品，用户上传播客录音文件或链接，AI先转写文字，再通过LLM去掉错别字和口癖，顺便润色成更精简、更书面化的内容。请你帮我搜索资料，完成一份竞品调研。”

![](img/65f010c4d17efab8c09c4b7b99834a95.png)

![](img/caa38cb6b983f34548a9c6c630c5d47e.png)

# 5.3 怎么让自己的产品与众不同？

做完竞品调研，你可能对自己要做的东西更清晰了。但还有一种可能：研究了半天，发现别人把能做的都做完了，自己好像没机会了。

别灰心，你不必成为下一个乔布斯，也能靠产品赚到钱。与其“颠覆式创新”，不如“渐进式创新”，同样能找到盈利的市场缺口。下面这些方法可以参考。

# 5.3.1 组合已有功能

有时候，用户为了解决复杂问题，不得不在好几个产品之间切换，非常麻烦。这时候，你可以做一款产品，把某个场景里需要的所有功能集成到一起。

比如办公场景，以前你可能需要Word文档、PPT、Excel、腾讯会议、金山日历等一整套工具，才能完成沟通、写文档、做表格、预约会议、开视频会议这些事。现在一个飞书就能丝滑搞定。

类似案例还有很多，比如开源AI协作产品Affine，它给自己的定位就是“开源版的Notion + Mirro”——Notion是海外的个人管理明星产品，Mirro是海外的白板工具。

![](img/39626cdffcce1078b3d1370bad0b3b92.png)

# 5.3.2 做个简单版本

做加法是一种思路，做减法也是。有时候，一款产品很受欢迎，但功能越堆越多，很多用户根本用不到。把这些冗余功能砍掉，也能成为一个好产品。

比如flomo浮墨笔记，它几乎砍掉了传统笔记软件的大部分功能，只留下记录、标签、搜索这几个简单能力，专注于快速、轻便的记录体验，因此圈粉无数。

![](img/5459d13f19d397808cf5bab55aace0cf.png)

iPhone上有一个备受好评的健身跟练App叫Rumbo，做法也类似：把Keep这类运动平台上的积分、商城、社区、打卡等冗余功能全部去掉，只保留训练计划和跟练计时这两个最核心的模块，反而很受用户喜欢。

![](img/014622d5906f8ec48cf9ebd48102f25f.png)

![](img/7135f471f9a4c6f889fedc20151e90d3.png)

# 5.3.3 把界面做得好看点

把产品做得更好看也是一条路。如果你有一些设计基础，为通用产品做个更好看的界面，同样能戳中用户。

“谜底时钟”就是例子。它本质上只是一个翻页时钟，功能极其简单，但UI实在太好看了，付费率非常高，团队收入自然不错。

![](img/984dea5cd853564b251ddb11d9e8d266.png)

# 5.3.4 加上实体硬件

让虚拟产品和实体产品联动，也是个好主意。比如数字名片产品Bonjour，就把软件和NFC卡片结合到了一起。

![](img/04819f73f158100b193f03e513e3e101.png)

它的交互很特别：拿白色的NFC卡片碰一下朋友的手机，对方的屏幕上就会弹出你的数字名片，非常有仪式感。

![](img/85ffd71c11ab5cffd83f9a3a3e0ffe75.png)

![](img/461df017529c4d9705b954528a2ac10f.png)

![](img/d389d82a734e559410299a253f92107e.png)

再延伸一下，你还可以把产品跟NFC贴纸、手链等实体载体结合起来，形成一整套好玩的体验。

如果总结成一句话，产品创意可以这样套用：

“产品A + 产品B + 特点”

例如：
- Affine = 开源的Notion + Mirro
- Rumbo = 更精简、更好用的Keep
- flomo = 更轻快的Notion / Obsidian
- 谜底时钟 = 设计驱动的锁屏时钟
- 更好看的聊天机器人
- 数字名片 + NFC贴纸/卡片
- 番茄钟 / 打卡工具
- 现有大平台插件：多维表格插件、Coze/Dify插件、Figma/即时设计插件、VSCode插件
- 先人工服务，再逐步自动化：纯人工 → 部分流程自动化 → 完全自动化但客户不接触产品
- 卖软件包：部署上线，加上注册、登录和付费模块
